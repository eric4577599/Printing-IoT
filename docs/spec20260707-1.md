### 2.1 工作項 1:動手前資料安全驗證(gate,必須最先做)

**功能描述**:確認零件資料在 MmsDB 完整無缺後,才允許對主系統動任何刀。

**輸入**:FlexoDB(5433)與 MmsDB(5434)之 `Parts` / `Suppliers` / `SupplierParts`。
**輸出**:三表兩庫 `COUNT(*)` 對照表,寫入本回 RD 報告。

**流程**:
1. 確認兩座 Postgres 容器運行中(`docker compose ps`;未運行先啟動)。
2. 逐表執行 `SELECT COUNT(*)`,FlexoDB 與 MmsDB 必須逐表相等。
3. 確認 `MM/backups/` 最新 `flexodb-backup-*.sql` 存在、非空、內容含三表。
4. 全程**唯讀**,兩庫皆不得寫入。

**Edge case**:

| 情境 | 預期行為 |
|---|---|
| 任一表筆數不一致 | **立即中止本回全部工作**,回報差異明細(表名、兩邊筆數),主系統零異動 |
| MmsDB 缺任一表 | 同上中止(表示回2 前置不成立) |
| 任一容器連不上 | 先嘗試啟動;仍失敗則中止回報,不得繞道改連別庫 |

### 2.3 工作項 3:EF migration `RemoveSmartPartsModule`

**功能描述**:以 migration 將 FlexoDB 的 `Parts` / `Suppliers` / `SupplierParts` 三表 drop;Down 可完整還原三表**結構**(資料還原不在 Down 責任內,靠 MM backups)。

**輸入**:工作項 2 完成後的模型。
**輸出**:`backend/PrintingIoT.Infrastructure/Migrations/` 新增一組 `*_RemoveSmartPartsModule.cs` + `.Designer.cs`,並更新 `PrintingContextModelSnapshot.cs`。

**規則**:
- 以 `dotnet ef migrations add RemoveSmartPartsModule` 產生(EF 依模型差異自動產 DropTable),比照 `20260606021031_RemoveMaintenanceModule` 檢查產出。
- **Up**:先 drop 子表 `SupplierParts`,再 `Parts`、`Suppliers`(EF 自動處理順序,RD 須人工複核)。
- **Down**:CreateTable 重建三表,必須含 — 全部欄位與型別、Guid PK、`IX_Parts_InternalPN` 唯一索引、`SupplierParts→Parts` 與 `SupplierParts→Suppliers` 兩組 Restrict FK〔勘誤:原誤寫 Cascade〕、`Price` 的 precision 設定。與 drop 前 schema 逐項一致。
- 註解正體中文,說明 Up/Down 輸入輸出邏輯。

**驗證流程(必做並留紀錄)**:
1. 對 FlexoDB `database update` 套用 → `psql \dt` 確認三表消失、其餘表無恙。
2. `database update <前一個 migration>` 執行 Down → `psql \d` 逐項比對三表結構(欄位/索引/FK)與移除前一致。
3. 再次 `database update` 回到最新(最終狀態 = 三表已 drop)。

**Edge case**:

| 情境 | 預期行為 |
|---|---|
| FlexoDB 三表有資料(必然,原資料未動) | drop 照做 — 資料已在 MmsDB 且有備份;報告註明資料去向 |
| backend-api 容器在驗證期間重啟 | 啟動即自動 `MigrateAsync` 套用;RD 須控制驗證順序避免搶跑(§1.2) |
| Down 後再 Up | 可重複執行,結果一致(migration 本身保證) |
| 有人誤以為 Down 會還原資料 | 報告與 migration 註解明寫:Down 僅還原結構,資料還原須另從 `MM/backups/` 匯入 |
