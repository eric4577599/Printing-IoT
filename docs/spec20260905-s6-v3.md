## 2. 缺口一 · 登入帳號大小寫語意(定案:不分大小寫)

> 本節與 §3、§4、§5、§6 內容自 v1 起未變更,**v1 已施工完成且通過驗收**,保留於此供 RD 與 Tester 對照,不需重做。

### 2.1 決策與理由(已定案,RD 不得改採他案)

**採「帳號不分大小寫」**:

1. 現場是**觸控終端**,作業員不該因為大小寫打錯而登不進去 —— 這正是 S5 §12 R2 想避免的失效模式。
2. 建立端(`AuthController.CreateUser`)**早已是不分大小寫唯一**(S5 §4.2、AC-22),登入端本來就該一致。
3. 精確比對的代價(部署時大小寫必須逐字對齊、錯了只會看到「帳號或密碼錯誤」)全部落在最沒有除錯能力的人身上。

### 2.2 正規化定義(唯一的一份定義,全系統共用)

```
Normalize(s) = (s ?? "").Trim().ToUpperInvariant()
```

- **大寫**而非小寫:與既有 `AppRoles.Normalize` 同一慣例,也與 ASP.NET Core Identity 的 `NormalizedUserName` 一致。
- **含 Trim**:觸控鍵盤與條碼槍常帶入前後空白,`" op1 "` 必須能登入(AC-49)。
- **只作用於帳號**。密碼、顯示名稱、班別一律不動。

### 2.3 現況分歧(v1 施工前的事實,供追溯)

| 位置 | v1 施工前 |
|---|---|
| `AuthController.cs:57` | `.FirstOrDefaultAsync(u => u.Username == request.Username)` —— **精確比對** |
| 同檔 `:202-204` | `StringComparison.OrdinalIgnoreCase` 檢查重複,且**載入全表後在記憶體比對** |
| `PrintingContext.cs:73-74` | `Username` 唯一索引**未指定不分大小寫定序** —— DB 層沒有背書 |

## 3. 應用層與資料庫層一致化(選型與理由)

### 3.1 選定方案:新增 `UsernameNormalized` 欄位 + 唯一索引

`Users` 新增 `UsernameNormalized`(varchar(50), NOT NULL),值恆為 `Normalize(Username)`,並在其上建**唯一索引**。
登入查詢與重複檢查一律比對這個欄位。

### 3.2 為什麼不選另外兩案(必須寫進報告)

| 方案 | 為什麼不選 |
|---|---|
| **改索引定序**(PostgreSQL ICU non-deterministic collation 或 `citext`) | ① 相等語意藏在資料庫定序裡,`u.Username == x` 這行程式碼看不出它不分大小寫;② **EF Core InMemory 不支援 collation**,核心 AC(「建 `OP1` 用 `op1` 登入成功」)在測試環境根本驗不出來,等於又造一個沒有驗收出口的洞;③ `citext` 需安裝擴充,屬部署環境變更 |
| **存入前一律轉小寫、直接覆寫 `Username`** | 破壞顯示:`OP1` 會被存成 `op1`,名冊與稽核日誌全變小寫,現場 OP1~OP5 命名慣例消失。**帳號的顯示形態必須保留**(AC-47 / AC-55 釘住) |

選定方案的代價:多一個欄位、必須保證兩欄永遠同步。第二點以 §3.3 的**實體層自動同步**消除。

### 3.3 實體層自動同步(防呆,不可改成手動設定)

`backend/PrintingIoT.Core/Entities/Auth/User.cs`:

```
Username           : required string   // 保留原始大小寫,供顯示與稽核;setter 內同步寫入 UsernameNormalized
UsernameNormalized : string            // 對外唯讀(private set),值恆為 Normalize(Username),[Required][MaxLength(50)]
```

任何建立路徑(controller、seed、既有測試的 `new User { Username = "op1", ... }`)都自動正確,
既有測試因此**不需要修改**(AC-52 / AC-62 反向釘住這個保證)。

### 3.4 正規化工具

`backend/PrintingIoT.Core/Constants/AppUsernames.cs`(與 `AppRoles.cs` 同層同命名空間):

```
public static class AppUsernames
{
    public static string Normalize(string? username);   // (username ?? "").Trim().ToUpperInvariant()
}
```

函式級註解用正體中文,說明輸入 / 輸出 / 邏輯,並註明「大寫慣例與 `AppRoles.Normalize` 一致」。

### 3.5 後端改動點

| 檔案 | 改動 |
|---|---|
| `Core/Entities/Auth/User.cs` | 依 §3.3 新增 `UsernameNormalized` 與 `Username` 的同步 setter |
| `Core/Constants/AppUsernames.cs` | **新增**,§3.4 |
| `Infrastructure/Data/PrintingContext.cs` | 新增唯一索引 `IX_Users_UsernameNormalized`;**保留**既有 `Username` 唯一索引 |
| `API/Controllers/AuthController.cs`(Login) | `var normalized = AppUsernames.Normalize(request?.Username); ... FirstOrDefaultAsync(u => u.UsernameNormalized == normalized)`。其餘邏輯(`IsActive`、BCrypt、失敗訊息不區分原因、限流)全部保持 S5 現狀 |

## 4. 資料庫 migration

**檔名**:`backend/PrintingIoT.Infrastructure/Migrations/20260905010000_AddUsernameNormalizedUniqueIndex.cs`
(+ `.Designer.cs`,並更新 `PrintingContextModelSnapshot.cs`)。

**Up(順序不可調換)**:

1. `AddColumn "UsernameNormalized"` varchar(50),先 `nullable: true`。
2. `Sql`:`UPDATE "Users" SET "UsernameNormalized" = UPPER(TRIM("Username"));`
3. `AlterColumn` 改為 `nullable: false`。
4. `CreateIndex` `IX_Users_UsernameNormalized`,`unique: true`。

**Down**:`DropIndex` → `DropColumn`。

**本機無法套用(必須在報告標明)**:本機沒有 Docker、不連真實 PostgreSQL,migration 只能產生與編譯,
**無法實際 apply**。`PrintingIoT.Tests` 走 EF Core InMemory,不經 migration。

**對既有資料的影響(必須寫成部署前置檢查)**:

- 正常情況:既有帳號完全不受影響,大小寫原樣保留。
- **唯一會失敗的情況**:資料庫已存在僅大小寫不同的兩個帳號(例如 `OP1` 與 `op1`),第 4 步建唯一索引失敗、整個 migration 回滾。
- 部署者**套用前**先跑,回傳空集合才可繼續:

  ```sql
  SELECT UPPER(TRIM("Username")) AS n, COUNT(*)
  FROM "Users" GROUP BY 1 HAVING COUNT(*) > 1;
  ```

- **ASCII 限定的等價性註記(v3 新增,見 §13 第 9 項)**:上述 PostgreSQL 的 `UPPER(TRIM(...))`
  與 C# 的 `Trim().ToUpperInvariant()` **只在 ASCII 帳號上等價**。非 ASCII 字母的大小寫映射、
  以及 `TRIM` 與 `String.Trim()` 對非空白類 Unicode 空白字元的處理都可能不同(E21 已把非 ASCII 帳號劃出範圍)。
  這句必須寫在報告的檢查 SQL 旁邊,避免有人把它當成通用保證。
- 本 migration **不做任何自動合併** —— 自動挑一筆刪除會靜默毀掉某個人的帳號。

## 7. 前端改動 —— 名冊 `username` 的**兩個**寫入點

`localStorage.appUsers` 是**同一份資料,兩個元件都會寫**。任何一邊寫錯,現場都會出現
「點名冊登入 → 401 → 只顯示帳號或密碼錯誤」。兩邊的欄位語意必須完全一致:

| 欄位 | 語意 |
|---|---|
| `id` | 使用者代碼,例如 `OP1`。名冊內的主鍵 |
| `name` | 顯示名稱,例如 `王小明`。**只供顯示,永不作為帳號** |
| `username` | **後端帳號**,值即代碼(`OP1`)。這是送進 `POST /api/v1/auth/login` 的字串 |
| `role` / `shift` | 沿用既有語意,本輪不動 |
| `password` | **永遠不得存在**(S5 E14 / AC-61 釘住) |

### 7.1 `frontend/src/modules/auth/LoginModal.jsx`(**v1 已完成,保留,不得回退**)

| 位置 | 現況(v1 施工後) |
|---|---|
| `sanitizeRoster`(`:18`) | `username: u?.username ?? u?.id ?? u?.name ?? ''` |
| `handleAddUser`(`:162`) | `username: newUserCode` |

`handleUserRowClick`(`:113`)行為不變:只填入帳號,密碼仍須手動輸入。

### 7.2 `frontend/src/components/settings/GeneralTab.jsx`(**本版新增,D-1**)

| 位置 | 現況(錯) | 改為 |
|---|---|---|
| 名冊白名單重建(`:63`) | `username: u?.username ?? u?.name ?? ''` | `username: u?.username ?? u?.id ?? u?.name ?? ''` |
| `handleAddUser` 建立列物件(`:111`) | `username: newUserName`(顯示名稱當帳號) | `username: newUserCode`(代碼即後端帳號) |

限制與注意事項:

1. **只改這兩行**(必要時補函式級正體中文註解說明為何 `username` 必須是代碼)。
   該檔的公司抬頭、班別、原因主檔、匯入匯出等區塊**一行都不要動**。
2. 不得新增 i18n 鍵(避免 `localeParity` 測試變紅),不得新增相依套件。
3. `:67` 與 `:135` / `:149` 的 `localStorage.setItem('appUsers', ...)` 三個寫入呼叫維持原樣 ——
   本輪只改寫入**內容**,不改寫入時機。
4. `handleUserClick`(編輯既有列)不動:它只把 `id` / `name` / `shift` 填回表單,
   按下「更新」時 `username` 由 `newUserCode` 重新推導,因此編輯後 `username` 會跟著代碼走(E25)。
