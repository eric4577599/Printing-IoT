## 最大的三個根因

1. **身分驗證從未被當成系統邊界**。後端 JWT 管線裝好但全專案零個 `[Authorize]`,前端自建一套明文帳密的假登入且已打包進正式 bundle,MM 的 `Auth:Enabled` 預設 false 屬 fail-open。
2. **資料真相來源從未被定義**。同一份排程同時活在 localStorage、Redis 與 PostgreSQL,誰覆寫誰靠時序決定。`POST /api/orders/sync` 是無條件全量鏡像刪除,報表四頁只讀瀏覽器本機資料。
3. **模擬器路徑與真機路徑分岔演化,而開發只驗模擬器**。真機 WISE 路徑不寫 `ProductionLogs`、狀態硬寫死字串 `"1"`,接上真硬體那天生產歷史是空的。

另有兩條橫向問題:單機台單廠假設已寫進資料模型(全域單鎖、單一 Redis key、Worker clientId 硬寫死);以及零可觀測性與零備份,使上述靜默失效無人發現。

## 三向介面現況

- **上行 ERP／MES**:唯一已實作的是 `POST /api/erp/push-orders`,無認證、無冪等。IoT→ERP 的回拋方向(實際產量、完工回報、停機原因、稼動率)完全不存在,且資料模型中也沒有可回拋的內容。
- **MCP**:兩個 repo 皆無任何 MCP server 實作或設定。導入成本低且適合唯讀問答,但須先補認證與完工資料模型,寫入型工具暫緩。
- **下行 PLC 硬體**:MQTT 是唯一真的在跑的通道(Mosquitto 1884,匿名、無 ACL、無 TLS);Modbus 與 OPC UA 僅存在於文件與設定下拉選單,無實作。`IMachineDriver` 宣告了但無任何實作類別,裝置相容靠 Worker 內逐一猜欄位名的 `TryGetProperty`。
- **平行 MM**:與主系統共用 docker network 與 cloudflared 通道,資料庫分離。兩大缺口是沒有單一登入,以及保養觸發所需的機台累計運轉量無同步管道,保養目前只能是純日曆制。

## 改善路線

1. **第一階段 · 止血(1 到 2 週)**:全後端預設拒絕的授權原則、改掉鏡像刪除語意、對外埠收攏綁 127.0.0.1、環境改回 Production、Redis 掛 volume、建立 pg_dump 排程。
2. **第二階段 · 補整合(4 到 8 週)**:真機路徑補寫生產歷史並與模擬路徑合流、完工回報落地、ERP 推單補冪等、新增 ERP 回拋介面、報表改讀後端、落實 `IMachineDriver`、MM 建立設備對映與運轉量同步。
3. **第三階段 · 工程化(3 到 6 個月)**:健康檢查與可觀測性、MQTT QoS 1 與自動重連、資料模型補多廠多機台維度、稽核軌跡、migration 改受控部署、清理技術債與補核心測試。
