# 規格:PRIIOT ⇄ MM 整合契約 v1(草案,待 MM 確認)

> 依據:設計說明書 §14(2026-11-16,Eric 決定)。本檔為契約草案;MM 確認後雙邊各存一份。
> 範圍:本系統(PRIIOT)提供的**唯讀**整合端點與機器身分 `MM_SERVICE`。不含 MM 端實作。

## 1. 通則

- 前綴 `/api/v1/integration`,契約版本 `1`(回應標頭 `X-Contract-Version: 1`)。破壞性變更才升版;新增欄位不算。
- 認證:`X-Api-Key`(機器身分 `MM_SERVICE`)。例外:`login-codes` 簽發端點用使用者的 JWT(見 §3)。
- 時間一律 UTC ISO-8601(`...Z`);顯示用時區由 MM 自行轉 `Asia/Taipei`。
- 錯誤:`{"error":{"code":"…","message":"…"}}`;碼:`unauthorized`(401)、`forbidden`(403)、`not_found`(404)、`invalid_request`(400)、`rate_limited`(429)。
- JSON 一律 camelCase。

## 2. 機器身分 `MM_SERVICE`

- 與 `ERP_SERVICE` 同規格:只能由 API 金鑰取得,不可指派給人,不列入角色表。
- 新 policy `MmRead`:只接受 `X-Api-Key`,角色 `MM_SERVICE`(**不**接受 ADMIN 的 JWT 以外的混用;ADMIN 人工驗證可用 Swagger 帶金鑰)。
- 金鑰只能打本契約的端點,打不開 ERP 推單與其他端點(金鑰角色與端點 policy 互斥)。

## 3. 端點

| 端點 | 認證 | 說明 |
|---|---|---|
| `GET /health` | MM_SERVICE | `{status:"ok", apiVersion:"1", serverTimeUtc}`;MM 用來判斷降級 |
| `POST /introspect` | MM_SERVICE | body `{token}`;回 `{active, userId, username, displayName, roles[], expiresAtUtc}`。權杖無效、過期或使用者已停用 → 只回 `{active:false}`,不洩漏原因 |
| `POST /login-codes` | 使用者 JWT(任何角色) | body `{audience:"mm"}`;回 `{code, expiresInSeconds:60}`。單次有效,存 Redis,綁 audience |
| `POST /login-codes/exchange` | MM_SERVICE | body `{code}`;回同 introspect 的使用者資訊;代碼**原子刪除**,第二次兌換回 `invalid_request` |
| `GET /devices` | MM_SERVICE | `[{deviceId, lastSeenUtc}]`(由歷史紀錄的不重複 deviceId 彙整),供 MM 下拉對照 |
| `GET /devices/{deviceId}/counter?sinceId=&limit=` | MM_SERVICE | 見 §4 |
| `GET /devices/{deviceId}/status-events?sinceId=&limit=` | MM_SERVICE | 見 §5 |

- `deviceId` 比對:不分大小寫、忽略前後空白(與 MM 的一對一規則一致)。
- `limit` 預設 500、最大 1000。

## 4. 計數 `counter`

回應:`{deviceId, items:[{id, timestampUtc, count, status, resetBefore}], nextSinceId}`。

- `id` 為歷史紀錄的遞增主鍵;`sinceId` 之後(不含)的紀錄,依 `id` 遞增。`nextSinceId` = 本批最大 `id`(無資料則原樣回傳 `sinceId`)。MM 以它做游標,**去重鍵為 `(deviceId, id)`**。
- `count` = 機台計數原始值。**單調性不保證**:新值小於前一筆代表歸零(換單、斷電、PLC 重置),此時 `resetBefore=true`。MM 累計時:`resetBefore=false` 加差值;`resetBefore=true` 把新值當新起點的增量。
- **取樣粒度**:歷史紀錄有節流(狀態變化必寫,否則每 `data_log_interval` 秒一筆),因此補回的是節流後的樣本,不是每筆計數;累計值以最後一筆為準。
- ⚠ 待驗證:現場計數是否為「每張工單歸零」或「累計不歸零」。實機確認前,MM 必須自行處理歸零。

## 5. 狀態事件 `status-events`

回應:`{deviceId, items:[{id, timestampUtc, status, previousStatus}], nextSinceId}`。

- 只回「狀態與前一筆不同」的紀錄(狀態轉換)。`status` ∈ `Unknown | Running | Idle | Error | Maintenance`。
- 故障起訖 = `status=Error` 的轉入與轉出;精度為取樣間隔。**沒有故障碼**(待 PLC 暫存器確認);只作維修依據的提示,不自動建單(由 MM 使用者決定)。
- ⚠ 待驗證:現場 PLC/WISE 是否真的把故障對映成 `Error`。

## 6. 安全與限制

- 全部唯讀。金鑰明文只在建立時回傳一次(沿用現有機制);撤銷即時生效。
- 速率限制:每把金鑰 60 次/分,超過回 429。
- `introspect` 結果不由 PRIIOT 快取;MM 端快取 TTL 30–60 秒(MM 設計文件定案)。
- 帳號停用:`introspect` / `exchange` 即時反映(`active:false`)。已發出的 PRIIOT 權杖本身最長仍可用 2 小時(已知限制 B1),但經此端點驗證即被拒。

## 7. 實作順序與驗收

1. `MM_SERVICE` + `MmRead` policy + 金鑰建立可選此角色(只限 ADMIN)。
2. `health`、`introspect`、`login-codes`、`exchange`。
3. `devices`、`counter`、`status-events`。
4. 驗收(DoD):xUnit 授權矩陣(金鑰打不開其他端點、ERP 金鑰打不開本契約、停用使用者 `active:false`、代碼單次有效與過期、`resetBefore` 判定、游標去重);再以真實金鑰對運作中的 API 跑一次實測。
