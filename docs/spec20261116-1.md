# 規格:PRIIOT ⇄ MM 整合契約 v1(定稿,2026-11-16;雙邊已對齊)

> 依據:設計說明書 §14(2026-11-16,Eric 決定)。MM 已回覆確認(含補充 8 項),本檔併入後定稿;雙邊各存一份。
> 範圍:本系統(PRIIOT)提供的**唯讀**整合端點與機器身分 `MM_SERVICE`。不含 MM 端實作。

## 1. 通則

- 前綴 `/api/v1/integration`,契約版本 `1`(回應標頭 `X-Contract-Version: 1`)。破壞性變更才升版;新增欄位不算。
- 認證:`X-Api-Key`(機器身分 `MM_SERVICE`)。例外:`login-codes` 簽發端點用使用者的 JWT(見 §3)。
- 時間一律 UTC ISO-8601(`...Z`);顯示用時區由 MM 自行轉 `Asia/Taipei`。
- 錯誤:`{"error":{"code":"…","message":"…"}}`;碼:`unauthorized`(401)、`forbidden`(403)、`not_found`(404)、`invalid_request`(400)、`rate_limited`(429,**帶 `Retry-After` 標頭**)、`service_unavailable`(503,Redis 或後端暫時不可用)、`cursor_expired`(410,見 §4)。
- JSON 一律 camelCase。401 / 403 由驗證層回應,**沒有本文**(只看狀態碼);其餘錯誤才有 `error` 本文。

## 2. 機器身分 `MM_SERVICE`

- 與 `ERP_SERVICE` 同規格:只能由 API 金鑰取得,不可指派給人,不列入角色表。
- 新 policy `MmRead`:只接受 `X-Api-Key`,角色 `MM_SERVICE`(**不**接受 ADMIN 的 JWT 以外的混用;ADMIN 人工驗證可用 Swagger 帶金鑰)。
- 金鑰只能打本契約的端點,打不開 ERP 推單與其他端點(金鑰角色與端點 policy 互斥)。

## 3. 端點

| 端點 | 認證 | 說明 |
|---|---|---|
| `GET /health` | MM_SERVICE | `{status:"ok", apiVersion:"1", serverTimeUtc}`;MM 用來判斷降級 |
| `GET /users/{userId}` | MM_SERVICE | **MM 每個請求重驗用**。回 `{active, userId, username, displayName, roles[]}`;`userId` 不存在或已停用 → **固定回 200 `{active:false}`**(不用 404,避免區分「不存在」與「已停用」)。`roles[]` 為本系統角色原字串 |
| `POST /introspect` | MM_SERVICE | 給其他用途:body `{token}`(本系統 JWT);回 `{active, userId, username, displayName, roles[], expiresAtUtc}`。無效、過期或已停用 → 只回 `{active:false}` |
| `POST /login-codes` | 使用者 JWT(任何角色) | body `{audience:"mm"}`;回 `{code, expiresInSeconds:60, redirectUrl}`。單次有效,存 Redis,綁 audience。`redirectUrl` = 設定檔中的 MM 入口網址 + `#code=<code>`(**用網址片段,不放 query string**,不進 access log 與 Referer);MM 前端讀到後 POST 給 MM 後端兌換。MM 入口網址由本系統設定檔管理,不寫進文件 |
| `POST /login-codes/exchange` | MM_SERVICE | body `{code}`;回 `{active, userId, username, displayName, roles[]}`(`roles[]` 為角色原字串 `ADMIN`/`ENGINEER`/`SUPERVISOR`/`OPERATOR`,角色對映在 MM 端做);**只回使用者資訊,不回本系統權杖**;代碼**原子刪除**,第二次兌換回 `invalid_request` |
| `GET /devices` | MM_SERVICE | `[{deviceId, lastSeenUtc}]`(由歷史紀錄的不重複 deviceId 彙整),供 MM 下拉對照 |

- `devices/{deviceId}/…` 在歷史紀錄裡**完全沒出現過**該 `deviceId` → **404 `not_found`**(MM 視為「對不到」,不當成零計數)。
| `GET /devices/{deviceId}/counter?sinceId=&limit=` | MM_SERVICE | 見 §4 |
| `GET /devices/{deviceId}/status-events?sinceId=&limit=` | MM_SERVICE | 見 §5 |

- `deviceId` 比對:不分大小寫、忽略前後空白(與 MM 的一對一規則一致)。
- `limit` 預設 500、最大 1000;`status-events` 的 `limit` 計的是**掃描的歷史紀錄筆數**,回傳的轉換筆數可能更少。回應含 `hasMore`(布林):`true` 表示還有資料,MM 可立刻續拉。

## 4. 計數 `counter`

回應:`{deviceId, items:[{id, timestampUtc, count, status, resetBefore}], nextSinceId, hasMore}`。`deviceId` 為**正規化後**的值(去前後空白、與資料庫存的原樣大小寫);`count` 型別為 **64 位元整數**(以小數儲存的原始值取整數部分輸出)。

- **首次連線**:`sinceId` 省略時**只回最新一筆作為基準,不回補歷史**;可改帶 `sinceUtc`(回該時間點之後的紀錄)。MM 以「連線當下讀數」為起算點。
- **`cursor_expired`(410)**:`sinceId` 大於目前最大 `id`(例如資料庫被還原或重置)時回 410,MM 須重新取基準。目前歷史紀錄**沒有自動清理機制**;日後若加保存期限,會在此契約公告並於清理後讓過舊的游標回 410。

- `id` 為歷史紀錄的遞增主鍵;`sinceId` 之後(不含)的紀錄,依 `id` 遞增。`nextSinceId` = 本批最大 `id`(無資料則原樣回傳 `sinceId`)。MM 以它做游標,**去重鍵為 `(deviceId, id)`**。
- `count` = 機台計數原始值。**單調性不保證**:新值小於前一筆代表歸零(換單、斷電、PLC 重置),此時 `resetBefore=true`。MM 累計時:`resetBefore=false` 加差值;`resetBefore=true` 把新值當新起點的增量。
- **取樣粒度**:歷史紀錄有節流(狀態變化必寫,否則每 `data_log_interval` 秒一筆),因此補回的是節流後的樣本,不是每筆計數;累計值以最後一筆為準。
- ⚠ 待驗證:現場計數是否為「每張工單歸零」或「累計不歸零」。實機確認前,MM 必須自行處理歸零。

## 5. 狀態事件 `status-events`

回應:`{deviceId, items:[{id, timestampUtc, status, previousStatus}], nextSinceId, hasMore}`。`deviceId` 同上為正規化值;**第一筆的 `previousStatus` 可為 `null`**;`sinceId` 省略的首次連線行為與 counter 相同(只回最新一筆狀態作基準)。

- 只回「狀態與前一筆不同」的紀錄(狀態轉換)。`status` ∈ `Unknown | Running | Idle | Error | Maintenance`。
- 故障起訖 = `status=Error` 的轉入與轉出;精度為取樣間隔。**沒有故障碼**(待 PLC 暫存器確認);只作維修依據的提示,不自動建單(由 MM 使用者決定)。
- ⚠ 待驗證:現場 PLC/WISE 是否真的把故障對映成 `Error`。

## 6. 安全與限制

- 全部唯讀。金鑰明文只在建立時回傳一次(沿用現有機制);撤銷即時生效。
- 速率限制分兩桶,**互不搶額度**:資料桶(`health`、`devices`、`counter`、`status-events`)每把金鑰 60 次/分;身分桶(`users`、`introspect`、`login-codes/exchange`)每把金鑰 120 次/分。超過回 429 並帶 `Retry-After`。
- 本系統不快取 `users` / `introspect`;**MM 端快取 TTL 定為 30 秒**,MM 工作階段絕對上限 12 小時,但每個請求都以 `GET /users/{userId}` 重驗。
- 帳號停用:`users` / `exchange` / `introspect` 即時反映(`active:false`);因此 MM 側延遲上限 = 快取 TTL(30 秒)。
- 本系統不可達時 MM 對已登入工作階段給寬限(**Eric 已同意**:最後一次成功重驗後 10 分鐘內照常使用,MM 端可設定;寬限內只能檢視與建紀錄、不能做管理動作),超過要求重新登入;本系統全掛期間無人能新登入 MM(不留本機緊急管理員)。

## 7. 實作順序與驗收

1. `MM_SERVICE` + `MmRead` policy + 金鑰建立可選此角色(只限 ADMIN)。
2. `health`、`users/{userId}`、`introspect`、`login-codes`、`exchange`。
3. `devices`、`counter`、`status-events`。
4. 驗收(DoD):xUnit 授權矩陣(金鑰打不開其他端點、ERP 金鑰打不開本契約、停用使用者 `active:false`(`users` / `exchange` / `introspect` 三處)、`users` 不存在與停用回應一致、代碼單次有效與過期與 audience 綁定、兩個限速桶互不影響、`sinceId` 省略與 410、未知 deviceId 回 404、`resetBefore` 判定、游標去重);再以真實金鑰對運作中的 API 跑一次實測。
