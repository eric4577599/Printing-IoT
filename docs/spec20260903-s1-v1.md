## 1. DF-04 — 排程同步改為 upsert 語意

### 1.1 現況與後果

`SyncScheduleAsync` 收到整份清單後,逐欄無條件覆寫既有列、依陣列位置重設 `Sequence`,
再把清單外的所有列 `_context.Orders.Remove` 掉。後果:多終端互刪、ERP 剛推的單被前端 800ms 後的
自動同步吃掉、一次請求即可清空整份排程。

### 1.2 請求契約(新)

端點維持 `POST /api/orders/sync`,**請求本體由「裸陣列」改為物件**。

新增 `backend/PrintingIoT.Core/DTOs/ScheduleSyncRequest.cs`:

```
public class ScheduleSyncRequest
{
    public List<OrderSyncDto> Orders { get; set; } = new();
    public List<Guid> DeleteIds { get; set; } = new();   // 明確刪除清單;未列入者一律不刪
}

public class OrderSyncDto
{
    public Guid? Id { get; set; }
    public string? OrderNumber { get; set; }
    public string? CustomerName { get; set; }
    public decimal? TargetLength { get; set; }
    public OrderStatus? Status { get; set; }
    public int? Sequence { get; set; }        // 保留供相容,後端忽略(以陣列位置為準)
    public string? BoxType { get; set; }
    public string? PaperSpec { get; set; }
    public int? Quantity { get; set; }
    public string? ProductCode { get; set; }
    public DateTime? DeliveryDate { get; set; }
    public string? ProductionBatch { get; set; }
    public string? TraceCode { get; set; }
    public string? SpecJson { get; set; }
}
```

介面改為 `Task<IEnumerable<Order>> SyncScheduleAsync(ScheduleSyncRequest request);`。

### 1.3 行為規則

1. **比對鍵**:依序
   a. `Id` 有值且資料庫存在 → 更新該列;
   b. 否則 `OrderNumber` 非空白且資料庫有同號列 → 更新該列(多筆同號取 `CreatedAt` 最早的一筆);
   c. 否則新增(`Id` 有值就沿用該 GUID,否則新產生;`CreatedAt` 未設時填 `DateTime.UtcNow`)。
2. **不自動刪除**:清單外的既有列一律保留,`Sequence` 也不動。
3. **明確刪除**:只刪 `DeleteIds` 中存在於資料庫的列;找不到的 id 靜默忽略。
   同一 id 同時出現在 `Orders` 與 `DeleteIds` → **以 upsert 為準不刪除**,並記一筆 warning log。
4. **重排序保留**:`Orders` 中第 i 筆的 `Sequence = i`(0-based,與現行一致)。
5. **空請求保護**:`Orders` 與 `DeleteIds` 皆空 → 不動作,直接回傳現況。
   `Orders` 空但 `DeleteIds` 有值 → 只執行刪除。
6. **回應**:同步後的全部訂單,依 `Sequence` 升冪(同序以 `CreatedAt` 升冪)。

### 1.4 前端配合

- `frontend/src/services/api.js`:`syncSchedule(orders, deleteIds = [])` → `POST /orders/sync` 送 `{ orders, deleteIds }`。
- `frontend/src/components/layout/MainLayout.jsx` 的 `deleteOrder(orderId)`:本地移除後,若 `isGuid(orderId)`
  就呼叫既有的 `DELETE /api/orders/{id}`(`apiDeleteOrder`);失敗只 `console.warn`,不阻塞 UI。
  **理由**:鏡像刪除拿掉後,若前端不主動送刪除指令,刪除功能會退化成「只在本機消失」。
- debounced 鏡像同步照舊每 800ms 送整份清單,但 `deleteIds` 傳空陣列。

## 2. DF-05 — 目標長度與楞別不再被歸零

### 2.1 現況與後果

`toBackendOrder` 沒有輸出 `targetLength` 與 `paperSpec`,後端又整欄無條件賦值,
於是每次自動同步都把 ERP 推來的目標長度寫成 0、楞別清空。**兩邊都要修**。

### 2.2 後端:只更新呼叫端實際提供的欄位

`SyncScheduleAsync` 更新既有列時,逐欄判斷:

| 情況 | 行為 |
|---|---|
| 欄位為 `null`(呼叫端未提供) | **不覆寫**,保留既有值 |
| 欄位為非 null 值(含空字串 `""`、`0`) | 視為呼叫端明確指定,覆寫 |

適用欄位:`OrderNumber`、`CustomerName`、`TargetLength`、`Status`、`BoxType`、`PaperSpec`、
`Quantity`、`ProductCode`、`DeliveryDate`、`ProductionBatch`、`TraceCode`、`SpecJson`。
新增列時,null 欄位使用實體預設值(字串 `string.Empty`、數值 `0`、`Status = Pending`)。

### 2.3 前端:`orderMapper.js` 補兩個欄位

`toBackendOrder(order, sequence)` 增加:

- `paperSpec`:取 `order.paperSpec || order.flute`;**只有非空字串才輸出這個鍵**,否則整個鍵不輸出
  (`JSON.stringify` 會略過 `undefined`,後端收到 null → 不覆寫)。
- `targetLength`:取 `order.targetLength ?? order.targetLen`,經 `Number()` 後
  **只有 `Number.isFinite` 為真才輸出這個鍵**,否則不輸出。

`fromBackendOrder(be)` 增加還原(置於 `...spec` 之後):

- `paperSpec: be.paperSpec || spec.paperSpec || ''`
- `targetLength: Number(be.targetLength ?? spec.targetLength ?? 0)`
- `flute` 不動(仍由 SpecJson 還原),避免影響 `OrderDetailsModal` 的既有顯示。

## 3. ERP-02 — 推單冪等與產品碼唯一索引

### 3.1 推單改 upsert(依 `OrderNumber`)

`PushOrdersAsync` 對每一筆:

- 資料庫已有同 `OrderNumber` 的訂單(多筆取 `CreatedAt` 最早)→ **更新**,ERP 為權威來源,覆寫
  `CustomerName`、`TargetLength`、`BoxType`、`PaperSpec`、`Quantity`、`ProductCode`、
  `DeliveryDate`、`ProductionBatch`、`TraceCode`。
- **不動** `Id`、`CreatedAt`、`Sequence`、`Status`、`SpecJson`(避免把生產中的單打回 `Pending`、
  避免清掉前端排程位置與規格 payload)。
- 沒有同號 → 新增,`Status = Pending`、`Sequence = 0`。
- **同一批次內出現重複 `OrderNumber`** → 第二筆更新同一列,兩列皆回成功、共用同一個 `OrderId`。

### 3.2 產品碼唯一索引與先查再建

- `PrintingContext.OnModelCreating` 加:
  `modelBuilder.Entity<Product>().HasIndex(p => p.ProductCode).IsUnique();`(索引名 `IX_Products_ProductCode`)。
- 附 EF migration(建議名稱 `AddProductCodeUniqueIndex`),**只建索引,不改欄位型別、不刪資料**。
  若環境沒有 `dotnet-ef` 工具,可手寫 migration 檔並同步更新 `PrintingContextModelSnapshot.cs`。
- 自動建立佔位產品前**先查再建**:批次開始時一次載入涉及的 `ProductCode` 字典,
  新建的產品同步寫回字典,確保同批次內同碼只建一筆。
- **部署注意(寫進 migration 檔的中文註解)**:正式庫若已有重複 `ProductCode`,建立唯一索引會失敗;
  上線前需先由 DBA 清理重複資料。本輪不執行任何資料清理。

## 4. SEC-05 / ERP-10 — 推單端點防護與逐列回應

### 4.1 批次筆數上限

- 設定鍵 `Erp:MaxPushBatchSize`,預設 **1000**;寫入 `backend/PrintingIoT.API/appsettings.json`
  (`"Erp": { "MaxPushBatchSize": 1000 }`),`ErpController` 以 `IConfiguration` 讀取,取不到就用預設值。
- 超過上限 → **HTTP 400**,且**不寫入任何一筆**(在 Controller 進 Service 之前擋掉)。
  回應本體:`{ success = false, error = "批次筆數超過上限", maxBatchSize = <上限>, received = <收到筆數> }`。
- 本體為 `null` → 400,`error = "請求本體不可為空"`。
- 空陣列 → **200**,`total = 0`、`results = []`(不視為錯誤,維持既有寬鬆行為)。

### 4.2 逐列欄位驗證

在 Service 內以常數定義上限,逐列驗證,**驗證失敗的列不寫入,其餘照寫**:

| 欄位 | 規則 | 失敗訊息 |
|---|---|---|
| `OrderNumber` | 必填、非空白 | 訂單編號不可為空 |
| `OrderNumber` | ≤ 50 字元 | 訂單編號超過 50 字元 |
| `CustomerName` | ≤ 100 字元 | 客戶名稱超過 100 字元 |
| `BoxType` | ≤ 50 字元 | 箱型超過 50 字元 |
| `PaperSpec` | ≤ 100 字元 | 楞別超過 100 字元 |
| `ProductCode` | ≤ 50 字元 | 產品碼超過 50 字元 |
| `ProductionBatch` | ≤ 50 字元 | 生產批號超過 50 字元 |
| `TraceCode` | ≤ 100 字元 | 追溯碼超過 100 字元 |
| `Quantity` | ≥ 0 | 數量不可為負 |
| `TargetLength` | ≥ 0 | 目標長度不可為負 |

一列有多個錯誤時,回報第一個命中的訊息即可。
`Order` 實體本身**不加 `MaxLength`**(避免額外的欄位型別 migration),長度規則只在 Service 層把關。

### 4.3 回應契約(新)

新增 `backend/PrintingIoT.Core/DTOs/ErpPushResultDto.cs`:

```
public class ErpPushRowResultDto
{
    public int Index { get; set; }              // 輸入陣列位置(0-based),供呼叫端定位
    public string OrderNumber { get; set; } = string.Empty;
    public bool Success { get; set; }
    public string? Error { get; set; }          // 成功時為 null
    public Guid? OrderId { get; set; }          // 成功時為後端 Id
}

public class ErpPushResponseDto
{
    public bool Success { get; set; }           // 全部成功才為 true
    public int Total { get; set; }
    public int Succeeded { get; set; }
    public int Failed { get; set; }
    public List<ErpPushRowResultDto> Results { get; set; } = new();
}
```

- `PushOrdersAsync` 回傳型別由 `Task<int>` 改為 `Task<ErpPushResponseDto>`,同步更新 `IOrderService`。
- `results` 順序與輸入順序一致。
- 部分成功仍回 **200**;只有「批次上限」與「本體為 null」回 400。呼叫端一律解析 `results` 判斷成敗。
- 寫入策略:先驗證整批 → 只把通過的列加入/更新 → **單次 `SaveChangesAsync`**。
  不使用顯式交易(EF InMemory provider 不支援),以「先驗證再寫入」達成「壞列不落地」。

## 6. Edge case 與預期行為

| 情境 | 預期行為 |
|---|---|
| sync 請求本體為 `null` | HTTP 400,不動資料 |
| sync `Orders` 為空、`DeleteIds` 為空 | 不動作,回傳現況(保留現行的暫態保護) |
| sync `Orders` 為空、`DeleteIds` 有值 | 只刪除指定列 |
| sync 同一 id 在 `Orders` 出現兩次 | 後出現者勝(最終 `Sequence` 為其陣列位置),不建立第二列 |
| sync `Id` 提供但資料庫沒有 | 以該 GUID 新建,不拋出錯誤 |
| sync `OrderNumber` 為空白且無 `Id` | 一律新建(不做空號比對) |
| sync 資料庫有多筆同 `OrderNumber` | 取 `CreatedAt` 最早的一筆更新,並記 warning log |
| sync `SpecJson = null` | 不覆寫既有 `SpecJson` |
| sync `Status = null` | 不覆寫既有狀態(生產中的單不會被打回 Pending) |
| 推單 `orderDtos = null` | HTTP 400,`error = "請求本體不可為空"` |
| 推單空陣列 | HTTP 200,`total = 0`、`results = []` |
| 推單整批都驗證失敗 | HTTP 200,`success = false`、`succeeded = 0`,資料庫零寫入 |
| 推單 `ProductCode` 為空字串 | 不建立佔位產品,不套用 `OptPhase`/`OptGap`,該列仍算成功 |
| 推單命中既有產品 | 套用 `OptimizationPhase`/`OptimizationGap`,不新增產品 |
| 推單筆數剛好等於上限 | **通過**(上限為含),超過才 400 |
| 前端刪除訂單但後端 `DELETE` 失敗 | 本地仍移除,`console.warn`,不阻塞 UI(下次開頁會由後端資料復原該列) |
| 後端回傳 `paperSpec = ""` 而 SpecJson 有值 | `fromBackendOrder` 退回 SpecJson 的值 |

### 8.2 實作已定、本版正式確認的語意

以下幾點 v1.0 沒寫死,實作各自做了決定。**這些決定判定為正確,列為規格的一部分,不得再改**;
Tester 若看到與直覺不同,以本節為準。

1. **`fromBackendOrder` 兩個欄位的退回運算子刻意不同**
   - `paperSpec: be.paperSpec || spec.paperSpec || ''` —— 後端空字串**會**退回 SpecJson(空楞別視同沒值)。
   - `targetLength: Number(be.targetLength ?? spec.targetLength ?? 0)` —— 只有 `null`/`undefined` 才退回;
     後端明確的 `0` 是合法目標長度,**不**退回 SpecJson。
2. **`toBackendOrder` 用「不輸出鍵」而非 `null` 表達「未提供」**。`JSON.stringify` 會略過 `undefined`,
   後端反序列化成 `null` → `ApplySyncDto` 不覆寫。斷言時要用 `'paperSpec' in payload === false`,不是 `=== null`。
3. **sync 的空請求保護在 Service 層**:`Orders` 與 `DeleteIds` 皆空 → 直接回傳現況,不進 `SaveChangesAsync`。
4. **推單空陣列在 Service 層早退**:回 `Success=true, Total=0, Results=[]`(HTTP 200)。
5. **長度上限只在 Service 層(`ValidatePushRow`)把關**。`Order` 實體既有的 `[MaxLength]` 標註
   (BoxType 50 / PaperSpec 100 / ProductCode 50 / ProductionBatch 50 / TraceCode 100)數值與 Service 常數一致,
   `OrderNumber`(50)、`CustomerName`(100)實體本來就沒有標註 —— **不要為了對齊而改實體**,那會多一次欄位型別 migration。
6. **sync 與推單對 `null` 的處理刻意相反**:sync 是「null 不覆寫」(前端鏡像同步不該清空 ERP 的值);
   推單是「`dto.X ?? string.Empty` 即清空」(**ERP 為權威來源**,ERP 沒給就代表該欄位真的沒有)。
   這是設計決定,不是不一致的 bug。
7. **migration 檔名 `20260903000000` 排在既有最後一支 `20260726075633` 之後**,順序正確;
   `PrintingContextModelSnapshot.cs` 已同步更新。

### 8.5 已知殘留風險(本輪不處理,列入下輪候選)

- **Sequence 基準不一致**:`ReorderSequenceAsync` 寫 `index + 1`、`SyncScheduleAsync` 寫 `index`(0-based)。
  兩個端點對同一批資料會給出差 1 的序號基準。屬既有問題,本輪不動。
- **正式庫可能無法套用唯一索引**:既有 `Products` 若有重複 `ProductCode`,migration 會失敗,
  需 DBA 前置清理(migration 檔註解已載明)。本輪不寫任何資料清理腳本。
- **前端刪除為「先本地移除、背景送 DELETE」**:DELETE 失敗時本地與後端短暫不一致,要重新載入頁面才會復原。
- **`Erp:MaxPushBatchSize` 屬營運參數**,調整不需改程式,但 `appsettings.json` 的預設值變更仍算設定異動。
