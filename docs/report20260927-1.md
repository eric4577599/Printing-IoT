## 3. 意外發現

### 3.1 🔴 B18 — Worker 的 MQTT 斷線後不會重連

驗收時注入訊號,Redis 完全沒動。追下去:

- Worker 日誌從 **2026-09-26 01:17 UTC(台灣 09:17)** 起每 10 秒一行 `MQTT Client disconnected. Reconnecting...`,
  到今天共四萬多行;Redis `factory/monitor` 的最後一筆還停在 9/15。
- 從 Worker 容器對 `mqtt-broker:1883` 的 TCP 是通的,broker 本身也活著。
- **根因在程式碼**:`Worker.cs` 只在 `StartAsync` 連一次,沒有掛 `DisconnectedAsync`;
  `ExecuteAsync` 的迴圈(`Worker.cs:100-104`)**只印「Reconnecting」,實際上什麼都沒做**。
  日誌的字面意思是在重連,其實沒有。

影響:只要 broker 或網路閃斷一次(Docker Desktop 休眠、Mac 睡眠、broker 重啟都算),
Worker 就永久失聰,**所有 PLC 訊號直到有人重啟 Worker 為止全部遺失**,而且畫面上看不出來。

處置:已 `docker restart printingiot-backend-worker-1`,重啟後注入訊號立即進 Redis,確認恢復。
**這只是止血** —— 下次斷線還是會再發生。修法方向:掛 `DisconnectedAsync` 做退避重連並在重連後重新訂閱
(或改用 MQTTnet 的 ManagedClient),再加一個「Worker 多久沒收到訊息」的健康檢查,讓失聰能被看見。

另:broker 的 stdout 日誌停在 2026-08-21,之後沒有任何輸出,排查時沒有 broker 端的證據可用。

### 3.2 🟡 B19 — 車速送不到前端

注入 `speed: 50` 後 Redis 是 `speed: 50`,但同一時間 `/api/monitor/realtime` 回的是 `speed: 0`、
`deviceId: null`、`timestamp: 0001-01-01`,畫面車速也一直是 0;計數(di1)則有更新。
看起來 API 端是從別的來源組這筆資料,和 Redis 不一致。**沒有深究**,但它讓「車速不為 0 不准完工 / 退回」
這兩道現場防呆在目前環境下**實際上無法觸發**。
