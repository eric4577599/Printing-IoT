## 0. 這一輪在解什麼問題

現況是「門鎖裝好了但沒上鎖」:

| 層 | 現況 | 後果 |
|---|---|---|
| 後端 | `Program.cs` 已註冊 JwtBearer 並驗 issuer/audience/lifetime/signing key,但**全後端零個 `[Authorize]`** | 所有 API 對任何人開放 |
| 後端 | `AuthController.SetupAdmin` 密碼走 **query string**,建立角色字串 `"Admin"` | 密碼進伺服器日誌與瀏覽器歷史 |
| 前端 | `AuthContext.jsx` 頂端 `export const USERS` 四組**明文帳密**;`LoginModal.jsx` 另有 OP1~OP5(密碼 `123`);`GeneralTab.jsx` 再有 OP1~OP3(密碼 `123`) | 憑證進 bundle 並已推上 GitHub |
| 前端 | 登入成功把**含密碼的整個物件**寫進 `localStorage.currentUser`;開發模式自動以管理者登入 | 密碼落在瀏覽器儲存 |
| 前端 | `api.js` 只設 baseURL,**無 Authorization 標頭、無攔截器** | 即使後端上鎖也無法通過 |
| 前端 | `loginDirect()` 可**不帶密碼**直接登入(LoginModal 選人即登入) | 真登入被繞過 |
| 前端 | `/debug` 路由在 `MainLayout` 之外 | 連假登入這層都繞過 |
| 角色 | 前端 `ADMIN / SUPERVISOR / OPERATOR / ENGINEER`(全大寫),後端建 `"Admin"` | 兩邊對不上,授權必然失效 |
| 週邊 | 限流以 `RemoteIpAddress` 分區但未啟用 ForwardedHeaders | 反向代理後所有人歸成同一來源 |
| 週邊 | `app.UseRateLimiter()` 註冊在 `app.UseCors()` **之前** | 429 缺 CORS 標頭,瀏覽器看到不明錯誤 |
| 週邊 | `appsettings.Development.json` 含已進版控的 `Jwt:Secret` | 簽章密鑰外洩 |

**本輪最大風險**:現場作業員目前用的就是前端硬編碼那幾組帳號。改成真登入後,若資料庫沒有對應使用者,
現場**完全無法操作**。因此本規格把「初始化路徑」當成一等公民(§4),而非附帶事項。

## 2. 角色詞彙與權限矩陣

### 2.1 正式角色名稱

選定**全大寫**作為正式詞彙(前端既有寫法即是,改動面最小,且大寫在權杖 claim 中不易與顯示名稱混淆):

| 角色代碼 | 中文 | 層級 | 說明 |
|---|---|---|---|
| `ADMIN` | 系統管理者 | 4 | 全權,含使用者管理與系統設定 |
| `ENGINEER` | 工程師 | 3 | 系統設定、模擬 / 除錯,不含使用者管理 |
| `SUPERVISOR` | 領班 | 2 | 主檔維護(產品、原因)、排程,不含系統設定 |
| `OPERATOR` | 作業員 | 1 | 現場操作:看板、排程狀態、報工 |

**正規化規則(兩道保險,缺一不可)**:

1. `AuthController` 簽發權杖時,角色一律 `role.Name.ToUpperInvariant()` 後才寫入 `ClaimTypes.Role`
   → 資料庫殘留舊值 `"Admin"` 也會發出 `"ADMIN"`,不會因舊資料而授權失效。
2. Migration 執行 `UPDATE "Roles" SET "Name" = UPPER("Name")` 把既有列正規化(§9)。

角色常數集中於新檔 `backend/PrintingIoT.Core/Constants/AppRoles.cs`,前後端不得再出現角色字面值散落。

### 2.2 授權原則(policy)

於 `Program.cs` 定義:

| Policy 名稱 | 允許角色 | 用途 |
|---|---|---|
| (fallback,無名) | 任何已驗證身分 | 未明確標註的端點一律套用 |
| `UserAdmin` | ADMIN | 使用者管理 |
| `SystemConfig` | ADMIN, ENGINEER | 通訊 / 機台 / 箱型設定、模擬與除錯 |
| `MasterDataWrite` | ADMIN, SUPERVISOR, ENGINEER | 產品主檔、原因主檔的寫入 |

**fallback policy**:`options.FallbackPolicy = new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build();`
—— 這是「預設拒絕」的核心,新增的 Controller 若忘記標註也會被擋下,而不是默默開放。

### 2.3 端點權限矩陣

| Controller / 端點 | 方法 | 授權 | 備註 |
|---|---|---|---|
| `/api/v1/auth/login` | POST | **`[AllowAnonymous]`** | 唯一必須匿名的端點:未登入者取得權杖的唯一入口 |
| `/api/v1/auth/setup-admin` | POST | **`[AllowAnonymous]`** | 必須匿名(空資料庫時世上還沒有任何可用身分),但受「Users 表為空 + 一次性設定權杖 + 密碼強度」三重保護,見 §4.1 |
| `/api/v1/auth/users` | GET / POST | `UserAdmin` | 新增,見 §4.2 |
| `/api/v1/auth/users/{id}` | PUT | `UserAdmin` | 改顯示名稱 / 班別 / 角色 / 密碼 / 停用 |
| `/api/docs` `/api/docs/{filename}` | GET | 已驗證 | 系統設計文件不再匿名公開,**這是刻意的行為變更** |
| `/api/monitor/realtime` `/api/monitor/history` | GET | 已驗證 | 現場看板需要 |
| `/api/orders` `/api/orders/{id}` | GET | 已驗證 | |
| `/api/orders` `/api/orders/{id}` `/api/orders/{id}/status` `/api/orders/reorder` `/api/orders/sync` | POST/PUT/DELETE | 已驗證 | **刻意不限角色**:現場排程拖拉與開完工由作業員操作,加角色限制會鎖住現場(見 §12 風險 R2) |
| `/api/products` `/api/products/{id}` | GET | 已驗證 | |
| `/api/products` `/api/products/{id}` | POST/PUT/DELETE | `MasterDataWrite` | 主檔寫入 |
| `/api/reasons` `/api/reasons/{id}` | GET | 已驗證 | 現場彈窗要讀原因清單 |
| `/api/reasons` `/api/reasons/{id}` | POST/PUT/DELETE | `MasterDataWrite` | 主檔寫入 |
| `/api/production/completions` | GET / POST | 已驗證 | **報工必須讓作業員做**,不得加角色限制 |
| `/api/production/completions/{id}` | GET | 已驗證 | |
| `/api/settings/factory-time` | GET | 已驗證 | 前端算工廠日要用 |
| `/api/settings/communication` `/api/settings/machine-sections*` `/api/settings/box-types` | GET | 已驗證 | 讀設定現場也需要 |
| 同上 | POST/PUT/DELETE | `SystemConfig` | 設定寫入 |
| `/api/simulation/test-mqtt` `/api/simulation/speed` | POST | `SystemConfig` | 模擬 / 除錯屬工程行為 |
| `/api/erp/push-orders` | POST | 已驗證(fallback) | **本輪起 ERP 無法呼叫**,S6 補 M2M 憑證。必須寫進交付報告 |

**標註方式**:Controller 類別層級加 `[Authorize]`(即使 fallback 已生效,明示優於默示,也讓 Swagger 產出正確),
方法層級以 `[Authorize(Policy = "...")]` 覆寫;`AuthController` 的 `login` / `setup-admin` 以 `[AllowAnonymous]` 開洞。

**匿名端點的理由(逐一交代)**:
- `login`:未登入者取得權杖的唯一入口,不可能要求先有權杖。
- `setup-admin`:資料庫為空時世上還沒有任何可簽發的身分;以「Users 表必須為空 + 環境變數設定權杖 + 密碼強度 + 專屬限流」四重條件收斂風險,詳 §4.1。

## 3. 後端功能規格

### 3.1 `Program.cs` 中介軟體順序(必須完全照此順序)

```
1. app.UseForwardedHeaders()        ← 最前面,任何讀 RemoteIpAddress 的東西之前
2. app.UseGlobalExceptionHandler()
3. app.UseSwagger / UseSwaggerUI    (Development / Testing)
4. app.UseCors("AllowFrontend")     ← 移到限流之前
5. app.UseRateLimiter()             ← 移到 CORS 之後,429 才會帶 CORS 標頭
6. app.UseAuthentication()
7. app.UseAuthorization()
8. app.MapControllers()
```

啟動期的 `MigrateWithRetryAsync` 不是中介軟體,移到 `var app = builder.Build();` 之後、管線設定之前,避免混淆閱讀順序。

### 3.2 ForwardedHeaders

```
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    o.ForwardLimit = 設定值 ForwardedHeaders:ForwardLimit,預設 1;
    o.KnownNetworks.Clear();
    o.KnownProxies.Clear();
});
```

- `KnownNetworks/KnownProxies` 清空的理由:Cloudflare Tunnel 與 Docker bridge 的來源位址不固定,無法白名單。
- **代價必須寫進註解與報告**:清空後 `X-Forwarded-For` 來自任何人都會被採信,因此本設定
  **只在 API 僅能經由通道對外時成立**;若日後 API 直接對公網開放,必須改回 `KnownProxies` 白名單。
- 以設定鍵 `ForwardedHeaders:Enabled`(預設 `true`)保留關閉開關;為 `false` 時不註冊該中介軟體。

### 3.3 限流

- 全域限流維持現狀(100 / 分鐘 / 來源),分區鍵仍用 `httpContext.Connection.RemoteIpAddress`
  —— `UseForwardedHeaders` 會改寫該值,因此**不需改動 lambda**,順序修好即生效。
- **新增**具名限流 `"auth"`:`PermitLimit` = 設定值 `RateLimit:Auth:PermitLimit`(預設 10)/
  `Window` = `RateLimit:Auth:WindowMinutes`(預設 1)分鐘,同樣以來源位址分區。
  以 `[EnableRateLimiting("auth")]` 掛在 `login` 與 `setup-admin` 上,阻擋暴力嘗試。

### 3.4 設定鍵(只寫 `appsettings.json`,不動 compose)

| 鍵 | 預設 | 說明 |
|---|---|---|
| `Auth:SetupToken` | `""` | **空字串 = `setup-admin` 完全關閉(回 404)**。部署時以環境變數 `Auth__SetupToken` 注入 |
| `Auth:MinPasswordLength` | `12` | 初始化與建立使用者的最低密碼長度 |
| `RateLimit:Auth:PermitLimit` | `10` | 登入 / 初始化端點每視窗允許次數 |
| `RateLimit:Auth:WindowMinutes` | `1` | 同上視窗長度 |
| `ForwardedHeaders:Enabled` | `true` | 是否啟用 X-Forwarded-* 處理 |
| `ForwardedHeaders:ForwardLimit` | `1` | 信任的代理層數 |

`appsettings.Development.json` **移除整個 `Jwt` 區塊**,只留 `Logging`。開發者改以環境變數
`Jwt__Secret` 或 `dotnet user-secrets` 提供;`Program.cs` 既有的例外訊息已足夠指引。
`appsettings.Testing.json` 內的測試用密鑰**保留不動**(測試專用、非正式環境憑證)。

## 4. 初始化路徑(本輪的可用性生命線)

### 4.1 `POST /api/v1/auth/setup-admin`

**輸入**(`[FromBody]`,不再有任何 query string 參數):

```
SetupAdminRequest {
  setupToken : string   // 必填,與 Auth:SetupToken 比對
  username   : string   // 必填,1~50 字,預設值不再寫死 "admin"
  password   : string   // 必填,長度 >= Auth:MinPasswordLength,須含至少一個字母與一個數字
  displayName: string?  // 選填,<= 50 字
}
```

**輸出**:`200 OK` + `{ username, roles: ["ADMIN"] }`。**不回傳權杖** —— 部署者必須另外走 `login`,
確保密碼確實可用,而不是拿到一個假裝成功的權杖。

**行為與狀態碼**:

| 情境 | 回應 | 說明 |
|---|---|---|
| `Auth:SetupToken` 未設定或為空 | `404 Not Found` | 端點視同不存在,不洩漏其存在性 |
| `setupToken` 不符 | `401 Unauthorized` | 以 `CryptographicOperations.FixedTimeEquals` 做定時比對,避免時序側通道 |
| Users 表已有任一使用者 | `409 Conflict` | 維持「只在使用者表為空時可用」的前提 |
| 密碼不符強度 | `400 Bad Request` + 具體原因 | **必須不建立任何使用者、不留下任何 Role 列** |
| `username` 空或超長 | `400 Bad Request` | |
| 全部通過 | `200 OK` | 見下方副作用 |

**副作用(成功時)**:
1. 建立四個角色列 `ADMIN` / `SUPERVISOR` / `ENGINEER` / `OPERATOR`(若尚未存在)。
2. 建立指定 username 的使用者,`PasswordHash` 為 BCrypt 雜湊,`IsActive = true`,綁 `ADMIN` 角色。
3. 寫一筆 `LogWarning` 稽核紀錄(含 username 與來源 IP,**不含密碼**)。

**檢查順序不可調換**:SetupToken 檢查必須在「Users 表是否為空」之前,否則會變成一個免驗證的
「資料庫有沒有使用者」探測器。

### 4.2 `POST /api/v1/auth/users`(`UserAdmin`)

**輸入**:

```
CreateUserRequest {
  username    : string   // 必填,1~50,不分大小寫唯一
  password    : string   // 必填,同上強度規則
  role        : string   // 必填,ADMIN | SUPERVISOR | ENGINEER | OPERATOR(大小寫不敏感,存入前正規化為大寫)
  displayName : string?  // 選填 <= 50
  shift       : string?  // 選填 <= 10,例:A / B / C
}
```

**輸出**:`201 Created` + `{ id, username, displayName, shift, roles }`(**永不回傳雜湊或密碼**)。

| 情境 | 回應 |
|---|---|
| username 已存在(不分大小寫) | `409 Conflict` |
| role 不在四個正式角色內 | `400 Bad Request` |
| 密碼不符強度 | `400 Bad Request` |
| 呼叫者非 ADMIN | `403 Forbidden` |
| 未帶權杖 | `401 Unauthorized` |

### 4.3 `GET /api/v1/auth/users`(`UserAdmin`)

輸出使用者清單 `[{ id, username, displayName, shift, roles, isActive, createdAt }]`,
**不含 `PasswordHash`**。此端點是前端名冊(§5.4)的資料來源。

### 4.4 `PUT /api/v1/auth/users/{id}`(`UserAdmin`)

**輸入**(全部選填,僅更新有給的欄位):`{ displayName?, shift?, role?, password?, isActive? }`。
輸出 `204 No Content`。找不到 → `404`;密碼不符強度 → `400`;role 不合法 → `400`。

**安全約束**:不得把最後一個 `IsActive` 的 ADMIN 停用或降級 → `409 Conflict`
(否則系統會沒有任何管理者可用,且 `setup-admin` 因 Users 表非空而無法救援)。

### 4.5 部署者操作順序(必須原樣寫進交付報告)

> **在第 5 步完成之前,現場完全無法操作系統。** 這是刻意的,不是缺陷。

1. 產生**新的** JWT 簽章密鑰,以 `Jwt__Secret` 環境變數注入(舊密鑰已外洩,見 §12 R4)。
2. 以 `Auth__SetupToken` 注入一組一次性隨機字串,重啟 API。
3. 套用 migration(§9)。
4. `POST /api/v1/auth/setup-admin`,建立第一個 ADMIN 帳號。
5. 以該 ADMIN `POST /api/v1/auth/login` 取得權杖,再逐一 `POST /api/v1/auth/users`
   建立現場帳號(至少要涵蓋目前使用中的 OP1~OP5,角色 `OPERATOR`)。
6. **清空 `Auth__SetupToken` 並重啟 API**(端點回歸 404)。
7. 前端重建容器(compose 掛原始碼、服務跑 build 產物,不重建不會上線)。

## 5. 前端功能規格

### 5.1 `frontend/src/services/authStorage.js`(新檔)

單一職責:權杖與使用者輪廓的持存,**唯一允許碰 `localStorage` 認證鍵的地方**。

| 函式 | 輸入 | 輸出 | 邏輯 |
|---|---|---|---|
| `saveAuth(token, profile)` | 權杖字串、輪廓物件 | 無 | 寫入 `authToken` 與 `authUser`;**寫入前以白名單挑欄位**,任何 `password` 欄位一律剔除 |
| `getToken()` | 無 | `string \| null` | 讀 `authToken` |
| `getProfile()` | 無 | `object \| null` | 讀 `authUser`,JSON 解析失敗回 `null` 並清除 |
| `clearAuth()` | 無 | 無 | 移除 `authToken` / `authUser`,並移除舊鍵 `currentUser`(遷移清理) |
| `isExpired(profile)` | 輪廓 | `boolean` | `profile.expiresAt` 早於現在即為 true |

輪廓白名單欄位:`username`、`displayName`、`roles`、`role`、`shift`、`sessionShift`、`expiresAt`。

### 5.2 `frontend/src/services/api.js`

**新增登入函式**(baseURL 已是 `${API_URL}/api`,故路徑為 `/v1/auth/login`):

```
login(username, password) → POST /v1/auth/login,body { username, password },回 response.data
```

**請求攔截器**:`getToken()` 有值時設 `config.headers.Authorization = 'Bearer ' + token`;無值時**不得**設此標頭。

**回應攔截器**(錯誤分支):

| 情境 | 行為 |
|---|---|
| 回應 401 **且** 請求 URL 不是登入端點 | `clearAuth()`,`window.dispatchEvent(new CustomEvent('auth:unauthorized'))`,再 `Promise.reject(error)` |
| 回應 401 **且** 請求 URL 是登入端點 | **不清除、不派發事件**,直接 reject —— 密碼打錯只該顯示「帳密錯誤」,不該引發全域登出風暴 |
| 回應 403 | 不清除權杖(身分有效、權限不足),直接 reject,由呼叫端顯示訊息 |
| 無 `error.response`(網路錯誤 / 後端不可達) | **不得**當成 401,不清除權杖,直接 reject |

### 5.3 `frontend/src/modules/auth/AuthContext.jsx`

**刪除**:`export const USERS`(整段四組明文帳密)、`loginDirect`、開發模式無條件自動登入。

**新介面**:

| 名稱 | 型別 | 說明 |
|---|---|---|
| `user` | `object \| null` | 已登入輪廓,含 `username` / `displayName` / `role` / `roles` / `shift` / `sessionShift` |
| `login(username, password)` | `async → { ok, reason? }` | `reason`:`'invalid'`(401)、`'network'`(無回應)、`'server'`(其他) |
| `logout()` | `() => void` | `clearAuth()` + `setUser(null)` |
| `setSessionShift(shift)` | `(string) => void` | 更新輪廓中的班別並持存(班別仍是前端 session 概念,不進權杖) |
| `isAuthenticated` | `boolean` | `user !== null` |
| `hasRole(...roles)` | `(...string) => boolean` | 大寫比對,`ADMIN` 不自動涵蓋其他角色(以矩陣為準,不做層級推導) |

**掛載行為**:
1. 從 `getProfile()` / `getToken()` 還原;任一為空 → `user = null`。
2. `isExpired(profile)` 為 true → `clearAuth()`,`user = null`。
3. 監聽 `auth:unauthorized` 事件 → `setUser(null)`(儲存已由攔截器清掉)。卸載時移除監聽。

**開發自動登入**:僅當 `import.meta.env.DEV && import.meta.env.VITE_DEV_AUTOLOGIN === 'true'`
且 `VITE_DEV_USERNAME` / `VITE_DEV_PASSWORD` 皆有值時,才**呼叫真實 login 端點**自動登入。
**程式碼內不得有任何預設帳密字面值**;三個環境變數任一缺少即不自動登入。預設狀態為關閉。

**`user.name` 相容**:輪廓提供 `name` 作為 `displayName ?? username` 的衍生值,
讓 `MainLayout.jsx` 既有的 `user.name`(3 處)與 `user.role` 不必大改。

## 8. Edge case 與預期行為

| # | 情境 | 預期行為 |
|---|---|---|
| E1 | 資料庫 Users 表為空、前端已改真登入 | 任何登入皆回 401,前端停在登入畫面並顯示「帳號或密碼錯誤」。**系統不可用,這是預期的**,必須靠 §4.5 部署順序解除 |
| E2 | 使用中權杖滿 2 小時過期 | 下一次 API 呼叫回 401 → 攔截器清權杖 + 派事件 → `AuthContext` 轉 `null` → `MainLayout` 回到登入畫面。**未存檔的表單資料會遺失**,本輪接受此取捨,S6 再評估 refresh token |
| E3 | 後端不可達(容器未起 / 網路斷) | axios 無 `error.response`,**不得**清權杖、不得登出;顯示連線錯誤,使用者重試即可 |
| E4 | 使用者密碼打錯 | 只顯示「帳號或密碼錯誤」,不清除既有權杖、不派發全域登出 |
| E5 | 已登入但權限不足(403) | 保留登入狀態,顯示「權限不足」;**不得**登出或跳登入畫面 |
| E6 | CORS 預檢 `OPTIONS` | CORS 中介軟體在授權之前處理,預檢**不得**被 fallback policy 擋成 401 —— 順序修正後必須實測確認 |
| E7 | 429 限流命中 | 回應帶 CORS 標頭(AC-26),前端能讀到狀態碼並顯示「請稍後再試」,而非不明錯誤 |
| E8 | 多分頁同時開啟 | localStorage 共用,一頁登出後另一頁要到下次 API 呼叫回 401 才會同步登出。**可接受**,不做跨分頁廣播 |
| E9 | 資料庫殘留舊角色字串 `"Admin"` | 簽發時大寫正規化 + migration UPDATE 雙保險,授權仍正確(AC-23) |
| E10 | `Auth:SetupToken` 忘了在初始化後清空 | 端點仍在,但因 Users 表非空一律回 409,無法建立第二個管理者。**仍必須清空**,以免資料庫被清空時遭利用 —— 寫進報告的檢查清單 |
| E11 | ERP 呼叫 `/api/erp/push-orders` | 本輪起回 401。**ERP 推單功能暫時中斷**,必須在報告置頂標示,S6 補 M2M 憑證 |
| E12 | `/api/docs` 需要登入 | 產品 UI 的 `/docs` 頁面在登入後才能讀。這是刻意收緊,不是缺陷 |
| E13 | 舊瀏覽器殘留 `localStorage.currentUser`(含明文密碼) | `clearAuth()` 與 `AuthContext` 掛載時一律移除該鍵,避免舊密碼繼續躺在使用者機器上 |
| E14 | 名冊 `appUsers` 殘留含 `password` 的舊資料 | 讀取時以白名單重建物件並回寫,剝除 `password` 欄位 |
| E15 | migration 未套用就啟動(缺 `DisplayName` 欄位) | `DisplayName` 為可空欄位;若查詢因欄位不存在而失敗,屬部署順序錯誤,由 §4.5 第 3 步規範避免。程式端不做欄位偵測 |
