# S7 規格 — ERP 機器對機器憑證、名冊接後端、403 文案 i18n、權杖刷新

> 2026-09-06 · 分支 `fix/audit-20260903` · 前置為 S5 + S6(commit `9e86cf9`)

## 0. 這一趟要解決什麼

S5 讓後端預設拒絕未驗證請求之後,留下四個缺口(見 `docs/report20260905-2.md` §6)。
本趟一次收掉:

| 代號 | 缺口 | 後果(不修的話) |
|---|---|---|
| **G1** | ERP 是程式呼叫、沒有互動式登入,`/api/erp/push-orders` 卻要求身分 | **ERP 完全推不了單**,排程沒有新工單 |
| **G2** | 設定頁名冊仍寫 localStorage,未接 `/api/v1/auth/users` | 管理者以為建了帳號,實際只動到本機一份清單,現場登不進去 |
| **G3** | `RequireAuth` 的 403 文案硬編碼正體中文 | 越南 / 泰國籍作業員看到看不懂的錯誤 |
| **G4** | 存取權杖 2 小時到期後直接 401 | **未存檔的表單資料遺失**(E2),換班前後最常踩 |

## 1. G1 · ERP 機器對機器憑證

### 1.1 選型

Eric 裁決:**API 金鑰 + 資料庫雜湊保管**。

被否決的兩案與理由:
- *服務帳號走現有登入*:後端幾乎不用改,但把權杖快取、到期重取、401 重試的複雜度外推給客戶的 ERP。
- *設定檔靜態金鑰*:一天內可完成,但無法在不重啟服務的情況下輪替或撤銷,也分不出是哪一支呼叫端。

### 1.2 金鑰格式

```
pio_{prefix}_{secret}
     └12 hex┘ └base64url(32 bytes)┘
```

- `prefix` 明文入庫並建唯一索引 —— 驗證時以它撈出**單一列**再比對雜湊,不做全表逐列雜湊。
  管理介面也用它讓人分辨「現在跑的是哪一支」,不必看到明文。
- `secret` 只以 SHA-256 入庫。金鑰是 256 bit 高熵隨機值,無字典攻擊面,
  故用快雜湊而非 BCrypt —— 每次請求都要驗一次,慢雜湊會直接變成推單端點的瓶頸。
- **明文只在建立當下回傳一次**,後端不留。遺失只能撤銷重發。

### 1.3 資料表 `ApiKeys`

| 欄位 | 說明 |
|---|---|
| `Prefix` | 明文前綴,唯一索引 |
| `KeyHash` | 完整明文的 SHA-256(Base64) |
| `Role` | 目前恆為 `ERP_SERVICE` |
| `IsActive` | 撤銷開關,**撤銷不刪列**(稽核軌跡) |
| `ExpiresAt` | 可空;到期即失效 |
| `LastUsedAt` | 節流寫入(最小間隔 1 分鐘),輪替時判斷舊金鑰能否安全撤銷 |
| `CreatedBy` | 建立者帳號 |

### 1.4 授權模型

- 新增驗證方案 `ApiKey`(讀 `X-Api-Key` 標頭),**不是預設方案**。
- 新增 policy `ErpPush`:方案清單 = `ApiKey` + `Bearer`,角色 = `ERP_SERVICE` 或 `ADMIN`。
- `ErpController` 由裸 `[Authorize]` 改掛 `ErpPush`。
- 其餘端點的 fallback policy 仍只認 `Bearer` → **一支外洩的金鑰打不開整個系統**。
- 允許 `ADMIN` 是刻意的:授權矩陣 AC-02 要求 ADMIN 權杖在每個端點都不得被擋,
  現場也需要有人能在 ERP 掛掉時手動補一批單。

### 1.5 管理端點

`/api/v1/apikeys`,全數限 ADMIN 且**只接受 JWT** —— 不讓一支金鑰拿自己去產生下一支,
否則外洩後無法靠撤銷收斂。

| 方法 | 路徑 | 說明 |
|---|---|---|
| GET | `/api/v1/apikeys` | 列出全部(含已撤銷),絕不回傳明文或雜湊 |
| POST | `/api/v1/apikeys` | 建立,**回應是唯一一次拿到明文的機會** |
| POST | `/api/v1/apikeys/{id}/revoke` | 撤銷(冪等) |

### 1.6 驗收準則

AC-S7-01 ~ 06(金鑰產生器單元)、AC-S7-10 ~ 26(端到端)。重點:
有效金鑰推得了單且真的寫入;撤銷 / 到期 / 竄改 / 偽造一律 401;
**金鑰不是萬用鑰匙**(推單以外的端點一律 401);非 ERP_SERVICE 角色的金鑰 403;
ADMIN 的 JWT 仍推得了單;OPERATOR 的 JWT 403;列表不得洩漏明文或雜湊。

## 2. G2 · 使用者名冊接後端

### 2.1 事實來源分界

| 誰 | 讀哪裡 | 為什麼 |
|---|---|---|
| 設定頁 `GeneralTab` | **後端** `/api/v1/auth/users` | 管理者要維護的是真帳號 |
| 登入視窗 `LoginModal` | **本機快取** `localStorage.appUsers` | 登入視窗面對的是**未登入**的人,呼叫不了 ADMIN 端點 |

快取由設定頁在每次成功載入後改寫。這是刻意的形狀:名冊的事實來源是後端,
快取只服務「觸控便利清單」與「斷網時看得到清單」兩件事。
**已停用的帳號不進快取** —— 登不進去的帳號留在清單上,點了只會拿到「帳號或密碼錯誤」。

### 2.2 行為變更

- 新增使用者**密碼必填**(後端沒有密碼建不了帳號);編輯時密碼**留空 = 不變更**。
- 帳號(代碼)建立後不可修改 —— 後端沒有改帳號的端點。
- 角色改為下拉選單(OPERATOR / SUPERVISOR / ENGINEER / ADMIN)。
- **「刪除」語意改為「停用」**:後端沒有刪除端點,帳號要留稽核軌跡。
  停用最後一位啟用中的 ADMIN 會被後端擋下(409),顯示後端訊息。
- 三種降級狀態都必須說出來:載入中 / 非 ADMIN 唯讀(403)/ 後端不可達(顯示快取)。
  **失敗時絕不清空畫面**。

### 2.3 安全不變量

密碼**絕不落地**:任何一行只要碰 `localStorage` 就不得同時碰密碼;
名冊快取的白名單投影(`toRosterCache`)不得有 password 欄位。
S5 原本的判準「GeneralTab 不得出現 `password:`」自本趟起不成立(必須把密碼送去後端),
已由上述兩條更精確的判準取代。

## 3. G3 · 403 文案 i18n

新增 `authGuard` 語系群組(五語系齊補,否則 `localeParity` 會紅):
`forbidden` / `forbiddenHint` / `backHome` / `sessionExpired`。

狀態碼「403」本身**刻意不進語系檔** —— 它是 HTTP 標準碼不是文案,
翻譯它只會讓現場回報問題時說不出同一個號碼。

## 4. G4 · 權杖刷新

### 4.1 機制

登入回應新增 `refreshToken` 與 `refreshTokenExpiresAt`(additive,舊呼叫端不受影響)。
存取權杖仍 2 小時;刷新憑證預設 12 小時(`Auth:RefreshTokenHours`),涵蓋一個班。

- 只存 SHA-256 雜湊,明文只在登入 / 刷新的回應出現一次。
- **一次性 + 輪替**:每次換發都作廢舊憑證並發新的。
- **重用偵測**:已作廢的憑證再度出現 = 它被複製過(正常客戶端不會重送已換過的憑證),
  此時作廢該使用者**全部**憑證,逼真正的持有者重新登入。
- 帳號被停用時立即作廢其憑證;換發端點也會再檢查一次 `IsActive`。

| 方法 | 路徑 | 驗證 | 說明 |
|---|---|---|---|
| POST | `/api/v1/auth/refresh` | 匿名 + 限流 | 憑證本身即身分;存取權杖已過期的客戶端必須換得到 |
| POST | `/api/v1/auth/logout` | 匿名 + 限流 | 作廢憑證,一律回 204(不洩漏憑證是否存在) |

### 4.2 前端

401(非登入 / 非刷新 / 非登出端點)→ 換發 → **重送原請求**。

- 每個原始請求只重試一次,避免換發成功但後端仍 401 時無限重送。
- **同時只允許一次換發**:多個請求同時撞到 401 會共用同一個 promise,
  否則各自拿同一張憑證去換,第二個之後會踩到後端重用偵測而把整串作廢。
- 換發成功時三個儲存值一起更新:存取權杖、刷新憑證、輪廓的 `expiresAt`。
- 換不到就登出,事件只派發一次。
- 登出:**本機清除不等後端回應** —— 斷網時仍必須登得出去。

### 4.3 已知殘留

存取權杖是無狀態 JWT,**無法撤銷**:登出或停用之後,已發出的存取權杖最長仍有 2 小時殘命。
要收掉需要黑名單或改用不透明權杖,不在本趟範圍。
