# report20260907-3 · S11 完工送出重試(堵住 pending 的源頭)

> 2026-09-07 · 承 `docs/report20260907-2.md` §6 第 1 項

## 1. 為什麼要做

S10 做的是**事後對帳** —— 報表頁掃描本機殘留的 pending 實績再補送。
但源頭一直開著:`Dashboard.jsx` 的完工 POST **只送一次**,失敗的 `.catch` 裡只有
`console.warn` 加一行操作記錄,那筆就永遠停在 `pending`,等人去報表頁按回填。

一次網路抖動、一次 502、一次撞限流、一次權杖剛好過期,都足以產生一筆。
S5/S6 開了認證之後第四種尤其常見。所以 pending 不是歷史包袱,是**持續在長的**。

## 2. 改了什麼

新增 `frontend/src/utils/completionRetry.js`(純決策 + 可注入相依的送出迴圈):

| 匯出 | 職責 |
|---|---|
| `classifyFailure(err)` | 這個失敗重試有沒有機會變好 |
| `nextDelayMs(err, attempt)` | 這次要等多久 |
| `sendCompletionWithRetry(payload, deps)` | 送出並依上述兩者重試,**絕不 reject** |

**重試判準**(判準本身就是這次的交付,不是實作細節):

- 沒有 response(斷網 / DNS / 逾時)→ 重試
- 429 / 408 / 5xx → 重試,是對方的暫時狀態
- **401 → 重試**。api 攔截器已經試過換發權杖,走到這裡表示換發也失敗;
  但作業員可能正在另一個分頁重新登入,慢一點再送有機會成功
- **其他 4xx(400 / 403 / 409)→ 不重試**。重送一模一樣的內容只會得到一模一樣的拒絕,
  徒然拖慢換單

退避階梯 2s → 8s → 30s(合計約 40 秒內收斂)。429 改以伺服器的 `Retry-After` 為準,
但夾在 60 秒上限內 —— 一筆不得卡死整條路徑;階梯用完時即使是 429 也不再等。

`Dashboard.jsx` 的完工路徑改用它:**全程不 await**,重試在背景進行,
現場的換單與計時歸零一秒都不等它;元件卸載(換頁 / 登出)就停止重試。
重試次數會寫進畫面的操作記錄(`Completion sync retry #2 in 8s (rateLimited)`),
成功時若重試過會標明 `(after N attempts)` —— **不靜默**。

## 3. 為什麼重試是安全的

**前提是冪等**:後端以 `clientRecordId` 去重,同鍵重送回 `duplicated: true`
且資料庫不長第二筆。所以「送出去了但回應沒收到」這種最危險的情境,重送不會產生兩筆實績。

**沒有這個前提就不該重試** —— 已寫進模組檔頭,改動時先確認它還在。
測試也直接釘住:三次重送的 `clientRecordId` 必須是同一個。

## 4. 順帶查清:`JWT_SECRET` 不必輪替

handoff 從上線那天起就掛著「不確定 `.env` 裡那組是不是新產的」。實查結果:

- 現值 64 字元,`git log --all -p | grep -F` **在版控任何歷史裡都找不到** → 是新產生的
- 曾經進過版控的那組是 `YourSuperSecretKeyThatIsAtLeast32CharactersLong!`(範本預設值),
  與現值長相完全不同
- `docker inspect printingiot-backend-api-1` 的 `Jwt__Secret` 與 `.env` **逐字元相同**,
  執行中的 API 用的就是這一組

→ **不需要輪替,也就不需要挑時間讓所有人重新登入。**
