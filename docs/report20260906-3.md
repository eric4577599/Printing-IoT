## 0. 一句話

後端補了三支彙總端點、前端三個檢視改讀它們;但**這一趟真正的收穫是黃金向量抓到了一個已經存在的漂移** ——
同一組資料,後端稼動率算出 66.7,前端算出 66.6。

---

## 1. 問題是什麼

`OeeCalculator.cs`(C#)與 `reportUtils.js`(JS)是同一組 OEE 公式的兩份實作。
`OeeCalculator` 的類別註解已經明寫「前端 `calculateOEE` 必須依同一份規則表實作」——
**那句話本身就是風險的自白**:兩邊靠人記得同步,沒有任何機制強制。
兩邊各自對著自己手寫的期望值測,任一邊被改動,另一邊的測試不會有反應。

而彙總又更糟:後端根本沒有彙總端點,「當日加權平均 OEE」「當月每日一列」「停機原因排行」
只能在瀏覽器裡算 —— 後端連參與的機會都沒有。

## 2. 做了什麼

### 2.1 三支彙總端點

| 端點 | 回傳 |
|---|---|
| `GET /api/production/summary/daily` | 日報彙總物件(欄位名對齊前端 `calculateDailySummary`) |
| `GET /api/production/summary/monthly` | `{ dailyRows, totals }`,每日一列 + 整月總計 |
| `GET /api/production/summary/stop-reasons` | 停機原因陣列,依次數遞減 |

三支共用 `from` / `to`(工廠日,含端點)與 `shift`(不分大小寫)。三條設計紀律:

- **算術全部委由 `OeeCalculator`**,服務層不自己寫任何一行率值公式 —— 否則就成了第三份實作。
  為此把 `Round1` 開放為 public,並補上 `Utilization` / `YieldRate` / `AchievementRate` 三個彙總用的函式。
- **不分頁,但不靜默截斷**。區間內完工列超過 `Production:SummaryMaxRows`(預設 20000)時回 **400**
  並說明請縮小區間,不回部分結果(沿用 S4 的紀律)。
- **停機原因不回下鑽明細**。展開列要的「哪幾張單」是逐筆資料,回應大小會隨區間內訂單數無上限成長;
  前端改為彙總看這支、展開時從既有的逐筆清單篩。

率值口徑對齊前端既有語意,不是重新發明:良率與達成率以**區間總量**重算(不是逐筆率值的平均),
`avgOEE` 依**產量加權**(規則 6),月報每一列與總計都拿**該層級的彙總數據重算 OEE**(S3 GAP-05 的裁決)。

### 2.2 黃金向量:讓漂移不可能再發生

新增 `tests/fixtures/oee-golden-vectors.json`,14 組輸入與期望值。
**C# 與 JS 讀的是同一個檔** —— C# 是權威實作(期望值由它背書),JS 只需證明自己算得出同樣的數字。
任一邊改了公式而沒改另一邊,該邊立刻紅。

向量涵蓋:分母為零(三處各一)、超產封頂、負值夾零、負荷時間夾到 0、`min` 夾住上限,
以及**三個 x.x5 的四捨五入邊界**(良率 88.85、稼動率 66.65、效能 33.35)。

## 3. 抓到的東西

### 3.1 稼動率 66.65:後端 66.7、前端 66.6(**已存在的真漂移**)

黃金向量一上線就有一筆紅的:

```
AssertionError: expected 66.6 to be 66.7
```

根因是**運算順序**,不是四捨五入寫法:

| | 算式 | 結果 |
|---|---|---|
| 後端 C# | `(decimal)6665 / 10000 * 100m` | decimal 精確,得 `66.65` → AwayFromZero → **66.7** |
| 前端 JS | `(6665 / 10000) * 100` | 先除掉了精度,實際是 `66.649999999999991` → **66.6** |

`6665 / 10000` 在二進位浮點下是 `0.66649999999999998…`,再乘 100 就落在真值下方。
這個 double 與 `66.65` 的 double 是**不同的兩個數**,資訊在第一次除法就丟了,
之後怎麼四捨五入都救不回來。

修法:新增 `percent(numerator, denominator)` 統一成 **先乘 100 再除**,只留一次(正確捨入的)除法,
結果就是最接近真值的那個 double。`calculateOEE` 的三因子、`calculateUtilization`、
`calculateYieldRate`、`calculateAchievementRate` 全部改走它。

這條由「稼動率原始值剛好 66.65」那筆向量釘住 —— 換回先除後乘,立刻轉紅。

**這不是本輪寫壞的東西,是本輪照出來的。** 在黃金向量存在之前,
這個分岔已經在正式程式碼裡,而且兩邊的測試都是綠的。

### 3.2 順手加的巧思,查證後拿掉了

發現 3.1 的當下,我先改的是 `round1`,用十進位字串移位(`Number(\`${n}e1\`)`)繞開浮點誤差。
它讓測試變綠了,但那是誤打誤撞 —— 真正的根因在上游的運算順序。

改對順序之後,回頭掃了兩條路徑(x.x5 邊界的所有整數分子分母組合、以及 OEE 三因子相乘那條),
**沒有任何一個案例需要那個字串技巧**。既然沒有測試涵蓋得到它,它就是沒被驗證的複雜度,
於是把 `round1` 收回最單純的 `Math.round(value * 10) / 10`,只在註解裡留下查證結論。

### 3.3 `MonthlyReportView` 會被非預期的回應形狀炸掉

接上端點後,既有測試冒出 `TypeError: Cannot read properties of undefined (reading 'length')`。
原因是我直接解構 `const { dailyRows, totals } = backendSummary` ——
回應一旦不是預期形狀(改版、走錯端點、代理插手),`dailyRows` 就是 `undefined`,
下一行的 `.length` 把整個報表頁炸成白畫面。

三個檢視都補上形狀守衛,不符就退回前端計算 —— 數字略有落差遠好過白畫面。
同時讓畫面上的來源標示跟著守衛走:被擋下來時不可以還說「數字來自後端」,那是騙人的。

### 3.4 `AC-S4-06` 的判準與意圖分岔了(**換掉,不是放寬**)

既有測試 `AC-S4-06:班別變更不觸發新的 API 請求` 在本輪轉紅:
彙總端點自 S8 起由後端做班別過濾,**換班別本來就應該重打彙總**。

這條測試真正要守的不變量是「不要為了換個班別,就把整個區間的逐筆紀錄重抓一次」。
所以改成只數 `/production/completions` 的呼叫次數,而不是把斷言放寬成「總數 ≥ 之前」那種不會失敗的東西。
判準換掉了,守住的東西沒有變少 → `[[test-assertions-must-match-real-invariants]]`

## 4. 明確沒做:`reportUtils` 的彙總函式不退場

規格 §4,這是本輪最重要的取捨,不可略過。

S4 的現況是「後端紀錄 + localStorage 僅存本機的舊單」合併呈現。
後端彙總**只看得到後端的資料** —— 對還有本機舊單的瀏覽器,若直接改讀後端彙總,
那些單會從彙總數字裡消失,但逐筆明細裡還看得到。**數字與明細互相矛盾,比數字略有漂移更糟。**

所以切換帶了一個條件:

> 區間內 `localOnlyCount > 0` 時**不採用後端彙總**(連請求都不發),改用前端計算並在畫面標示原因;
> `localOnlyCount === 0` 時才採用後端彙總,並標示資料來源為後端。

handoff 第 9 項(舊實績回填後端)完成之後,這個分支才能拆掉,前端公式也才真的能退場。
**但漂移風險不必等到那時候** —— §2 的黃金向量已經把它關掉了。

## 7. 已知限制與留給下一趟

1. **前端公式仍在**(§4)。要真的退場,得先做 handoff 第 9 項的舊實績回填。
2. ~~**彙總端點未經真實 PostgreSQL 驗證**~~ ✅ 2026-09-06 21:20 已對真實 PostgreSQL 15 驗過
   (`docs/report20260906-4.md` E 段):三支端點皆回 200,`Shift.ToUpper()` 在 Npgsql 翻譯正常。
   **仍成立的部分**:非 ASCII 班別的大小寫對映在 PostgreSQL 與 .NET 之間可能不同,
   現場班別是 `A` / `B` / `C` 不受影響,日後若開放自訂班別名稱要重新確認。
3. **彙總沒有快取**。目前沒有證據顯示查詢慢,先做對再做快;
   真的變慢時最先該看的是 `ProductionDate` 上有沒有索引。
4. **`localOnlyCount > 0` 時完全不用後端彙總**,即使該區間絕大多數資料都在後端。
   這是刻意保守 —— 混合兩個來源的彙總比單一來源更難解釋。
5. **`AvgSpeed` 的月報欄位取算術平均**,沿用前端既有語意(未依產量加權)。
   與 OEE 的加權處理不一致,但改動它會改變既有報表數字,不在本輪範圍。
