## ⛔ 先看這段:文件寫的順序照做會出事

`docs/report20260905-2.md` §2 把「套用 migration」寫成第 3 步、把「重啟 API」寫成第 2 步。
**這個順序在這個專案上不成立**,因為:

> `backend/PrintingIoT.API/Program.cs:159` 在啟動時呼叫 `MigrateWithRetryAsync<PrintingContext>()`。
> **migration 不是一個由人挑時機的步驟,而是「API 一啟動就發生」。**

所以照字面做的話,第 2 步的重啟就已經把八個 migration 全部套下去了 ——
**第 3 步那段「不可略過」的重複帳號檢查,會在事情發生完之後才跑到**。

而且 `MigrateWithRetryAsync` 的 catch 攔的是 `Exception`,不分連線失敗還是唯一索引建失敗,
所以真的撞到重複帳號時,它會**把同一個必然失敗的 migration 重試 10 次**(約 20 秒)才擲出,
容器接著因為 `restart: always` 進入無限重啟。現場看到的是「API 一直起不來」,
而不是「有兩個帳號大小寫撞在一起」。

**修正後的順序寫在下面 §2**:所有 DBA 前置檢查都移到「拉起新版容器之前」,
在**舊的 / 只有 postgres 的**堆疊上跑完。`scripts/preflight-check.sh` 就是為了這件事寫的。

## 1. 整備時發現的落差

### 1.1 `Auth__SetupToken` 根本沒接進 docker-compose(阻斷,已修)

`docs/report20260905-2.md` §2 第 2 步要求「以 `Auth__SetupToken` 注入一組一次性隨機字串」,
但 `docker-compose.yml` 的 `backend-api` 服務只有 `Jwt__Secret` 一個認證相關環境變數,
**沒有任何地方會把 `AUTH_SETUP_TOKEN` 傳進容器**。照文件做的人會發現這一步做不到,
只能自己改 compose —— 而那是上線當下最不該即興發揮的地方。

已修(本輪):

| 檔案 | 變更 |
|---|---|
| `docker-compose.yml` | `backend-api` 加 `Auth__SetupToken=${AUTH_SETUP_TOKEN:-}` 與 `Auth__RefreshTokenHours=${AUTH_REFRESH_TOKEN_HOURS:-12}` |
| `.env.example` | 新增 `AUTH_SETUP_TOKEN=`(留空 = 端點關閉)與 `AUTH_REFRESH_TOKEN_HOURS=12`,含用途說明 |

**預設值刻意是空字串** —— 空 = `setup-admin` 回 404 = 端點關閉,這是平常該有的狀態。
只有建立第一個 ADMIN 那幾分鐘才填值。

### 1.2 待套用的 migration 是 **8 個**,不是 handoff 寫的 7 個

以 `feat/extract-maintenance@3487288`(稽核分支開出的基底)為界對照,稽核這條線新增的是:

| 2 | `20260904000000_AddProductionLogSource` | 無 |
| 3 | `20260904010000_AddProductionCompletion` | 無 |

### 1.3 限流會把整個廠共用一個桶(**非阻斷,但上線後要盯**)

限流的分區鍵是 `httpContext.Connection.RemoteIpAddress`(`Program.cs:107`、`Program.cs:122`),
由 `UseForwardedHeaders` 依 `ForwardedHeaders:ForwardLimit`(預設 **1**)改寫。兩條路徑結果不同:

| 路徑 | backend 看到的 `X-Forwarded-For` | 取最右 1 筆的結果 | 影響 |
|---|---|---|---|
| 廠內直連 `:5600` | `<瀏覽器 IP>` | 瀏覽器 IP ✅ | 每台終端各自一個桶,正確 |
| 走 Cloudflare Tunnel | `<真實 IP>, <cloudflared 容器 IP>` | **cloudflared 容器 IP** ⚠️ | **所有遠端使用者共用一個桶** |

共用桶的額度是全域 100 次/分、登入端點 10 次/分。現場終端幾乎都是廠內直連,不受影響;
**受影響的是遠端存取**(Eric / 管理端),一個人開著儀表板就可能自己把自己打到 429。

**這輪刻意不改**,因為它不是一行設定就能解的:

- 改 `ForwardLimit=2` 可以修好 Tunnel 這條路 —— 但 `KnownNetworks` / `KnownProxies` 已被清空
  (`Program.cs:36-37`),廠內直連的人只要自己送一個 `X-Forwarded-For: 1.2.3.4`,
  nginx 會接成兩筆,取第 2 筆就是他自己挑的值 —— **等於可以任意換桶,登入限流形同虛設**。
- 現行的 `ForwardLimit=1` 是防偽的(最右一筆永遠由 nginx 自己補上,偽造不了),代價就是 Tunnel 那條路失準。
- 要兩邊都對,得讓 nginx 依來源決定是否採信既有 XFF(或改採 `CF-Connecting-IP`),那是設計決定,不是上線動作。

**上線建議**:維持現狀,上線後觀察遠端存取是否出現 429;真的礙事再處理。診斷指令見 §5。

### 1.4 其他非阻斷觀察

- **`ASPNETCORE_ENVIRONMENT=Development`**(`docker-compose.yml`)會讓 `/swagger` 對外開著
  (`Program.cs:174`)。所有端點都已 `[Authorize]`,Swagger UI 本身讀得到但打不動,
  屬既有狀態,這輪不動 —— 但值得列為上線後的收斂項。
- **前端 `VITE_API_URL` 是死設定**。`frontend/Dockerfile` 在 build 階段就 `npm run build`,
  Vite 的 `import.meta.env` 在那時定案;compose 裡那行 `environment` 是給 runtime 的 nginx 容器,
  對已經 build 好的 bundle 沒有作用。實際生效的是 `API_URL = ''` → `baseURL = '/api'` → 走 nginx 反向代理,
  **行為正確**,只是那行設定會誤導人。
- **走 nginx 代理時 CORS 根本不參與**(同源),`Cors:AllowedOrigins` 只在 `npm run dev` 直連 :5200 時才有意義。

## 2. 上線 runbook(可直接照貼)

> 全程在部署主機執行,`cd` 到專案根。
> **在 C 段完成之前,現場完全無法操作系統** —— 這是刻意的,不是缺陷。

### A 段 · 前置(在拉起新版 API **之前**做完)

```bash
# A1. 取得這次要上的程式碼
git fetch origin && git checkout main && git pull --ff-only

# A2. 準備 .env(第一次才需要 cp)
[ -f .env ] || cp .env.example .env

# A3. 產生全新的 JWT 簽章密鑰,寫進 .env 的 JWT_SECRET
#     舊密鑰 DevOnlyLocalSecretKeyAtLeast32CharsLong! 已在版控歷史中,視同已外洩(R4)
openssl rand -base64 48

# A4. 只把資料庫拉起來(不動 API,因此不會觸發 migration)
docker compose up -d postgres

# A5. 備份 —— 在任何 migration 跑之前
docker compose exec -T postgres pg_dump -U "${POSTGRES_USER:-postgres}" -d FlexoDB \
  > "backup-FlexoDB-$(date +%Y%m%d-%H%M).sql"

# A6. 前置檢查(唯讀,不改任何東西)。exit 0 才可以往下走
./scripts/preflight-check.sh
```

`preflight-check.sh` 會查:`.env` 的必填值、`__EFMigrationsHistory` 與 repo 的落差、
**兩個唯一索引的重複資料**、以及 `Users` 現況(決定要不要走 setup-admin)。
有任何阻斷項它會 `exit 1` 並列出處置方式 —— **沒過就不要往 B 段走**。

### B 段 · 拉起新版(這一步會自動套用 migration)

```bash
# B1. macOS 產生的 dot-underscore 檔會弄壞 dotnet build
find . -name "._*" -delete

# B2. 建置並拉起全部服務。前端一定要重建,compose 掛的是原始碼、服務的是 build 產物
docker compose up -d --build

# B3. 盯 API 啟動記錄,確認 migration 全部套用成功
docker compose logs -f backend-api
#     要看到:"PrintingContext migrated successfully."
#     若反覆出現 "connection failed ... Retrying",先停下來看錯誤內容,不要放著讓它重試 10 次
```

### C 段 · 建立帳號(**做完之前現場登不進來**)

```bash
# C1. 產生一次性初始化權杖,填進 .env 的 AUTH_SETUP_TOKEN,重啟 API 讓它生效
openssl rand -hex 32
#     編輯 .env → AUTH_SETUP_TOKEN=<剛才那串>
docker compose up -d backend-api

# C2. 建立第一個 ADMIN(密碼至少 12 字元且須含字母與數字)
curl -s -X POST http://localhost:5200/api/v1/auth/setup-admin \
  -H 'Content-Type: application/json' \
  -d '{"setupToken":"<剛才那串>","username":"admin","password":"<強密碼>","displayName":"系統管理者"}'

# C3. 以該 ADMIN 登入取得權杖
TOKEN=$(curl -s -X POST http://localhost:5200/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<強密碼>"}' | jq -r .token)
echo "${TOKEN:0:20}..."   # 非空即成功

# C4. 逐一建立現場帳號(至少涵蓋目前在用的 OP1~OP5),shift 填 A / B / C
for op in OP1 OP2 OP3 OP4 OP5; do
  curl -s -X POST http://localhost:5200/api/v1/auth/users \
    -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d "{\"username\":\"$op\",\"password\":\"<該帳號的密碼>\",\"role\":\"OPERATOR\",\"displayName\":\"$op\",\"shift\":\"A\"}"
  echo " <- $op"
done

# C5. 確認名冊
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:5200/api/v1/auth/users | jq -r '.[] | "\(.username)\t\(.isActive)"'
```

帳號**不分大小寫**(`OP1` / `op1` / `Op1` 都登得進去,前後空白會被 Trim),**密碼永遠精確比對**。

### D 段 · 收尾

```bash
# D1. 清空 AUTH_SETUP_TOKEN 並重啟,讓 setup-admin 回歸 404
#     編輯 .env → AUTH_SETUP_TOKEN=
docker compose up -d backend-api

# D2. 確認端點真的關了(要看到 404)
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:5200/api/v1/auth/setup-admin \
  -H 'Content-Type: application/json' -d '{"setupToken":"x","username":"x","password":"x"}'

# D3. 未帶權杖的請求要被擋(要看到 401)
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:5200/api/orders
```

### E 段 · 實機驗收(對照 handoff Next Step 5)

| # | 走法 | 要看到什麼 |
|---|---|---|
| E1 | 完工一張單 → **整頁重載** | 完工單**不會復活**,順序與狀態正確(S1) |
| E2 | 以 `op1`(小寫)登入 | 成功;狀態列顯示 `Operator: … (Shift: A) (OPERATOR)`,**班別不得為空** |
| E3 | 登入後開著 **超過 2 小時** | 自動換發權杖,**不被踢出去**(S7 G4)。既有階段沒有刷新憑證,首次仍會被登出一次,再登入起才有 |
| E4 | ADMIN 建帳號 → 該帳號登入 → 在設定頁停用 → 再登入 | 停用後**立刻登不進去**(S7 G2) |
| E5 | 登入後開 `/docs` | 文件正常顯示(不是 401) |
| E6 | 未登入直接開 `/debug` | 被擋下 |

**E3 的已知缺口**:JWT 是無狀態的,停用或登出後**已發出**的存取權杖最長仍有 2 小時殘命
(handoff Next Step 11)。E4 驗的是「不能再登入」與「換不到新權杖」,不是「舊權杖立刻失效」。

## 3. 出事了怎麼回去

| 情況 | 處置 |
|---|---|
| API 起不來、記錄顯示 migration 失敗 | migration 本身是交易式的,失敗會回滾。**不要反覆重啟** —— 先讀錯誤,九成是 §1.2 表格裡那兩個唯一索引的重複資料。修完資料重跑 `preflight-check.sh` |
| 已套用但要退回舊版程式碼 | migration 有 `Down`,但**退版會遺失新表的資料**(`ApiKeys` / `RefreshTokens` / `ProductionCompletions` / `ReasonCodes`)。優先用 A5 的 `pg_dump` 還原,而不是跑 `Down` |
| 現場登不進去、來不及查 | 現場作業員可**手動輸入正確帳號**登入,不需等管理者(名冊快取只影響觸控清單,帳號本身在後端) |
| 完全回不去 | `docker compose down` → 還原 A5 的備份 → `git checkout <舊 commit>` → `docker compose up -d --build` |
