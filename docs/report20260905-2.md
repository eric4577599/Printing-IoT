### 1.3 S6 收尾(登入帳號大小寫定案 + CORS 預檢驗收出口)

規格 `docs/spec20260905-s6-v1.md`。S5 的程式**沒有回退**,S6 補的是兩個會咬人的缺口。

#### (1) 登入帳號自本版起「不分大小寫」,密碼仍然精確比對

S5 的建立端(`POST /api/v1/auth/users`)本來就是不分大小寫唯一,登入端卻是精確比對。
結果是:管理者建 `OP1`、現場作業員在觸控終端打 `op1` 會拿到 `401`,而畫面只寫「帳號或密碼錯誤」,
**現場停線且沒有人猜得到原因**。本版把登入端對齊建立端:

- 正規化定義只有一份:`Normalize(s) = (s ?? "").Trim().ToUpperInvariant()`
  (`backend/PrintingIoT.Core/Constants/AppUsernames.cs`,大寫慣例與既有 `AppRoles.Normalize` 一致)。
- **`OP1` / `op1` / `Op1` / `oP1` 都能登入**;前後空白也會被 Trim,`" op1 "` 可登入
  (觸控鍵盤與條碼槍常帶空白)。
- **密碼永遠精確比對**,不因帳號正規化而放寬 —— AC-50 專門釘住這點。
- **帳號的顯示形態原樣保留**:資料庫存的是 `OP1`,使用者清單與登入回應回的也是 `OP1`,
  不會被轉成小寫。稽核與名冊的既有命名慣例不受影響。
- 作法:`Users` 新增 `UsernameNormalized` 欄位(varchar(50), NOT NULL)並在其上建唯一索引;
  值由 `User.Username` 的 setter 自動同步,**任何寫入路徑(controller / seed / 測試)都不可能漏設**。
  登入查詢與重複檢查一律比對這個欄位,不再把全表帳號載入記憶體比對。
- 併發同時建立 `OP1` 與 `op1` 時,由資料庫唯一索引擋下,`DbUpdateException` 轉為 `409 Conflict`。
  **誠實標註**:EF Core InMemory 不強制唯一索引,這條分支沒有自動化出口,靠模型層索引斷言(AC-53)
  加程式碼審查把關。

#### (2) 套用 migration 前的重複帳號檢查(部署前置,已寫入 §2 第 3 步)

見 §2 部署順序第 3 步。**這是本版唯一新增的部署前置條件**,回傳非空就不可套用 migration。

#### (3) 新增 migration:`20260905010000_AddUsernameNormalizedUniqueIndex`

`backend/PrintingIoT.Infrastructure/Migrations/20260905010000_AddUsernameNormalizedUniqueIndex.cs`
(+ `.Designer.cs`,並更新 `PrintingContextModelSnapshot.cs`),排在 S5 的 `20260905000000_...` 之後。

Up 的四步順序不可調換:新增可為 null 的欄位 → `UPDATE "Users" SET "UsernameNormalized" = UPPER(TRIM("Username"))`
回填既有列 → 改為 NOT NULL → 建唯一索引 `IX_Users_UsernameNormalized`。Down 為 `DropIndex` → `DropColumn`。
既有的 `Username` 唯一索引全程不動(較寬鬆、冗餘但無害)。

**本機無法套用**(同 R5):這台機器沒有 Docker、不連真實 PostgreSQL,migration 只做到產生與編譯,
**未經實際 apply 驗證**,須由部署者在有資料庫的環境執行,首次套用前先備份。
`PrintingIoT.Tests` 走 EF Core InMemory、不經 migration,因此測試全綠**不代表** migration 已驗證。

正常情況下既有帳號完全不受影響,大小寫原樣保留,只是多一欄正規化值;唯一會失敗的情況就是 (2) 的重複帳號。

#### (4) CORS 預檢已補上自動化驗收(AC-57 / AC-58)

S5 §8 E6 自己寫明「順序修正後必須實測確認」,但當時 §7 沒有對應 AC,整個測試專案零個 OPTIONS 預檢斷言。
本版補上兩條測試於 `backend/PrintingIoT.Tests/Integration/RateLimitAndCorsTests.cs`:

- **AC-57**:`OPTIONS /api/orders` 帶 `Origin: http://localhost:5600` 與 `Access-Control-Request-Method: POST`、
  **不帶任何權杖** → 不得為 `401`、必須 2xx,且回應帶 `Access-Control-Allow-Origin` 等於該來源。
- **AC-58**:同一請求改帶 `Origin: http://evil.example.com` → 回應**不得**帶 `Access-Control-Allow-Origin`
  (證明沒有人為了讓預檢通過而偷改成 `AllowAnyOrigin`)。

兩條實測皆通過。**誠實說明**:S5 的中介軟體順序本來就正確(`UseCors` 在限流與驗證 / 授權之前),
依 ASP.NET Core 行為預檢極可能一直是好的 —— 這裡補的是**契約缺口與回歸保護,不是修一個已證實的缺陷**,
不應被讀成「S5 的 CORS 壞掉過」。

排錯提示:若正式環境仍出現預檢失敗,先確認 Cloudflare Tunnel / 反向代理是否轉發 `OPTIONS`
—— 那超出應用程式範圍,不在上述 AC 的涵蓋內(E23)。

#### (5) 文件精確度更正:`setup-admin` 無 body 時回 `400` 而非 `404`

S5 規格 §4.1 表格寫「`Auth:SetupToken` 未設定 → 404」,那句隱含「請求帶了合法 body」的前提。
`POST /api/v1/auth/setup-admin` **完全沒有 body** 時,會先被 `[ApiController]` 的模型繫結擋成 **`400`**。
兩者不衝突(無 body 時與 SetupToken 是否設定無關,不洩漏端點存在性),**行為本身正確**,
AC-20 已釘住。這是文件精確度更正,**未改任何程式碼**。

#### (6) 前端名冊 `username` 修正(**兩個寫入點,本版都已修正**)

`localStorage.appUsers` 這份名冊有**兩個**元件會寫入,兩處都會造成同一個失效模式,本版一併修正:

| 寫入點 | 原本的問題 | 本版修正 |
|---|---|---|
| `frontend/src/modules/auth/LoginModal.jsx` | 新增名冊列時 `username` 存成顯示名稱 | 改存**後端帳號(代碼)**如 `OP1`;載入舊資料時缺 `username` 的列以 **id(代碼)**遞補,不再用顯示名稱 |
| `frontend/src/components/settings/GeneralTab.jsx` | 同上,設定頁「使用者名冊」新增列時也把顯示名稱當帳號 | 同上;遞補鏈改為 `username → id → name` |

失效模式:管理者建立「代碼 `OP1` / 操作員 王小明」若寫出 `username: '王小明'`,
作業員在登入畫面點該列會填入「王小明」送出 → 後端查無此帳號 → `401`,
畫面只顯示「帳號或密碼錯誤」。這正是本輪要消滅的「現場鎖門」失效模式,只是從管理者這條路徑進來。

舊名冊列若已被寫壞,三條修正途徑:

1. 作業員**手動輸入正確帳號**登入(不需管理者介入,最即時)。
2. 升級到本版後,在**登入視窗的管理者子面板**重新儲存該列。
3. 升級到本版後,在**設定 → 一般 → 使用者名冊**重新儲存該列。

⚠️ **第 2、3 條都必須先升級到本版**。本版之前在設定頁重新儲存,只會**再一次**寫入顯示名稱,
不但沒修好還會覆蓋掉手動改對的值。先前版本的交付說明把「重新儲存即修正」寫成通用解法,那是錯的。

**不做自動遷移** —— 無法可靠分辨「顯示名稱剛好等於帳號」與「寫壞的資料」(E20)。
名冊仍然不含 `password` 欄位(AC-61 回歸釘住)。
驗收:AC-59 ~ AC-61(登入視窗)、AC-66 ~ AC-68(設定頁)。

## 2. 部署者操作順序(規格 §4.5,原樣照抄)

> **在第 5 步完成之前,現場完全無法操作系統。** 這是刻意的,不是缺陷。

1. 產生**新的** JWT 簽章密鑰,以 `Jwt__Secret` 環境變數注入(舊密鑰已外洩,見 §12 R4)。
2. 以 `Auth__SetupToken` 注入一組一次性隨機字串,重啟 API。
3. 套用 migration(§9)。**套用之前必須先跑下面這段重複帳號檢查**(S6 新增,不可略過):

   ```sql
   SELECT UPPER(TRIM("Username")) AS n, COUNT(*)
   FROM "Users" GROUP BY 1 HAVING COUNT(*) > 1;
   ```

   - **回傳空集合** → 才可以往下套用 migration。
   - **回傳非空** → 表示資料庫裡有僅大小寫不同的重複帳號(例如同時存在 `OP1` 與 `op1`)。
     此時**先不要套用**:S6 的 `20260905010000_AddUsernameNormalizedUniqueIndex` 會在建立唯一索引那步
     失敗,**整個 migration 回滾**。必須由 DBA 先合併或改名,再重跑本檢查。
   - 本 migration **刻意不做任何自動合併** —— 自動挑一筆刪除會靜默毀掉某個人的帳號(E18)。
   - ⚠️ **這段檢查 SQL 的等價性只在 ASCII 帳號上成立**。PostgreSQL 的 `UPPER(TRIM())` 與
     程式端的 `Trim().ToUpperInvariant()` 對非 ASCII 字母的大小寫對映、以及部分 Unicode
     空白字元的修剪行為可能不同,所以這段 SQL **不是**通用保證。
     現場帳號一律是 ASCII 代碼(如 `OP1`),故不影響本次部署(E21);
     若日後開放非 ASCII 帳號,這段檢查必須重新設計。
   - 以目前狀況(S5 才剛啟用真登入,正式庫 `Users` 表預期為空或只有部署者剛建的帳號)踩中機率極低,
     但這是唯一會讓整段部署卡住的前置條件,仍必須逐次檢查。
4. `POST /api/v1/auth/setup-admin`,建立第一個 ADMIN 帳號。
5. 以該 ADMIN `POST /api/v1/auth/login` 取得權杖,再逐一 `POST /api/v1/auth/users`
   建立現場帳號(至少要涵蓋目前使用中的 OP1~OP5,角色 `OPERATOR`)。
6. **清空 `Auth__SetupToken` 並重啟 API**(端點回歸 404)。
7. 前端重建容器(compose 掛原始碼、服務跑 build 產物,不重建不會上線)。
