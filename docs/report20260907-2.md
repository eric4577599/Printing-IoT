## 1. 現況比 handoff 描述的更麻煩

`Dashboard.jsx` 完工時的流程:

```js
localStorage 寫入 → syncState: 'pending'
createProductionCompletion(payload)
  .then(...)   // 成功 → 標 'synced'
  .catch(err => {
      console.warn('完工實績落地後端失敗,本地紀錄標記為 pending', err);
      // ← 沒有重試。那筆就永遠停在 pending
  });
```

所以本機殘留有**兩群**,不是一群:

| 群 | 特徵 | 成因 |
|---|---|---|
| A | 沒有 `syncState` 欄位 | S3 之前的舊單,那時根本還沒有後端端點 |
| B | `syncState: 'pending'` | POST 失敗。**自從 S5/S6 開了認證,任何在未登入或權杖過期時完工的單都會 401 然後留在本機** |

第二群會**持續產生**。因此本輪做的是可重複執行的「掃描 → 檢視 → 回填」,不是 one-shot migration。

## 2. handoff 列的四個待決問題,逐一有了答案

handoff 寫「要真正解決需先確認去重規則、工單關聯遺失怎麼補、工廠日怎麼重算,以及客戶現場實際資料量」。

### 2.1 去重規則 —— 沿用既有的冪等鍵,但**要驗內容**

鍵就是 `clientRecordId`(= `String(record.id)`,而 `id` 是完工當下的 `Date.now()`),
與 `completionMapper` 的 `localClientRecordId` 規則一致 —— 兩邊若不同,合併呈現與回填就會對不上同一筆。
後端 `RecordCompletionAsync` 本來就對這個鍵冪等,所以**重跑安全**。

但有一個**不能靜默**的邊界:`Date.now()` 是每台瀏覽器各自產生的,
兩台終端在同一毫秒完工就會撞鍵。那時後端回 `duplicated: true`,
若直接當成「已存在」跳過,**等於弄丟一筆實績**。

處置:冪等命中時比對不良數與停機次數,不一致就標成 **conflict** 並列出差異,交人工判斷。
(不比率值 —— 舊資料的率值本來就可能與後端重算的不同,那是預期的。)

### 2.2 工單關聯遺失 —— 送 null,保留訂單編號文字,並回報筆數

後端 `OrderId` 要 GUID,舊紀錄的 `orderId` 多半是本機的數字 id,接不回去。
送 `null`、保留 `orderNumber` 文字 —— 實績仍查得到是哪一張單,只是點不進工單。
每一筆都回報 `orderLinkLost`,畫面上看得到有幾筆。

### 2.3 工廠日重算 —— **這是最容易靜默算錯的一段,用反解 + 驗證**

後端會拿 `completedAt` 重新推算工廠日。舊紀錄若只有 `date` 沒有 `finishedAt`,
把日期當成當地午夜送出,會被日界(08:00)判到**前一天** —— 整批位移,而且不會有任何地方示警。

**對真實後端實測證實了這個風險**:

| 送出 | 後端判定 | 目標 |
|---|---|---|
| `2026-08-01T00:00:00+08:00`(當地午夜) | **2026-07-31** ❌ | 2026-08-01 |

作法不是算時差,是**反解 + 驗證**:以日界當鐘面時刻造候選時間,
逐一用 `resolveFactoryDate` 回推,**只回傳確實會還原成目標工廠日的那個**。
判準就是不變量本身,不是我對時區算術的信心。

**跨語言驗證**(單元測試只驗得到前端那半,所以另外對真實後端跑了一次):

| 目標工廠日 | 反解時刻(UTC) | 後端 `FactoryDayCalculator` 判定 |
|---|---|---|
| 2026-08-01 | `2026-08-01T22:30:00Z` | 2026-08-01 ✅ |
| 2026-08-31 | `2026-08-31T22:30:00Z` | 2026-08-31 ✅ |
| 2024-02-29(閏日) | `2024-02-29T22:30:00Z` | 2024-02-29 ✅ |
| 2026-12-31(跨年) | `2026-12-31T22:30:00Z` | 2026-12-31 ✅ |

推補時間的那些紀錄一律標記 `approximatedTime` —— 「幾點完工」是我們補的,不是現場的,使用者有權知道。

### 2.4 資料量 —— 上限 1000,逐筆送並處理限流

`Dashboard.jsx` 對 `productionHistory` 有 1000 筆上限,所以最壞情況就是 1000 筆。
逐筆送(不併發:併發只會更快撞限流,而且讓進度顯示失去意義),
撞到 429 就退避 5 秒重試,最多約一分鐘 —— **429 是「要等」,不是失敗**。

這裡直接吃到我們昨天剛設的額度:全域 600/分。回填上千筆必然撞到,所以退避是必要的而非防禦性冗餘。

### 3.1 幾個刻意的取捨

**不送 `defectQty` / `stopCount`**。後端從明細重算這兩個彙總欄位,送了也會被忽略,
還會讓讀程式的人以為前端說了算。

**明細筆數超過 200 時擋下,不截斷**。截掉不良明細會讓後端算出偏低的不良數 ——
那是靜默竄改實績,寧可讓人工處理。

**冪等鍵過長時擋下,不截斷**。截了就不是同一筆,重跑會長出第二列。

**負值夾到 0 但回報**。後端對負值直接回 400,不夾的話整筆進不去;
但夾了不說等於偷改數字,所以每一次都列進 issues。

**停機時長容忍三種形狀**。`reportUtils.durationToMinutes` 只吃 `"MM:SS"`,**其餘一律回 0** ——
舊紀錄若把時長存成數字,直接套用會讓停機時間靜默歸零,而停機分鐘是稼動率的分母成分,
歸零會讓那筆的稼動率虛高。因此明確處理 `"MM:SS"` / 數字 / 數字字串,認不得的回 0 但回報。
(這一條是寫測試時撞出來的,原本沒想到。)

## 5. 這一項解掉之後的連鎖

S8 的報表彙總有一個條件:**區間內 `localOnlyCount > 0` 時不採用後端彙總**,
因為後端看不到本機殘留,採用它會讓彙總數字與逐筆明細互相矛盾。

回填完成之後 `localOnlyCount` 歸零,那個分支就不再觸發,報表自動改用後端彙總。
**但 `reportUtils` 的彙總函式仍不能刪** —— 它還是降級路徑(後端取不到時要有東西可用),
而且只要有任何一台瀏覽器還沒回填,那台就仍走前端計算。
