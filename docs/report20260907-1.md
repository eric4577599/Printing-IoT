## 1. 從記錄到根因

Eric 貼出的 nginx 記錄反覆出現同一組:

```
172.65.90.66 - - "GET /  HTTP/1.1" 200 453 ... HeadlessChrome/143.0.0.0
172.65.90.66 - - "GET /api/orders HTTP/1.1" 401 0 "http://localhost:5600/"
172.65.90.66 - - "POST /api/orders/sync HTTP/1.1" 401 0 "http://localhost:5600/"
```

### 1.1 第一個判斷我做錯了,當場推翻

我先看到 `172.65.90.66` 落在 Cloudflare 的 172.64.0.0/13 段、又不在 Docker 的 172.16–172.31 段,
就判定「有東西從外網打你的系統」。**錯了。**

決定性的反證只花一條指令:我自己從本機 `curl localhost:5600`,nginx 也記成 `172.65.90.66`。

```bash
curl -s -o /dev/null "http://localhost:5600/api/orders"
docker compose logs --tail 3 frontend | grep curl
# → 172.65.90.66 - - ... "GET /api/orders HTTP/1.1" 401 0 "-" "curl/8.7.1"
```

那些 HeadlessChrome 是**專案自己的 e2e 測試**(`frontend/tests/dashboard.e2e.test.js:31`
`page.goto('http://localhost:5600')`,referer 完全吻合),不是攻擊。

### 1.2 真正的根因:客戶端身分在 NAT 那一跳就消失了

實測三種來源:

| 來源 | nginx 記到的 `$remote_addr` |
|---|---|
| 本機 `localhost:5600` | `172.65.90.66` |
| 區域網路 `192.168.0.71:5600` | **同一個 `172.65.90.66`** |
| puppeteer e2e | **同一個 `172.65.90.66`** |

Docker Desktop 的埠轉發把**所有**進到已發布埠的流量 NAT 成單一位址。
限流分區鍵是 `RemoteIpAddress`,所以 **全廠共用一個桶**。

### 1.3 離觸發只差一台看板

- `frontend/src/hooks/useRealtimeData.js:59` → `setInterval(fetchRealtime, 1000)` = **60 次/分/台**
- 原全域額度 `Program.cs` → **100 次/分**(照「每個 IP 一個桶」設計的數字)
- **兩台看板 = 120 > 100**

實測(修正前):

```
連發 115 次 → 100 個 401、15 個 429
```

### 1.4 而且失效是靜默的

```js
} catch (err) {
    // Silently retry — normal in disconnected/startup scenarios
}
```

429 不顯示任何東西。操作員看到的是**數字凍住、沒有提示**,無從分辨「機台停了」與「連線被擋」。
這一條**沒有**在本輪修掉,列為開放問題 **O-16** —— 它牽涉現場 UI 取捨,不是我該替 Eric 決定的。

## 3. 修法:額度由設備數推導

Eric 的指示是「這只是 demo 系統,最多不超過 5 台連線,對應機台數量改為參數」。
因此不是拍一個大數字,而是讓額度可由設備數推導 —— 現場加機台只改一個數字,
而且「每台多少」這個意圖在設定檔裡看得懂。

### 3.1 設定

| 鍵 | 預設 | 意義 |
|---|---|---|
| `RateLimit:MaxDevices` | **5** | 現場會連線的設備數 —— 看板、管理端、ERP,**所有會打 API 的客戶端**都要算進去 |
| `RateLimit:PerDevice:PermitLimit` | 120 | 每台每分鐘的請求預算(輪詢佔 60,留一倍餘裕) |
| `RateLimit:PerDevice:WindowMinutes` | 1 | 視窗 |
| `RateLimit:Auth:PerDevicePermitLimit` | 5 | 每台每分鐘的登入嘗試 |
| `RateLimit:Auth:WindowMinutes` | 1 | 視窗 |
| `RateLimit:Global:PermitLimit` | *(不設)* | 絕對覆寫,設了就不走推導 |
| `RateLimit:Auth:PermitLimit` | *(不設)* | 同上 |

生效額度 = 設備數 × 每台預算 → **全域 600/分、登入 25/分**。

### 3.2 三個實作決定

**推導只有一份實作**。`ResolveRateLimitBudget(IConfiguration)` 同時供限流設定與啟動記錄使用 ——
兩處各算一次就會漂移,那正是這個專案剛在 S8 花力氣消滅的東西。

**設定必須在 `AddRateLimiter` 的 lambda 裡讀**。我第一版把讀取搬到外層 top-level,
結果七個測試同時轉紅:lambda 在 DI 建構時才執行,那時設定來源都已就緒;
外層執行得更早,`WebApplicationFactory` 用 `ConfigureAppConfiguration` 疊上去的測試設定還沒加進來。
這一點已寫成程式碼註解釘在原地。

**設備數夾到 1 以上**。`MaxDevices = 0` 會讓額度變成 0,第一次請求就 429,現場直接停擺 ——
一個打錯的設定值不該有這種威力。有測試釘住(`NonPositiveDeviceCount_ClampsToOne`)。

### 3.3 誠實標註

這個參數表達的是「**整廠預算 = 台數 × 每台預算**」,**不是**真的每台一個桶。
NAT 之後分不出裝置,單一台跑掉仍可能吃光全部配額。
要真正做到每台一桶,需要不可偽造的客戶端識別 —— 那是另一件事,不在本輪。
