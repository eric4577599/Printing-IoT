## 2. 缺口一 · 登入帳號大小寫語意(定案:不分大小寫)

### 2.1 決策與理由(已定案,RD 不得改採他案)

**採「帳號不分大小寫」**:

1. 現場是**觸控終端**,作業員不該因為大小寫打錯而登不進去 —— 這正是 S5 §12 R2 想避免的失效模式。
2. 建立端(`AuthController.CreateUser`)**早已是不分大小寫唯一**(S5 §4.2、AC-22),登入端本來就該一致;
   目前是同一個 `Username` 欄位在兩端採用不同的相等語意。
3. 精確比對的代價(部署時大小寫必須逐字對齊、錯了只會看到「帳號或密碼錯誤」)全部落在最沒有除錯能力的人身上。

### 2.2 正規化定義(唯一的一份定義,全系統共用)

```
Normalize(s) = (s ?? "").Trim().ToUpperInvariant()
```

- **大寫**而非小寫:與既有 `AppRoles.Normalize` 同一慣例,也與 ASP.NET Core Identity 的 `NormalizedUserName` 一致;
  `ToUpperInvariant` 是 .NET 官方建議的「用於比較的正規化」寫法(避免文化相依的大小寫映射)。
- **含 Trim**:觸控鍵盤與條碼槍常帶入前後空白,`" op1 "` 必須能登入(AC-49)。
- **只作用於帳號**。密碼、顯示名稱、班別一律不動。

### 2.3 現況分歧(事實與行號,供 RD 定位)

| 位置 | 現況 |
|---|---|
| `backend/PrintingIoT.API/Controllers/AuthController.cs:57` | `.FirstOrDefaultAsync(u => u.Username == request.Username)` —— **精確比對** |
| 同檔 `:202-204` | `StringComparison.OrdinalIgnoreCase` 檢查重複 —— **不分大小寫**,且是**載入全部帳號後在記憶體比對** |
| `backend/PrintingIoT.Infrastructure/Data/PrintingContext.cs:73-74` | `Username` 唯一索引**未指定不分大小寫定序** —— DB 層沒有背書,理論上併發可繞過應用層檢查 |

## 3. 應用層與資料庫層一致化(選型與理由)

### 3.1 選定方案:新增 `UsernameNormalized` 欄位 + 唯一索引

`Users` 新增一個 `UsernameNormalized`(varchar(50), NOT NULL),值恆為 `Normalize(Username)`,並在其上建**唯一索引**。
登入查詢與重複檢查一律比對這個欄位。

### 3.2 為什麼不選另外兩案(必須寫進報告)

| 方案 | 為什麼不選 |
|---|---|
| **改索引定序**(PostgreSQL ICU non-deterministic collation 或 `citext`) | ① 相等語意藏在資料庫定序裡,`u.Username == x` 這行程式碼看不出它是不分大小寫的,未來換人維護必踩;② **EF Core InMemory 供應者不支援 collation**,測試環境會與正式環境行為分歧 —— 本輪的核心 AC(「建 `OP1` 用 `op1` 登入成功」)在 InMemory 上根本驗不出來,等於又造一個沒有驗收出口的洞;③ `citext` 需要安裝擴充,屬於部署環境變更 |
| **存入前一律轉小寫,直接覆寫 `Username`** | 破壞顯示:帳號 `OP1` 會被存成 `op1`,名冊與稽核日誌全部變小寫,現場既有的 OP1~OP5 命名慣例消失。**帳號的顯示形態必須保留**(AC-47 / AC-55 釘住) |

選定方案的代價,誠實列出:多一個欄位、必須保證兩欄永遠同步。第二點以 §3.3 的**實體層自動同步**消除,而不是靠「記得在每個寫入點設定」。

### 3.3 實體層自動同步(防呆,不可改成手動設定)

`backend/PrintingIoT.Core/Entities/Auth/User.cs`:

```
Username           : required string   // 保留原始大小寫,供顯示與稽核;setter 內同步寫入 UsernameNormalized
UsernameNormalized : string            // 唯讀對外(private set),值恆為 Normalize(Username),[Required][MaxLength(50)]
```

- `Username` 的 setter 內呼叫 `AppUsernames.Normalize(value)` 寫入 `UsernameNormalized`。
- 這樣**任何**建立路徑(controller、seed、既有測試的 `new User { Username = "op1", ... }`)都自動正確,
  不可能有人忘記設定。既有測試因此**不需要修改**(AC-52 反向釘住這個保證)。
- EF Core 讀取時會同時設定兩個屬性,先後順序不影響結果(Username setter 算出的值與 DB 值相同)。

### 3.4 正規化工具

新增 `backend/PrintingIoT.Core/Constants/AppUsernames.cs`(與 `AppRoles.cs` 同層同命名空間):

```
public static class AppUsernames
{
    public static string Normalize(string? username);   // (username ?? "").Trim().ToUpperInvariant()
}
```

函式級註解用正體中文,說明輸入 / 輸出 / 邏輯,並註明「大寫慣例與 AppRoles.Normalize 一致」。

### 3.5 後端改動點

| 檔案 | 改動 |
|---|---|
| `Core/Entities/Auth/User.cs` | 依 §3.3 新增 `UsernameNormalized` 與 `Username` 的同步 setter |
| `Core/Constants/AppUsernames.cs` | **新增**,§3.4 |
| `Infrastructure/Data/PrintingContext.cs` | 新增 `UsernameNormalized` 唯一索引(`IX_Users_UsernameNormalized`);**保留**既有 `Username` 唯一索引(較寬鬆、冗餘但無害,移除只是多餘的變動) |
| `API/Controllers/AuthController.cs:57`(Login) | 改為 `var normalized = AppUsernames.Normalize(request?.Username); ... FirstOrDefaultAsync(u => u.UsernameNormalized == normalized)`。**其餘邏輯不動**:`IsActive` 檢查、BCrypt 密碼驗證、失敗訊息不區分原因、限流,全部保持 S5 現狀 |
| 同檔 `:202-204`(CreateUser) | 記憶體比對改為 `await _context.Users.AnyAsync(u => u.UsernameNormalized == normalized)` —— **與 DB 唯一索引同一個判準**,且不再把全表帳號載入記憶體 |
| 同檔 SetupAdmin / CreateUser 的 `SaveChangesAsync` | 以 `try/catch (DbUpdateException)` 包住,唯一鍵衝突回 `409 Conflict`(併發競態的最後一道防線)。**誠實標註**:InMemory 供應者不強制唯一索引,此分支無法以自動化測試證明,由 AC-53(模型層索引存在)+ 程式碼審查把關 |
| `API/Controllers/AuthController.cs`(UpdateUser) | **不動**。`UpdateUserRequest` 沒有 username 欄位,帳號不可改 |

登入查詢的正規化必須在 **C# 端算好再進 LINQ**(`u.UsernameNormalized == normalized`),
不可寫成 `u.Username.ToUpper() == ...` —— 後者在 PostgreSQL 上會讓索引失效並全表掃描。

## 4. 資料庫 migration

**檔名**:`backend/PrintingIoT.Infrastructure/Migrations/20260905010000_AddUsernameNormalizedUniqueIndex.cs`
(+ `.Designer.cs`,並更新 `PrintingContextModelSnapshot.cs`)。排在 S5 的 `20260905000000_...` 之後。

**Up(順序不可調換)**:

1. `AddColumn "UsernameNormalized"` varchar(50),先 `nullable: true`。
2. `Sql`:`UPDATE "Users" SET "UsernameNormalized" = UPPER(TRIM("Username"));` —— 回填既有列。
3. `AlterColumn` 改為 `nullable: false`。
4. `CreateIndex` `IX_Users_UsernameNormalized`,`unique: true`。

**Down**:`DropIndex` → `DropColumn`。(既有 `Username` 唯一索引全程不動。)

**本機無法套用(必須在報告標明)**:這台機器沒有 Docker、不連真實 PostgreSQL,
migration 只能產生與編譯,**無法實際 apply**。`PrintingIoT.Tests` 走 EF Core InMemory,不經 migration,測試不受影響。

**對既有資料的影響(必須在報告寫成部署前置檢查)**:

- 正常情況:既有帳號**完全不受影響**,大小寫原樣保留,只是多一欄正規化值。
- **唯一會失敗的情況**:資料庫已存在僅大小寫不同的兩個帳號(例如 `OP1` 與 `op1`),第 4 步建唯一索引會失敗、整個 migration 回滾。
- 部署者**套用前**先跑這段檢查,回傳空集合才可繼續:

  ```sql
  SELECT UPPER(TRIM("Username")) AS n, COUNT(*)
  FROM "Users" GROUP BY 1 HAVING COUNT(*) > 1;
  ```

  非空表示有大小寫重複,必須由 DBA 先合併或改名(本 migration **不做任何自動合併** —— 自動挑一筆刪除會靜默毀掉某個人的帳號)。
- 以本專案現況(S5 才剛啟用真登入,正式庫 Users 表預期為空或只有部署者剛建的帳號)踩中機率極低,但仍必須檢查。

## 5. 缺口二 · CORS 預檢驗收出口

### 5.1 事實與現況

- S5 §8 E6 原文要求「順序修正後**必須實測確認**」,但 §7 無對應 AC,§11 DoD 只綁 AC-01~46 → **無驗收出口**。
- 獨立複驗:`grep -rn "HttpMethod.Options" backend/ --include="*.cs"` 無結果。
- `Program.cs:166` `app.UseCors("AllowFrontend")` 確實在 `:169` 限流與 Authentication / Authorization 之前;
  依 ASP.NET Core 行為,CorsMiddleware 會短路處理帶 `Origin` + `Access-Control-Request-Method` 的 OPTIONS 並直接回應,
  **實際行為極可能已經正確**。本輪補的是**契約與回歸保護**,不是修一個已證實的缺陷。

### 5.2 要補的行為定義

| 情境 | 預期 |
|---|---|
| `OPTIONS /api/orders`,帶 `Origin: http://localhost:5600`(`Cors:AllowedOrigins` 內)與 `Access-Control-Request-Method: POST`,**不帶任何權杖** | **不得**為 `401`;必須是 2xx(ASP.NET Core 預設 `204 No Content`),且回應帶 `Access-Control-Allow-Origin` 等於該來源 |
| 同上但 `Origin: http://evil.example.com`(不在允許清單) | **不得**帶 `Access-Control-Allow-Origin` 標頭(證明沒有人為了讓預檢通過而改成 `AllowAnyOrigin`) |

測試置於 `backend/PrintingIoT.Tests/Integration/RateLimitAndCorsTests.cs`,沿用該檔既有的 `AuthTestFactory` 與 `AllowedOrigin` 常數。

## 8. 資料與型別定義(本輪異動)

### 8.1 實體

| 欄位 | 型別 | 說明 |
|---|---|---|
| `User.Username` | `required string`,varchar(50) | **保留原始大小寫**,顯示與稽核用;setter 同步寫入 `UsernameNormalized` |
| `User.UsernameNormalized` | `string`(private set),varchar(50) NOT NULL | `Normalize(Username)`;唯一索引 `IX_Users_UsernameNormalized` |

### 8.2 API 契約

**不變**。`LoginRequest` / `LoginResponse` / `CreateUserRequest` / `UserSummary` 全部維持 S5 §6.1 定義,
`UsernameNormalized` **絕不出現在任何回應** —— 對外一律回原始大小寫的 `Username`。

### 8.3 輸入 / 輸出摘要(本輪唯一有行為變化的端點)

`POST /api/v1/auth/login`

- 輸入:`{ username: string, password: string }`。
- 比對:`Normalize(username)` 對 `UsernameNormalized`(不分大小寫、去前後空白);**密碼精確比對**(BCrypt)。
- 輸出:成功 `200` + `LoginResponse`,其 `username` 為**資料庫中的原始大小寫**;
  失敗一律 `401` 且訊息不區分「帳號不存在」與「密碼錯誤」(S5 既有行為,不變)。

## 9. 驗收標準(每條可被自動化測試驗證)

延續 S5 的 AC-01~46,本輪新增 **AC-47 ~ AC-62**。S5 既有 AC 全部繼續有效。

### 9.1 後端 · 帳號大小寫(`backend/PrintingIoT.Tests/Integration/AuthSetupAndUsersTests.cs`)

| ID | 驗收條件 |
|---|---|
| **AC-47** | ADMIN 權杖 `POST /api/v1/auth/users` 以 `username = "OP1"` 建立 OPERATOR → `201`;隨即以 `POST /api/v1/auth/login` 帶 `username = "op1"` 與同一密碼 → **`200`**,且回應的 `username` 為 **`"OP1"`**(原始大小寫)。**這是本輪的核心 AC** |

## 10. Edge case 與預期行為(本輪新增)

| # | 情境 | 預期行為 |
|---|---|---|
| **E16** | 管理者建 `OP1`,現場作業員輸入 `op1` / `Op1` / `oP1` | **登入成功**。這是本輪存在的理由(AC-47) |
| **E17** | 觸控鍵盤或條碼槍帶入前後空白 `" op1 "` | Trim 後成功登入(AC-49) |
| **E18** | 正式資料庫已同時存在 `OP1` 與 `op1` | migration 建唯一索引時**失敗並回滾**,不會靜默刪資料。部署者必須先跑 §4 的檢查 SQL 合併重複帳號。**這是刻意的**:自動挑一筆刪掉會毀掉某個人的帳號 |
| **E19** | 兩個併發請求同時建立 `OP1` 與 `op1` | DB 唯一索引擋下其中一筆,`DbUpdateException` 轉為 `409 Conflict`。**誠實標註**:InMemory 不強制唯一索引,此路徑無自動化出口,靠 AC-53 + 程式碼審查 |
| **E20** | 名冊舊列的 `username` 是顯示名稱(S5 寫壞的資料) | 該列點擊後填入的帳號可能不存在 → 登入 401。作業員可**手動輸入正確帳號**登入;管理者把該列**重新儲存一次**即修正(Upsert 覆寫)。不做自動遷移 —— 無法可靠分辨「顯示名稱剛好等於帳號」與「寫壞的資料」 |
| **E21** | 帳號含非 ASCII 字元(中文帳號) | `ToUpperInvariant` 對中文無作用,行為等同精確比對。**不在本輪範圍**,現場帳號一律 ASCII 代碼 |
| **E22** | 有人日後把登入查詢改回 `u.Username == request.Username` | AC-47 會紅。這正是本輪要建立的回歸保護 |
| **E23** | CORS 預檢在正式環境被反向代理攔截 | 超出應用程式範圍,不在 AC 內;若現場出現預檢失敗,先確認 Cloudflare Tunnel / 反向代理是否轉發 OPTIONS(寫入報告的排錯提示) |
