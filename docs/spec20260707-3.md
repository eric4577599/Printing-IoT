## 1. 工作項 1 — 修正 shadow FK(`ScheduleId1` / `PartId1`)

### 1.1 現況與根因(PM 已核對程式)

- `MMS.Core/Entities/MaintenanceRecord.cs` 有導覽屬性 `Schedule`(第 24 行)與 `Part`(第 27 行)。
- `MmsDbContext.OnModelCreating`(第 45–53 行)卻以 **無導覽版** `HasOne<MaintenanceSchedule>()` / `HasOne<SparePart>()` 設定關聯 → EF 視導覽屬性為「另一條」關聯,依慣例各生一個 shadow FK:`ScheduleId1`、`PartId1`。
- 兩個 shadow 欄位已隨 `InitialCreate` 進入 schema(欄位 + FK + index,見該檔第 193/195、215–216、225–226、289–301 行)。
- 應用程式**從未寫入 shadow 欄位**:`RecordsController` 一律直接指定 `ScheduleId` / `PartId`(第 71–72 行),不透過導覽屬性 → 既有資料的 `ScheduleId1` / `PartId1` 實務上恆為 NULL。

### 1.2 修正內容

1. **模型設定**:`OnModelCreating` 兩條關聯改綁導覽屬性,FK 與刪除行為不變(維持 optional FK 的 EF 預設,**不得**額外指定 `OnDelete`):
   - `HasOne(r => r.Schedule).WithMany().HasForeignKey(r => r.ScheduleId)`
   - `HasOne(r => r.Part).WithMany().HasForeignKey(r => r.PartId)`
2. **新增 migration**(名稱建議 `RemoveShadowForeignKeys`),內容:
   - **Up**:
     a. 先以 `migrationBuilder.Sql` 做防禦性回填(冪等,正體中文註解說明「實務上恆為 NULL,此為保險」):
        `UPDATE "MaintenanceRecords" SET "ScheduleId" = COALESCE("ScheduleId", "ScheduleId1"), "PartId" = COALESCE("PartId", "PartId1");`
     b. 依序 Drop FK(`FK_MaintenanceRecords_MaintenanceSchedules_ScheduleId1`、`FK_MaintenanceRecords_SpareParts_PartId1`)→ Drop index(`IX_MaintenanceRecords_ScheduleId1`、`IX_MaintenanceRecords_PartId1`)→ Drop column(`ScheduleId1`、`PartId1`)。
   - **Down**:還原 schema — 重加兩個 nullable uuid 欄位、index、FK(名稱與 InitialCreate 相同)。註解明載:**Down 只還原結構,不還原欄位內容**(shadow 欄位實務上恆為 NULL,可接受)。
3. **Snapshot**:以 `dotnet ef migrations add` 產生,snapshot 自動更新;不得手改 snapshot 內容。

### 1.3 輸入/輸出定義

- 輸入:無新增 API/DTO;純模型與 schema 修正。
- 輸出(schema):`MaintenanceRecords` 表不再有 `ScheduleId1`、`PartId1` 欄位及其 FK/index;`ScheduleId`、`PartId` 欄位與其既有 FK 不變。
- 輸出(行為):`/api/records` 等既有 API 行為完全不變。

### 1.4 Edge case 預期行為

| 情境 | 預期 |
|---|---|
| 既有 DB(已套用 InitialCreate + AddPartsManagement)升級 | `dotnet ef database update` 只套新 migration,零錯誤,既有 `MaintenanceRecords` 資料(含 `ScheduleId`/`PartId` 值)完整保留 |
| 空庫從零建立 | 三支 migration 依序全套成功,最終 schema 無 shadow 欄位 |
| 新 migration 執行 Down | schema 還原至 AddPartsManagement 狀態(欄位/FK/index 回來),再 Up 一次仍成功(可反覆) |
| 極端:某舊庫 `ScheduleId1` 有值而 `ScheduleId` 為 NULL | Up 的 COALESCE 回填先保住關聯值,再刪欄位,不掉資料 |

## 3. 工作項 3 — 搬移腳本備份檔保留上限

### 3.1 現況

`scripts/migrate-parts-data.sh` 每次完整執行都在 `BACKUP_DIR`(預設 `<repo>/backups`,已 gitignore)產生 `flexodb-backup-<UTC時戳>.sql`,**無清理機制**,長期堆積。

### 3.2 修正內容

1. 新增環境變數 **`BACKUP_KEEP`**(預設 `5`):備份成功(非空檢查通過)後,依檔名時戳排序保留最新 `BACKUP_KEEP` 份 `flexodb-backup-*.sql`,其餘刪除。
2. 安全約束:
   - **只**刪除 `BACKUP_DIR` 下符合 `flexodb-backup-*.sql` 命名的檔案;其他檔案一律不碰。
   - 清理僅在**本次備份成功之後**執行;`--verify` 模式(不備份)**不清理**。
   - `BACKUP_KEEP` 非正整數(含 0、負數、非數字)→ 以明確錯誤訊息中止(`fail`),不進行搬移與刪檔。
   - 清理動作輸出人可讀訊息(刪了哪些檔 / 保留幾份)。
3. 更新腳本檔頭說明(輸入環境變數清單加入 `BACKUP_KEEP`、輸出說明補保留策略)。
4. `scripts/test-migrate-parts-data.sh` 新增案例(建議 T5):於暫存 BACKUP_DIR 造出多於 `BACKUP_KEEP` 份的假備份檔(含 1 個不符命名的檔案)→ 執行清理後斷言:僅最新 N 份備份保留、不符命名檔案未被刪。若整合測試需 DB 而環境不可行,至少以可獨立呼叫的函式 + shell 斷言覆蓋清理邏輯。

### 3.3 輸入/輸出定義

- 輸入:環境變數 `BACKUP_KEEP`(選填,預設 5)+ 既有變數不變。
- 輸出:`BACKUP_DIR` 內 `flexodb-backup-*.sql` 檔數 ≤ `BACKUP_KEEP`;stdout 有清理結果訊息。
