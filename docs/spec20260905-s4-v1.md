## 1. 現況(讀碼確認,作為修改基準)

### 1.1 直接讀 localStorage 的入口(只有兩處)

| 位置 | 現行寫法 |
|---|---|
| `frontend/src/modules/reports/ReportsPage.jsx:59-67` | `useEffect` 內 `JSON.parse(localStorage.getItem('productionHistory') \|\| '[]')` → `setProductionHistory` |
| `frontend/src/pages/analysis/hooks/useAnalysisData.js:24-35` | `useMemo` 內同樣讀法,並就地以 `record.date >= startDate && <= endDate` 過濾 |

三個檢視元件(`DailyReportView`、`MonthlyReportView`、`StopReasonView`)與 `AnalysisTable` / `AnalysisSummary` 都只靠 props 收資料,**自己不碰儲存層**。

### 1.2 三個檢視元件各自持有的日期區間(本輪最容易踩的坑)

| 元件 | 日期區間來源 | 影響 |
|---|---|---|
| `ReportsPage` 生產明細 | 父層 `appliedRange`(按「確認」才更新) | 可直接下推 |
| `DailyReportView` | 父層 `startDate` / `endDate`(props) | 可直接下推 |
| **`MonthlyReportView`** | **元件內部** `selectedYear` / `selectedMonth` → 自算 `dateRange` | ⚠ 父層不知道它要哪個月 |
| **`StopReasonView`** | **元件內部** `startDate` / `endDate`(預設近 7 天) | ⚠ 同上 |

現行之所以能運作,是因為 localStorage 一次把**全部**資料交給父層,子元件再自行過濾。一旦父層改成只抓 `appliedRange` 區間,月報與停車原因頁會**顯示不出資料**。這是本輪的必修項,見 F3。

### 1.3 後端既有端點的實際契約(讀碼確認,與需求描述有兩點出入)

`GET /api/production/completions?from=&to=&page=&pageSize=`

- 回應是**裸 JSON 陣列**,`ProductionService.GetCompletionsAsync` 直接 `return rows.Select(ToDto).ToList()`,**沒有 total / totalPages / hasNext 的分頁信封**。
  → 因此「還有沒有下一頁」只能靠「本頁筆數是否等於 `pageSize`」判斷。這直接決定 F2 的分頁演算法。
- 清單查詢**已經 `Include(c => c.Defects).Include(c => c.Stops)`**,元素即完整 `ProductionCompletionDto`。
  → **不需要**為了拿停機明細而對每筆再打 `GET /completions/{id}`。
- 排序:`ProductionDate` 遞減、再 `CompletedAt` 遞減。
- `page < 1` 夾到 1;`pageSize` 夾到 1–500;`from` / `to` 格式錯 → 400。

`frontend/src/services/api.js:154` **已存在** `getProductionCompletions({ from, to, page, pageSize })`,本輪沿用,不重寫。

### 1.4 後端欄位缺口(本輪必須誠實處理,不可假裝有)

`ProductionCompletion` 實體與 DTO **沒有 `customer`,也沒有 `productName`**(實體註解說明刻意不對 `Order` 建導覽屬性,只留 `OrderId` 與冗餘的 `OrderNumber`)。但報表明細表(`ReportsPage` 第 3、5 欄)與分析頁 Excel 匯出都要顯示這兩個欄位。處理方式見 F4.3。

另一個缺口:S3 的 POST payload(`Dashboard.jsx:427-431`)送出的 `stops` 只有 `{ code, reason, durationMinutes }`,**沒有送 `startedAt`**,雖然後端 `ProductionStopRequest` 有這個欄位。因此目前資料庫內所有停機明細的 `StartedAt` 皆為 `null`,回讀後停車起始時間欄位會是空的。見 F6。

### 1.5 前端公式現況

`frontend/src/utils/reportUtils.js` 同時承擔兩類計算:

- **單筆率值**:`calculateOEE`、`calculateUtilization` —— 與 C# `OeeCalculator` 是同一份規則的兩處實作(S3 §5.1)。
- **彙總**:`calculateDailySummary`、`calculateMonthlySummary`、`groupStopReasonsByReason`、`calculateWeightedAvgOEE`、`analyzeStopReasons` —— **後端完全沒有對應實作**,也沒有任何彙總端點。

## 2. 設計原則

1. **後端是實績的權威來源**(承 S3 原則 1)。後端已算好的欄位,前端一律**原樣採用,不得重算**。
2. **不讓使用者以為資料遺失**。本輪不做資料搬移(S3 §9 第 2 項仍成立),因此讀取端必須自己補上落差,而不是把落差丟給使用者。
3. **降級不中斷現場**(承 S3 原則 4)。API 失敗時必須有明確退路,且退路狀態要**看得見**,不可靜默。
4. **不可靜默截斷**。任何「只取到一部分」的情形都必須在畫面上呈現。
5. **加法式變更**。既有 props 契約只能**新增選用參數**,不得改既有參數的意義或必要性;既有 export 不刪。
6. **不加相依套件**。只用既有 axios / React / vitest。
7. **兩份實作必須指名 SSOT**。凡是前後端都有的計算,規格必須寫明哪一側是真相;不留「兩份都在算、沒人說了算」的狀態。

## 3. 關鍵決策與理由

本輪四個需要判斷的點,決策與理由集中在此,實作細節在 §4。

### 決策 1 · 分頁:逐頁取到取完,並以硬上限防失控

**採用**:`pageSize = 500`(後端上限),`page` 從 1 遞增,直到某頁回傳筆數 `< 500` 為止;同時設硬上限 `maxPages = 20`(= 10,000 筆)。

**理由**:
- 後端回的是裸陣列、沒有 total(§1.3),所以「取完了沒」只能靠短頁判斷,這是唯一可靠的終止條件。
- 不選「改為後端彙總」:那要新增日彙總、月彙總、停機原因彙總三組端點與其契約,正是 S3 §9 判定「工作量與三項必做相當」而延後的東西;本輪目標是換資料來源,不是重做報表架構。彙總留在前端,見決策 4。
- 硬上限的作用是**防呆而非省流量**:若後端資料異常膨脹或分頁參數被誤改,不能讓前端無限迴圈打 API。
- 觸到硬上限時**不是靜默截斷**:回傳 `truncated: true` 與已取得筆數,由 UI 明確標示(AC-S4-07)。

**已知代價**:當總筆數恰為 500 的倍數時,會多打一次回傳空陣列的請求。這是正確性換來的成本,接受。

### 決策 2 · 降級:退回本機快取,並明確標示為降級狀態

**採用**:API 失敗(網路錯誤、非 2xx、逾時)時,不拋出、不白畫面,改用本機快取的資料繼續渲染,並把 `isDegraded` 設為 `true`,畫面顯示可辨識的警示列。

**理由**:
- 沿用 S3 §2 原則 4「降級不中斷現場」。報表是現場交班會看的東西,壞掉比舊要嚴重。
- 退路選本機快取而不是「顯示空清單」:快取本來就存在、內容是同一形狀、成本為零,且在真正離線時仍有最近 1000 筆可看。顯示空清單等同於謊稱「這段期間沒有生產」,違反原則 2。
- 降級**必須看得見**:若不標示,使用者會把不完整的快取當成完整資料判讀產能,比報表壞掉更危險。

### 決策 3 · 舊資料落差:合併呈現 + 以 `clientRecordId` 去重 + 標示來源

**採用**:同時取後端資料與本機快取,依區間過濾後**合併**;去重鍵為 `backendRow.clientRecordId === String(localRow.id)`;衝突時**後端列勝出**。合併結果每筆帶 `source: 'backend' | 'local'`,並回報 `localOnlyCount`。

**理由**:
- 本輪不做回填遷移(S3 §9 第 2 項),所以後端只有切換後的新完工。若只讀後端,S3 之前的歷史資料會整片消失 —— 需求第 6 點明文禁止讓使用者以為資料遺失。
- 只讀後端 + 標示「資料起始日」的替代方案被否決:它把舊資料**藏起來**再貼一張說明。使用者要的是看到那些單,不是知道它們為什麼看不到。合併能同時滿足兩者(資料看得到、來源分得清)。
- 去重鍵選 `clientRecordId` 而不是 `orderNo`:`clientRecordId` 是 S3 已經確立的冪等鍵,一筆完工一個值,而 `orderNo` 可能重工、可能為 `'-'`。
- 衝突時後端勝出:承原則 1,後端的率值與工廠日是權威;本機那份可能是 `syncState: 'pending'`,或是 S3 之前用舊 OEE 公式算的。
- **仍然滿足「不再直接讀 localStorage 當唯一來源」**:localStorage 降為兩個來源之一,且只在後端沒有該筆時才貢獻資料。

**混合口徑的處理**:S3 §12.6 已提醒舊紀錄的 `oee` 是舊公式算的。合併後同一張表出現兩種口徑會誤導,因此本機列的率值一律**用現行 `reportUtils.calculateOEE` 重算**(它是 S3 §5.1 規則的 JS 實作,與後端同一份規則),使全表口徑一致。後端列則**原樣採用後端值,絕不重算**(AC-S4-10、AC-S4-11)。

### 決策 4 · 公式 SSOT:單筆率值歸後端,彙總留前端,分界寫死在註解

先確認後端回傳的欄位是否足以取代前端計算 —— **答案是只夠一半**:

| 計算 | 後端有嗎 | 本輪 SSOT | 處置 |
|---|---|---|---|
| 單筆 OEE / 稼動率 / 效能 / 良率 | ✅ `oee` / `availabilityRate` / `performanceRate` / `qualityRate`,每筆都有 | **後端** `OeeCalculator` | 後端列直接用,前端不得重算 |
| 日報彙總(`calculateDailySummary`) | ❌ 無端點 | **前端** `reportUtils` | 保留 |
| 月報彙總(`calculateMonthlySummary`) | ❌ 無端點 | **前端** `reportUtils` | 保留 |
| 停機原因彙總(`groupStopReasonsByReason`) | ❌ 無端點 | **前端** `reportUtils` | 保留 |
| 產量加權平均 OEE(`calculateWeightedAvgOEE`) | ❌ 無端點 | **前端** `reportUtils` | 保留 |
| 本機列的單筆率值 | ❌(該筆後端根本沒有) | **前端** `reportUtils`(後端規則的 JS 孿生) | 保留 |

**結論**:S3 §2 原則 2 說的「前端公式在報表改讀後端後即可退場」**本輪不成立,`reportUtils` 全數保留**。理由是後端只提供逐筆率值,沒有提供任何彙總結果,而報表頁要的正是彙總。

**避免漂移的紀律**(必須落實成程式碼,不是口頭承諾):
- `reportUtils.calculateOEE` / `calculateUtilization` 的函式註解必須標明:「本函式是 `PrintingIoT.Core.Services.OeeCalculator` 的 JS 孿生,規則見 `docs/spec20260903-s3-v1.md` §5.1;**僅用於本機列與彙總重算,後端列的率值一律採用後端回傳值**。」
- 對映層必須有註解寫明「後端列不重算率值」,並由 AC-S4-10 釘住。

#### F1.3 `normalizeLocalRecord(record)`

把一筆本機快取記錄正規化成同一形狀。

**輸入**:localStorage 內的 `productionRecord`。
**輸出**:報表記錄物件,`source: 'local'`。
**邏輯**:
- 既有欄位原樣保留(本機列的形狀本來就是目標形狀)。
- **率值一律以 `reportUtils.calculateOEE({ runTime, stopTime, prepTime, goodQty, defectQty, targetQty })` 重算**並覆寫 `oee` / `availabilityRate` / `performanceRate` / `qualityRate`(決策 3 的混合口徑處理)。
- `clientRecordId` 補為 `String(record.id)`,讓去重可對得上。
- `date` 缺失時以 `finishedAt` 前 10 碼補;兩者都缺則該筆視為不可用,由 F1.4 濾掉。

#### F1.4 `mergeCompletionRecords(backendRecords, localRecords)`

**輸入**:兩個已正規化的陣列。
**輸出**:`{ records, localOnlyCount }`。
**邏輯**:
1. 以 `clientRecordId` 建 `Set`,收錄所有後端列。
2. 本機列中 `clientRecordId` 已在 `Set` 內者**捨棄**(後端列勝出)。
3. 其餘本機列標記 `source: 'local'` 併入,`localOnlyCount` = 併入筆數。
4. 結果依 `date` 遞減、再 `finishedAt` 遞減排序(對齊後端排序,讓合併前後視覺順序一致)。
5. `clientRecordId` 為空字串或 `undefined` 的列**不參與去重**,一律保留(寧可重複顯示,不可讓一筆單消失)。

### F2 · 分頁抓取服務

在 `frontend/src/services/api.js` 新增(沿用既有 `api` 實例與命名風格):

```
getAllProductionCompletions({ from, to, pageSize = 500, maxPages = 20 })
```

**輸入**:`from` / `to` 為 `YYYY-MM-DD`(可省略);`pageSize` 上限交由後端夾;`maxPages` 為硬上限。
**輸出**:`{ items, pageCount, truncated }`。
**邏輯**:
1. `page` 由 1 起,反覆呼叫既有的 `getProductionCompletions({ from, to, page, pageSize })`。
2. 把每頁結果串接進 `items`。
3. 當某頁回傳筆數 `< pageSize` → 已取完,`truncated = false`,結束。
4. 當 `page` 達到 `maxPages` 仍未取完 → 停止,`truncated = true`。
5. 任一頁拋錯 → **整個函式拋出**,由上層 hook 轉成降級(不在此吞例外,否則上層分不清「取完了」與「取到一半炸了」)。
6. 回應不是陣列(例如後端日後改成信封)→ 視為該頁 0 筆並結束,不得讓 `.length` 爆 `TypeError`。

**輸出**:

| `isDegraded` | `boolean` | 後端失敗、目前顯示的是本機快取(決策 2) |
| `truncated` | `boolean` | 觸到 `maxPages` 硬上限,資料未取完(決策 1) |
| `localOnlyCount` | `number` | 僅存在本機快取的筆數(決策 3) |
| `reload` | `Function` | 手動重取 |

**邏輯**:
1. `from` / `to` 變動時重新抓取(`enabled === false` 時不抓)。
2. 先讀本機快取並以 `filterByDateRange` 過濾到 `[from, to]`(本機列不經 API,必須自己過濾),再 `normalizeLocalRecord`。
3. 呼叫 `getAllProductionCompletions({ from, to })`。
   - 成功 → `mapCompletionToRecord` 後與本機列 `mergeCompletionRecords`,`isDegraded = false`。
   - 失敗 → `records` 僅含本機列,`isDegraded = true`,`error` 帶原始錯誤,**不重新拋出**。
4. 讀本機快取本身失敗(`JSON.parse` 壞掉、`localStorage` 不可用)→ 當作空陣列,`console.warn`,不影響後端列。
5. 競態:`from` / `to` 快速切換時,**只有最後一次請求的結果可以寫入 state**(以遞增的請求序號或 `AbortController` 旗標判斷,不得用過期回應覆蓋新結果)。
6. 元件卸載後不得 `setState`。

## 5. 狀態呈現規格

兩個入口的畫面都必須能表達下列狀態,且**互斥的主狀態**與**可疊加的警示列**分開處理。

**主狀態(擇一)**:

| 狀態 | 條件 | 呈現 |
|---|---|---|
| 載入中 | `isLoading === true` | 明確的「載入中」訊息(不是空白、不是骨架殘影) |
| 錯誤且無資料可退 | `isDegraded && records.length === 0` | 錯誤訊息 + 「重試」按鈕(呼叫 `reload`) |
| 無資料 | `!isLoading && !error && records.length === 0` | 「此區間無生產紀錄」,**措辭必須與錯誤區分**,不可讓查詢失敗看起來像沒生產 |
| 正常 | 其餘 | 原有表格 / 圖表 |

**警示列(可與正常狀態並存,可同時出現多條)**:

| 警示 | 條件 | 內容要點 |
|---|---|---|
| 降級 | `isDegraded && records.length > 0` | 「無法連線後端,目前顯示本機離線快取,資料可能不完整」+ 重試按鈕 |
| 未取完 | `truncated === true` | 「資料量超過單次查詢上限,目前僅顯示前 N 筆,請縮小日期區間」,N 為實際筆數(決策 1、需求第 3 點) |
| 本機列 | `localOnlyCount > 0` | 「其中 N 筆僅存在本機快取,尚未同步至後端」(決策 3) |

明細表另需以視覺標記(欄位或列樣式)區分 `source === 'local'` 的列。

## 7. 已知 edge case 與預期行為

| # | 情境 | 預期行為 |
|---|---|---|
| E-01 | `from` > `to`(使用者把起訖日填反) | 照送給後端(後端會回空陣列),前端顯示「無資料」;**不**自作主張對調,以免使用者以為自己填對了 |
| E-02 | `from` / `to` 為空字串 | 不帶該參數(既有 `getProductionCompletions` 已如此),等同不限該端;本機列則不做該端過濾 |
| E-03 | 後端回 400(日期格式錯) | 視為請求失敗 → 降級路徑;錯誤訊息顯示後端回的 `error` 文字(後端已是正體中文) |
| E-04 | 後端回 200 但 body 不是陣列 | 該頁視為 0 筆並結束分頁,不拋 `TypeError`(F2 步驟 6) |
| E-05 | 單頁回傳筆數 > `pageSize`(不應發生) | 以實際筆數併入,並視為「可能還有」繼續下一頁;不要因此判定取完 |
| E-06 | `stops[].durationMinutes` 為 0 | `duration === '00:00'`,`durationToMinutes` 回 0,彙總不受影響 |
| E-07 | `stops[].durationMinutes` ≥ 60 | `MM` 不封頂(如 `125.5` → `'125:30'`),`durationToMinutes` 解析後仍為 125.5 |
| E-08 | `stops[].durationMinutes` 的秒數四捨五入到 60 | 進位為 `mm+1` 與 `'00'`(F1.2),不得產生 `'03:60'` |
| E-09 | 後端列的 `orderNumber` 為空字串 | 顯示 `'-'`,與本機列 `orderNo: '-'` 的既有慣例一致 |
| E-10 | 本機快取有一筆 `syncState: 'pending'`,但後端其實已有同 `clientRecordId` 的列 | 去重後由後端列勝出;`localOnlyCount` 不計入這筆 |
| E-11 | 本機快取超過 1000 筆被截斷,最舊的資料已不存在 | 無法補救(本輪不做遷移),但 `truncated` 與「僅存在本機」提示不會誤報;交付報告須提醒此限制 |
| E-12 | 同一 `clientRecordId` 在本機出現兩次(理論上不該發生) | 去重後只保留一筆,以先出現者為準 |
| E-13 | `clientRecordId` 為空 / `undefined` 的本機列 | 不參與去重,一律保留(F1.4 步驟 5),寧可重複顯示也不讓一筆單消失 |
| E-14 | 使用者在載入中快速切換日期區間 | 只有最後一次請求的結果寫入 state(F3 步驟 5);不得出現舊區間結果覆蓋新區間 |
| E-15 | 元件在請求飛行中卸載 | 不呼叫 `setState`,不產生 React 警告 |
