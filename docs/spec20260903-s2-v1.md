## 1. 現況(讀碼確認,作為修改基準)

`backend/PrintingIoT.Worker/Worker.cs` 目前有兩條互不相干的處理路徑:

| | 模擬器路徑 `ProcessMachineUpdate` | 真機路徑 `ProcessWiseUpdate` |
|---|---|---|
| 觸發 topic | `factory/machine/update` | `Advantech/+/data`(可由 `mqtt_topic` 設定) |
| 計數來源 | `length` / `total_length` / `d1` | **硬寫死 `di1`** |
| 狀態來源 | `status` / `status_code`(int → `MachineStatus`) | **硬寫死字串 `"1"`** |
| 寫 Redis `factory/monitor` | 有 | 有 |
| 發布 `factory/monitor/update` | 有 | 有 |
| 寫 `ProductionLogs` | **有** | **完全沒有** |
| deviceId | 缺欄位時填 `"unknown"` 仍寫入資料庫 | 由 topic 第 2 段取得 |

其他已確認事實:

- `MonitorData`(`Core/Models/MonitorData.cs`)為 `record(DeviceId, Speed, DI1, Status, Timestamp)`,`Status` 是 `string`;模擬器路徑塞 `"Running"`/`"Idle"` 等列舉名稱,真機路徑塞 `"1"` —— 同欄位兩種語意。
- 前端 `useRealtimeData.js` 只把 `data.status` 原樣存成 `status_code`,**目前沒有任何地方比對它的值**,因此統一成列舉名稱字串不會造成前端回歸。
- `SpeedCalculator.CalculateSpeedAsync` 的「計數重置偵測」(`state.LastCount != -1 && currentRaw < state.LastCount`)**沒有檢查 `hasQty`**;真機路徑缺 `di1` 時會以 `currentRaw = 0` 呼叫,判定為重置並把 `LastCount`/`LastSmoothedSpeed` 打回 0 —— 這正是 COMM-09 的第二段傷害。
- 設定頁 `frontend/src/components/settings/CommunicationTab.jsx` 已送出 `plc_motor_signal`(預設 `DI-0`)與 `plc_count_signal`(預設 `DI-1`),經 `SettingsService` 寫進 Redis 鍵 `config/communication`,**後端無任何程式讀取**。
- `SpeedCalculator.RefreshMaxSpeedCacheAsync` 已有「每 60 秒重讀 `config/communication`」的既有作法,本規格要求沿用同一模式,不引入新機制。
- `PrintingIoT.Tests` 已參考 `PrintingIoT.Worker` 專案,測試可直接 new Worker 服務;`SpeedCalculatorTests` 已示範用 Moq 假造 `IConnectionMultiplexer` / `IDatabase`。

## 2. 設計原則

1. **單一管線**:真機與模擬走同一條「取樣 → 上鎖 → 算速度 → 寫快照 → 寫歷史 → 發布」管線,差異只留在最前面的 payload 解析器。
2. **可測試優先**:把邏輯從 `MqttWorker`(需要 MQTT 連線才能建構)搬到可獨立 new 出來的服務類別,`MqttWorker` 只剩「訂閱 → 解析 → 呼叫管線 → 發布」。
3. **不知道就說不知道**:任何取不到的訊號一律落到明確的未知值,禁止以「運轉中」或 `0` 假裝有資料。
4. **不加相依套件**:只用既有的 xUnit / Moq / EF Core InMemory / `Microsoft.Extensions.DependencyInjection`。

## 3. 功能需求

### F1 · 訊號名稱正規化與對映(對應需求 3)

**新增** `backend/PrintingIoT.Worker/Services/SignalMapping.cs`:

- `static string SignalNameNormalizer.Normalize(string? name)`
  - 輸入:設定值或 JSON 欄位名(可能為 `DI-1`、`di1`、`DI1`、`DI_1`、`ai0`、`null`)。
  - 邏輯:`null`/空白 → 回傳空字串;否則轉小寫並移除所有非 `a-z0-9` 的字元。
  - 輸出:正規化鍵,例:`DI-1`、`di1`、`DI1`、`DI_1`、` DI 1 ` 全部 → `di1`。
- `static bool JsonSignalReader.TryGetSignal(JsonElement root, string normalizedKey, out JsonElement value)`
  - 逐一走訪 `root` 的屬性,對屬性名做同一套 `Normalize` 後比對;命中第一個相符者即回傳 `true`。
  - `root` 非物件、`normalizedKey` 為空字串、或無相符屬性 → 回傳 `false`,`value` 為 `default`。
- `record SignalMapping(string CountField, string MotorField)` —— 兩個欄位都存**正規化後**的鍵。

### F2 · 訊號設定供應者(對應需求 3)

**新增** `backend/PrintingIoT.Worker/Services/SignalMappingProvider.cs`:

```csharp
public interface ISignalMappingProvider
{
    Task<SignalMapping> GetMappingAsync();   // 訊號欄位對映
    Task<int> GetDataLogIntervalSecondsAsync(); // 歷史寫入節流間隔(秒)
}
```

- 相依:`ILogger<SignalMappingProvider>`、`IConnectionMultiplexer`,以及**建構式可選參數 `TimeSpan refreshInterval`,預設 `TimeSpan.FromSeconds(60)`**(測試可傳 `TimeSpan.Zero` 驗證重讀,不必真的等 60 秒、不必加時間套件)。
- 快取:距上次讀取未滿 `refreshInterval` 直接回傳快取值;否則重讀 Redis 鍵 `config/communication`。
- 讀值規則:
  - `plc_count_signal` → `CountField`;缺值或空字串 → 預設 `DI-1`。
  - `plc_motor_signal` → `MotorField`;缺值或空字串 → 預設 `DI-0`。
  - 兩者都經 `Normalize` 後才存入 `SignalMapping`。
  - `data_log_interval`(秒)→ 非數字、`<= 0`、`> 3600` 一律回到預設 `300`。
- Redis 無鍵、JSON 壞掉、連線例外:記 `LogWarning`,沿用**上一次成功的值**(啟動即失敗則用預設值),**不得拋例外中斷訊息處理**。
- 生效時間:設定改動後最遲 `refreshInterval`(正式環境 60 秒)生效,**不需重啟服務**。

### F3 · 取樣模型與兩個解析器(對應需求 1、2、4)

**新增** `backend/PrintingIoT.Worker/Services/MachineSample.cs`:

```csharp
public record MachineSample(
    string DeviceId,
    TelemetrySource Source,
    long Count,               // 計數/長度原始值
    decimal? ProvidedSpeed,   // 來源已給的速度(模擬器);null 表示需由計數推算
    MachineStatus Status,
    DateTime TimestampUtc);
```

**新增** `backend/PrintingIoT.Worker/Services/WisePayloadParser.cs`:

```csharp
public interface IWisePayloadParser
{
    Task<MachineSample?> ParseAsync(string topic, string payload);
}
```

- deviceId:`topic.Split('/')`,長度 > 1 取 `parts[1]`,否則 `"WISE"`(維持現況)。
- 計數:以 `SignalMapping.CountField` 透過 `TryGetSignal` 取值。
  - `Number` → 取數值後 `(long)` 截斷。
  - `String` 且能以 `InvariantCulture` 解析為數值 → 同上(WISE 韌體常以字串送數值)。
  - **取不到、或型別無法轉數值(含 `true`/`false`/`null`)→ 整包回傳 `null`**(見 F4 的跳過規則)。
- 運轉狀態:以 `SignalMapping.MotorField` 取值後判定
  - `Number`:非 0 → `MachineStatus.Running`;0 → `MachineStatus.Idle`。
  - `True`/`False` → `Running`/`Idle`。
  - `String`:`"1"`/`"true"`/`"on"`(不分大小寫)→ `Running`;`"0"`/`"false"`/`"off"` → `Idle`;其他 → `Unknown`。
  - **欄位不存在、值為 `null`、或無法判讀 → `MachineStatus.Unknown`**。任何情況都不得回 `Running`。
- `ProvidedSpeed` 固定為 `null`(真機速度由 `SpeedCalculator` 推算)。
- `Source` = `TelemetrySource.Wise`;`TimestampUtc` = `DateTime.UtcNow`。
- JSON 無法解析 → 記 `LogWarning` 並回傳 `null`,不得讓例外冒出到 `HandleMessageAsync`。

**新增** `backend/PrintingIoT.Worker/Services/SimulatorPayloadParser.cs`:

```csharp
public static class SimulatorPayloadParser
{
    public static MachineSample? Parse(string payload);
}
```

- 沿用現行欄位順序:`speed` → `line_speed`(取得 `ProvidedSpeed`);`length` → `total_length` → `d1`(取得 `Count`);`status` → `status_code`(int)。
- `status` 轉 `MachineStatus`:值落在已定義的 0–4 才採用,否則 `MachineStatus.Unknown`。
- **deviceId 缺欄位或為空字串 → 使用常數 `"SIMULATOR"`,並記 `LogWarning`;不得再寫出 `"unknown"`。**
- `Source` = `TelemetrySource.Simulator`。
- 計數欄位一個都取不到 → 回傳 `null`(與真機同規則)。
- JSON 壞掉 → 記錄後回傳 `null`。

### F4 · 統一遙測管線(對應需求 1、4)

**新增** `backend/PrintingIoT.Worker/Services/TelemetryPipeline.cs`:

```csharp
public interface ITelemetryPipeline
{
    Task<MonitorData?> ProcessAsync(MachineSample sample);
}
```

相依:`ILogger<TelemetryPipeline>`、`ISpeedCalculator`、`IDeviceLockManager`、`IConnectionMultiplexer`、`IServiceScopeFactory`、`ISignalMappingProvider`。

處理順序(兩條路徑共用):

1. `sample` 為 `null` → 直接回傳 `null`(呼叫端不發布、不寫任何東西)。
2. `_lockManager.TryAcquireLock(sample.DeviceId)` 為 `false` → 回傳 `null`(維持現行搶佔規則,不改 `DeviceLockManager`)。
3. 速度:`sample.ProvidedSpeed` 有值就直接用;否則 `await _speedCalculator.CalculateSpeedAsync(sample.DeviceId, sample.Count, sample.TimestampUtc, hasQty: true)`。
   - 管線只在確定有計數時才被呼叫,因此 `hasQty` 恆為 `true`(「無計數」在 F3 就已經被擋成 `null`)。
4. 寫 Redis 快照:`StringSetAsync("factory/monitor", JSON)`,序列化選項維持 `PropertyNamingPolicy = CamelCase`。
5. 寫歷史(節流規則見 F5):符合條件時,以 `IServiceScopeFactory` 取 `PrintingContext`,新增
   `ProductionLog { DeviceId, Speed, TotalLength = sample.Count, Status = sample.Status, Source = sample.Source, Timestamp = sample.TimestampUtc }` 並 `SaveChangesAsync()`。
6. 回傳建立好的 `MonitorData`,由 `MqttWorker` 負責發布到 `factory/monitor/update`(管線不碰 MQTT,以利測試)。

資料庫寫入例外處理:`SaveChangesAsync` 丟例外時記 `LogError` 並**仍回傳 `MonitorData`**(即時畫面不因歷史寫入失敗而中斷)。

### F5 · 歷史寫入節流

合流後真機每秒一則訊息會直接灌爆 `ProductionLogs`,故管線內建節流:

- 以 `deviceId` 為鍵記錄「上次寫入時間」與「上次寫入狀態」。
- **寫入條件(任一成立即寫)**:
  1. 該 deviceId 尚無上次寫入紀錄(第一筆必寫);
  2. `sample.Status` 與上次寫入的狀態不同(狀態轉換必留紀錄);
  3. `sample.TimestampUtc - 上次寫入時間 >= data_log_interval`(由 F2 提供,預設 300 秒)。
- 條件皆不成立 → 只寫 Redis 快照與發布,不寫資料庫。

### F6 · 狀態型別統一(對應需求 2)

- `MonitorData.Status` 維持 `string`,兩條路徑一律填 `MachineStatus` 的**列舉名稱**(`Unknown` / `Running` / `Idle` / `Error` / `Maintenance`)。硬寫死的 `"1"` 消失。
- `MonitorData` 尾端新增具預設值的參數 `string Source = "unknown"`,填入 `sample.Source` 的小寫名稱(`wise` / `simulator`),序列化為 `source`。既有 5 參數呼叫端不受影響,前端忽略未知欄位。

### F7 · SpeedCalculator 基準保護(對應需求 4)

`backend/PrintingIoT.Worker/Services/SpeedCalculator.cs` 的重置偵測條件加上 `hasQty`:

```csharp
if (hasQty && state.LastCount != -1 && currentRaw < state.LastCount)
```

即:`hasQty == false` 的呼叫**完全不得改動 `LastCount` / `LastSmoothedSpeed` / `LastTime`**,回傳 0 即可。這是縱深防禦(管線已不會這樣呼叫),且可獨立測試。

### F8 · Worker 與 DI 接線

- `Worker.cs`

  - 移除兩處重複的 Redis 寫入、`MonitorData` 組裝與 DbContext 程式碼。
- `Program.cs` 註冊:`ISignalMappingProvider` / `IWisePayloadParser` / `ITelemetryPipeline` 皆為 `Singleton`(與 `ISpeedCalculator`、`IDeviceLockManager` 一致,因為都持有跨訊息狀態)。

Topic:`Advantech/{deviceId}/data`(或 `config/communication.mqtt_topic` 指定者)。Payload 範例:

## 6. Edge case 與預期行為

| 情境 | 預期行為 |
|---|---|
| payload 非合法 JSON | 記 `LogWarning`,回傳 `null`,不寫任何東西,不讓例外冒到 `HandleMessageAsync` |
| payload 是 JSON 陣列或純量而非物件 | 視同無欄位 → `null` |
| 計數欄位為字串 `"12345"` | 接受,解析為 12345(WISE 韌體常以字串送數值) |
| 計數欄位為 `true` / `null` / 非數字字串 | 視同取不到 → 整包跳過 |
| 計數欄位為小數 `123.7` | 以 `(long)` 截斷為 123(計數本質為整數脈衝) |
| 計數欄位為負數 | 照收,交由 `SpeedCalculator` 的重置偵測處理(維持既有語意) |
| 運轉訊號存在但計數缺失 | 仍整包跳過(AC-07);狀態單獨無法構成一筆有效取樣,記 `LogWarning` |
| `plc_count_signal` 與 `plc_motor_signal` 設成同一欄位 | 允許,同一值同時作為計數與運轉判定;不視為錯誤 |
| 設定值為空字串或空白 | 退回預設 `DI-1` / `DI-0` |
| 設定值含前後空白或底線(`" DI_1 "`) | 正規化後仍對映到 `di1` |
| payload 同時有 `di1` 與 `DI-1` 兩個屬性 | 取 JSON 文件順序中的第一個相符者,並記 `LogWarning` 提示欄位名稱重複 |
| Redis 無 `config/communication` 鍵 | 用預設對映,不阻斷處理 |
| 設備鎖拒絕(模擬器想搶真機的鎖) | 管線回傳 `null`,不寫快照、不寫歷史、不發布(維持既有 `DeviceLockManager` 行為,不修改該類別) |
| `SaveChangesAsync` 失敗(資料庫斷線) | 記 `LogError`,即時快照與發布照常,不重試、不阻塞下一則訊息 |
| 第一筆取樣 | 一定寫入 `ProductionLogs`(節流不吃第一筆) |
| 多台設備交錯 | 節流狀態以 deviceId 分開記錄,互不影響 |

## 8. 風險與注意事項

1. **`._*` 檔會弄壞建置**:每次 build/test 前先 `find . -name "._*" -delete`。
2. **dotnet 必須跳出沙箱**(`dangerouslyDisableSandbox: true`),否則會遇到 5 分鐘假失敗。
3. **不得執行 `git push` 或 `git commit`**,交由主流程處理。
4. **大小寫敏感**:新增檔案的 `using`/命名空間大小寫需與資料夾完全一致,否則 Docker 內建置會炸。
5. Migration 與 `PrintingContextModelSnapshot.cs` 必須同時更新,否則下次產生 migration 會出現幽靈差異。
6. 註解一律正體中文、函式級說明輸入/輸出/邏輯;禁止「接口/優化/程序/提交」等中國用語。
