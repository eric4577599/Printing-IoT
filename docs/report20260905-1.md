## 3. DoD §11 第 5 項要求明列的五件事

### 3.1 本輪**不做**資料回填遷移

後端資料庫**只有 S3 切換之後產生的新完工實績**。S3 之前寫進 `localStorage.productionHistory` 的歷史紀錄**沒有**、也不會被搬到後端(理由沿用 `docs/spec20260903-s3-v1.md` §9 第 2 項:去重規則未定、工單關聯已遺失、工廠日需重算、現場實際資料量未知)。

本輪的處理方式是**合併呈現 + 去重**(決策 3),不是遷移:

1. 同時取後端資料與本機快取,兩邊都依查詢區間過濾後合併;
2. 去重鍵為 `clientRecordId`(後端列的 `clientRecordId` vs 本機列的 `String(record.id)`),**同一筆時後端列勝出**;
3. 合併結果每筆帶 `source: 'backend' | 'local'`,明細表以「資料來源」欄與列樣式區分,CSV 匯出也帶這一欄;
4. 僅存在本機的筆數以 `localOnlyCount` 回報,畫面顯示「N 筆紀錄僅存在本機快取,尚未同步至後端」。

**這代表**:舊資料看得到,但它仍然只活在這台機器的瀏覽器裡。換一台機器、清掉瀏覽器資料,或是被 1000 筆上限擠掉,那些資料就沒了 —— 合併呈現繞過了問題,不代表問題已解。回填遷移仍在 backlog(§3.5 第 2 項)。

### 3.2 `reportUtils` 前端公式**本輪不退場**,以及 SSOT 分界

S3 §2 原則 2 曾寫「前端公式在報表改讀後端後即可退場」。**本輪不成立,`reportUtils` 全數保留,一個 export 都沒刪。**

理由:後端只提供**逐筆**率值,**沒有任何彙總端點**。而報表頁要的正是彙總。

本輪把分界寫死成一條規則:

> **單筆率值的 SSOT 在後端,彙總的 SSOT 在前端。**

| 計算 | 後端有嗎 | SSOT | 處置 |
|---|---|---|---|
| 單筆 OEE / 稼動率 / 效能 / 良率 | 有 | **後端** `PrintingIoT.Core.Services.OeeCalculator` | 後端列原樣採用,前端**絕不重算** |
| 日報彙總 `calculateDailySummary` | 無端點 | **前端** `reportUtils` | 保留 |
| 月報彙總 `calculateMonthlySummary` | 無端點 | **前端** `reportUtils` | 保留 |
| 停機原因彙總 `groupStopReasonsByReason` | 無端點 | **前端** `reportUtils` | 保留 |
| 產量加權平均 OEE `calculateWeightedAvgOEE` | 無端點 | **前端** `reportUtils` | 保留 |
| **本機列**的單筆率值 | 無(該筆後端根本沒有) | **前端** `reportUtils`(後端規則的 JS 孿生) | 以 `calculateOEE` 重算並覆寫 |

最後一列是刻意的:S3 §12.6 提醒過舊紀錄的 `oee` 是舊公式算的,合併後同一張表混兩種口徑會誤導判讀,因此本機列一律用現行公式重算,讓全表口徑一致。

**避免漂移的紀律已落實成程式碼**(不是口頭承諾):

- `frontend/src/utils/reportUtils.js` 的 `calculateOEE` 與 `calculateUtilization` 函式註解各自標明「本函式是 `PrintingIoT.Core.Services.OeeCalculator` 的 JS 孿生,規則見 `docs/spec20260903-s3-v1.md` §5.1;僅用於本機列與彙總重算,後端列的率值一律採用後端回傳值」;
- `frontend/src/utils/completionMapper.js` 檔頭與 `mapCompletionToRecord` 函式註解寫明「後端列不重算率值」,並由 AC-S4-19 的測試釘住(給一筆後端 DTO,其 `oee` 與 `calculateOEE` 由同組數字算出的結果刻意不同,合併後仍須等於後端值)。

### 3.3 `customer` / `productName` 目前靠本機快取補

後端 `ProductionCompletion` 實體與 DTO **沒有** `customer`,也**沒有** `productName`(實體註解說明刻意不對 `Order` 建導覽屬性,只留 `OrderId` 與冗餘的 `OrderNumber`)。但報表明細表第 3、5 欄與分析頁 Excel 匯出都要顯示這兩欄。

**本輪做法**(F4.3):hook 讀本機快取時順便建 `Map<clientRecordId, { customer, productName }>`,對映後端 DTO 時以 `clientRecordId` 反查補上;**查不到就顯示 `'-'`**,不猜、不留 `undefined` 或空字串。

**限制(請現場知悉)**:

- 對「**這台機器產生過的單**」100% 命中 —— 本機快取本來就存有這兩個值;
- **換一台機器**看報表,後端列的這兩欄會是 `'-'`;
- 本機快取上限 **1000 筆**,超過後最舊的會被擠掉,那些單的這兩欄也會變 `'-'`。

**且這裡有一項無法補救的情形(E-11)**:本機快取一旦超過 1000 筆被截斷,**最舊的那批資料就永久消失了**,不只是 `customer` / `productName` 補不回來 —— 若那些紀錄產生於 S3 切換之前(後端沒有該筆),整筆紀錄本身也一併消失,本輪的合併呈現救不回來,因為本輪不做遷移。這是既存事實,不是本輪引入的退步;但在後端補上這兩個欄位、或完成回填遷移之前,**現場請不要把本機快取當成長期保存**。若有必須留存的舊實績,應在資料被擠掉前自行匯出 CSV。

### 3.4 既有停機明細的起始時間仍為 `'-'`

S3 的 POST payload(`Dashboard.jsx`)送出的 `stops` 只有 `{ code, reason, durationMinutes }`,**沒有送 `startedAt`**,雖然後端 `ProductionStopRequest` 一直都有這個欄位。因此**資料庫內目前所有停機明細的 `StartedAt` 皆為 `null`**,回讀後停車起始時間欄位是空的。

**F6 已修,但只修往後的新資料**:

- `Dashboard.jsx` 的 `setStopReasons` 陣列項新增 `startedAtIso`;
- POST payload 的 `stops` 新增 `startedAt: r.startedAtIso || null`。

後端與 schema **零變更**。從本次部署之後產生的完工,停車起始時間才會有值;**在此之前落地的既有列仍是 `null`,對映層一律顯示 `'-'`**(不是 `'Invalid Date'`、不是 `undefined`,由 AC-S4-23 釘住)。既有列的回填列入 backlog(§3.5 第 5 項)。

## 4. 其他值得記一筆的實作決定

| 主題 | 決定 | 理由 |
|---|---|---|
| 分頁 | `pageSize = 500`、`page` 從 1 遞增到短頁為止,硬上限 `maxPages = 20`(= 10,000 筆) | 後端回**裸 JSON 陣列**、沒有 total / hasNext 信封,短頁是唯一可靠的終止條件。硬上限是防呆(防後端資料異常膨脹導致無限迴圈),不是省流量;觸到時 `truncated: true`,由 UI 明確標示,**不靜默截斷** |
| 降級 | API 失敗時不拋出、不白畫面,退回本機快取並把 `isDegraded` 設 `true`,顯示可辨識的警示列 | 報表是交班會看的東西,壞掉比舊嚴重。退路不選「顯示空清單」—— 那等同謊稱「這段期間沒有生產」 |
| 半份失敗 | 第 2 頁失敗(第 1 頁成功)視為**整體失敗**,走降級路徑 | 不得把只抓到一半的結果當成完整資料呈現(AC-S4-14) |
| 月報 / 停車原因自持區間 | 新增**選用** prop `onRangeChange({ startDate, endDate })`,元件在自己的區間初始化與變更時回報給 `ReportsPage` | §1.2 的坑:這兩個元件的日期區間在元件內部,父層不知道它要哪個月;不修會出現「明細有資料、月報空白」的假 bug。未傳入時行為與現況完全相同,既有測試零影響 |
| 班別篩選 | **不**下推後端,仍由前端 `filterByShift` 處理 | 避免班別切換造成不必要的重新抓取(AC-S4-06 以 `mockInstance.get` 呼叫次數斷言) |
| 停機時長格式 | 對映時必須轉成 `"MM:SS"` **字串**(秒進位到 60 時改為 `mm+1` 與 `'00'`) | `reportUtils.durationToMinutes` 只解析 `MM:SS`;塞數字會讓停機彙總全變零而**不拋例外**(靜默錯誤),由 AC-S4-22 釘住往返一致 |
| 競態 | `from` / `to` 快速切換時,只有最後一次請求的結果可寫入 state;卸載後不 `setState` | E-14、E-15 |
