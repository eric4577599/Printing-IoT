# spec20260910-1 · MM 維護模組與主系統的整合(機台綁定 + PLC 訊號繼承)

> 2026-09-10 · 依 Eric 指示:「`mms.ericchh.work` 可以單獨運作;如果由 `priiot.ericchh.work`
> 進入則自動綁定相同機器,接收(或說繼承)相同的 PLC 訊息。」
> 本文只定規格,**尚未實作**。跨 `Printing-IoT` 與 `MM` 兩個 repo。

---

## 1. 目標與非目標

### 目標

| # | 目標 |
|---|---|
| G1 | MM **維持可獨立運作** —— 直接開 `mms.ericchh.work` 的行為與現在完全相同 |
| G2 | 由主系統進入時,MM **自動綁定同一台機器**,畫面明確標示綁在哪一台 |
| G3 | MM **自行取得**與主系統相同的 PLC 訊息(並列訂閱,不經主系統轉手) |
| G4 | PLC 訊息在 MM 的三個用途:①運轉時數觸發保養 ②台帳顯示即時狀態 ③停機自動開維修單 |

### 非目標

- **不把保養/零件功能搬回主系統**。主系統只多一個外連入口,不多任何保養邏輯。
- **不做 SSO**。兩套帳號各自獨立,由主系統進入 MM 仍需 MM 的登入(見 §9 O-3)。
- **不由主系統代轉運轉資料**。這與既有設計形狀相牴觸 → `[[printingiot-mm-parallel-signal-source]]`。

## 2. 現況(實查,非文件自述)

### 2.1 兩邊都活著,但彼此完全不認識

| 項目 | 事實 |
|---|---|
| MM 對外 | `https://mms.ericchh.work` 可用(實測 200,登入畫面正常) |
| MM 容器 | `mm-mms-frontend-1` :5301、`mm-mms-backend-1` :5300、`mm-postgres-1` **127.0.0.1**:5434 |
| 對外方式 | **掛在 Printing IoT 的 cloudflared 上**,靠 docker 網路別名轉發(`MM/docker-compose.yml:42, :63`) |
| 主系統前端 | **沒有任何 MM 入口**,全域搜尋 `5301` / `mms` / `維護模組` 零命中 |
| MM 後端 | **完全沒有 MQTT**,`grep -rn "Mqtt" backend` 零命中 |

### 2.2 MM 的資料模型缺三塊地基

這是本案最要緊的發現 —— **PLC 訊息就算進來了,現在也沒有地方可以掛**:

| 缺口 | 現況 |
|---|---|
| **排程沒綁設備** | `MaintenanceSchedule` 只有 `Name / Description / Frequency / IsPartRequired / IsActive / CreatedAt / ChecklistTemplateId`,**沒有 `EquipmentId`** |
| **紀錄沒綁設備** | `MaintenanceRecord` 有 `ScheduleId` / `PartId`,**同樣沒有 `EquipmentId`** |
| **頻率只有日曆型** | `FrequencyType = Daily / Weekly / Monthly / AdHoc`,**沒有「運轉時數」型** |

`Equipment` 主檔本身是完整的(`MachineCode` 唯一鍵、`Status`、`Location` 等),
但**沒有任何東西關聯到它** —— 台帳是孤島。

### 2.3 主系統的 PLC 訊號長什麼樣

| 項目 | 事實 |
|---|---|
| Broker | Mosquitto,`:1884`(WS `:9001`) |
| 主題 | `Advantech/+/data`(真機)、`factory/machine/update`(模擬器) |
| 裝置代號 | 取自 **topic 第 2 段**:`Advantech/{deviceId}/data`(`WisePayloadParser.cs:44`) |
| 計數 | 依設定的 `CountField` 取值;數字或可解析的數值字串,小數截斷 |
| 狀態 | 依設定的 `MotorField`:**非 0 → `Running`,0 → `Idle`**,取不到 → `Unknown`(`WisePayloadParser.cs:141`) |
| 狀態列舉 | `Unknown=0 / Running=1 / Idle=2 / Error=3 / Maintenance=4` |
| 寫入節流 | 狀態改變立即寫;否則依 `data_log_interval`(1–3600 秒,現為 6 秒) |

**要更正一個常見誤解**:畫面說明寫「RUN ↔ STOP ↔ JOG」,但**程式裡沒有 JOG**,
只有二值判定(馬達訊號非 0 / 0)。JOG 是說明文字的遺留,規格不採信它。

## 3. 核心問題:這條鏈上有三個識別碼,彼此不認識

| 識別碼 | 住在哪 | 目前的值 | 誰在用 |
|---|---|---|---|
| **MQTT `deviceId`** | topic `Advantech/{deviceId}/data` | 由 WISE 硬體決定 | Worker 寫 `ProductionLog.DeviceId` |
| **主系統 `machine_id`** | 通訊設定(`SettingsService.cs:41`) | 現場已改為 `M20`(預設 `MACHINE_01`) | 生產日誌顯示 |
| **MM `Equipment.MachineCode`** | MmsDB,唯一鍵 | 由 MM 的台帳自行維護 | 保養/維修關聯 |

**主系統的 `machine_id` 與 MQTT 的 `deviceId` 是兩回事**,現在沒有任何地方把它們對起來;
MM 的 `MachineCode` 更是第三套。

### 決策 D1:以 `MachineCode` 為主鍵,在 MM 側維護對映

- MM 的 `Equipment` 增加 **`MqttDeviceId`** 欄位(可空,唯一 filtered index)。
- MM 訂到訊息時,以 topic 的 `deviceId` 查 `Equipment.MqttDeviceId` 找到設備。
- **對不到的 deviceId 一律丟棄並記一筆 warning**,不自動建立設備 ——
  自動建檔會讓打錯字的裝置在台帳裡長出殭屍設備。
- 主系統傳過來的是 **`machine_id`**(即 `MachineCode`),不是 `deviceId` ——
  主系統本來就不知道 MM 的內部鍵,傳它自己的機台識別碼即可。

> **前提**:現場需確保主系統的 `machine_id` 與 MM 台帳的 `MachineCode` 用同一組編碼。
> 目前主系統是 `M20`,MM 台帳有沒有這一台**尚未確認** → O-1。

## 4. 資料流

```
                    Mosquitto (:1884)
                    Advantech/{deviceId}/data
                       │
        ┌──────────────┴──────────────┐
        │                             │
   Printing IoT Worker           MM MqttIngestor      ← 並列訂閱,不互相轉手
        │                             │
   ProductionLogs                MachineRuntime
   (生產實績)                     (運轉時數/狀態/停機事件)
```

**兩邊各自訂閱同一個 broker。** MM 不打主系統的 API,主系統也不推資料給 MM ——
任一邊掛掉不影響另一邊,這是「真分離」的具體含意。

代價要說清楚:**同一份訊息會被解析兩次**,兩邊的解析邏輯可能漂移。
緩解方式見 §7 AC-09(黃金向量),做法沿用 S8 的 `oee-golden-vectors.json`。

## 5. Schema 變更(全部在 MM,主系統不動資料庫)

### 5.1 `Equipment`

```
+ MqttDeviceId : string?  (MaxLength 100, unique filtered index where not null)
```

### 5.2 `MaintenanceSchedule`

```
+ EquipmentId       : Guid?   (FK → Equipment, Restrict)
+ RuntimeHours      : int?    (FrequencyType.RuntimeHours 時必填,> 0)
  FrequencyType     : 新增 RuntimeHours 列舉值
```

**`EquipmentId` 可空**是為了不破壞既有資料(現有排程沒有設備)。
但 `FrequencyType.RuntimeHours` 的排程**必須有 `EquipmentId`** —— 時數是每台各自累積的。

### 5.3 `MaintenanceRecord`

```
+ EquipmentId : Guid?  (FK → Equipment, Restrict)
```

### 5.4 新表 `MachineRuntime`(每台一列,MM 自行累積)

| 欄位 | 型別 | 說明 |
|---|---|---|
| `EquipmentId` | Guid (PK, FK) | 一台一列 |
| `Status` | int | 最近一次判定的狀態(對齊主系統列舉) |
| `StatusChangedAtUtc` | DateTime | 本次狀態的起始時刻 |
| `LastSeenUtc` | DateTime | 最後收到訊息的時刻 |
| `RunningSecondsTotal` | long | **累積運轉秒數**(只在 Running 期間累加) |
| `RunningSecondsAtLastMaintenance` | long | 最近一次保養完成時的讀數,用來算「距上次保養跑了多久」 |

**累積規則**:每收到一則訊息,若上一狀態為 `Running`,把 `now - StatusChangedAtUtc` 加進
`RunningSecondsTotal`。**訊息斷流時不補算** —— 斷線期間機器有沒有在跑無從得知,
寧可少算也不要虛報時數而提早觸發保養。

> 這條規則的代價:長時間斷線會低估時數。以 `LastSeenUtc` 在畫面上標示「資料過期」,
> 讓人看得到而不是默默偏差。

### 5.5 新表 `MachineStopEvent`(停機事件,供自動開單與追溯)

| 欄位 | 說明 |
|---|---|
| `Id` / `EquipmentId` | |
| `StartedAtUtc` / `EndedAtUtc?` | 停機區間;未結束時 `EndedAtUtc` 為 null |
| `DurationSeconds?` | 結束時回填 |
| `MaintenanceRecordId?` | 若已自動開單,指向那張單 |

## 6. 三個用途的規則

### 6.1 運轉時數觸發保養(G4-①)

- `FrequencyType.RuntimeHours` + `RuntimeHours = N` 的排程,
  當 `RunningSecondsTotal - RunningSecondsAtLastMaintenance >= N * 3600` 即**到期**。
- 到期只**標示為到期**並列入待辦,**不自動建立保養紀錄** ——
  保養是人去做的事,系統自動生一張「已完成」的單毫無意義。
- 保養紀錄標記完成時,把該設備當下的 `RunningSecondsTotal` 寫入
  `RunningSecondsAtLastMaintenance`,計時歸零。

### 6.2 台帳顯示即時狀態(G4-②)

- 設備台帳每列顯示:狀態徽章(運轉 / 停止 / 未知)、`LastSeenUtc` 的相對時間、累積運轉時數。
- **`LastSeenUtc` 超過門檻(預設 5 分鐘)一律顯示「資料過期」** 而不是沿用最後狀態 ——
  沿用會讓一台早就斷線的機器在畫面上永遠「運轉中」。
- 即時值走輪詢(MM 前端目前只有 axios,不引入 WebSocket → 不主動加相依套件)。
  輪詢間隔預設 30 秒,可設定。

### 6.3 停機自動開維修單(G4-③)

**這是最容易做壞的一項** —— 門檻設錯會每天長出一堆垃圾單。規則:

- 進入非 `Running` 狀態即開一筆 `MachineStopEvent`(不開單)。
- **持續超過門檻 T 才建立維修單**(`MaintenanceType` 待定,見 O-2),預設 **T = 30 分鐘**。
- 同一個停機事件**只開一張單**(以 `MachineStopEvent.MaintenanceRecordId` 冪等)。
- 停機期間該設備已有未結案的自動單時**不再開第二張**。
- 自動開的單必須**明確標示為系統自動產生**,並記錄觸發時的停機起訖與時長。
- **可停用**:`MaintenanceSetting` 增加開關,預設 **關閉** ——
  新機制預設關閉,由現場確認門檻合理後才打開。

## 7. 入口與綁定

### 7.1 主系統側

- 導覽列新增「維護 (MM)」外連,**開新分頁**。
- 目標網址**從設定讀,不寫死**(不同廠的 MM 網址不同):
  通訊設定新增 `mm_base_url`,空值時**不顯示該入口**。
- 帶參數:`?machine=<machine_id>`(即 `MachineCode`),外加 `from=priiot` 供 MM 判斷來源。
- 權限:**ADMIN / ENGINEER / SUPERVISOR 可見,OPERATOR 不可見**(與 S14 文件分權同一組判準)。

### 7.2 MM 側

- 讀 `?machine=`,以 `MachineCode` 查設備:
  - **查到** → 全站鎖定該設備的視角,頂部顯示「已綁定機台 M20(來自 Printing IoT)」與解除按鈕。
  - **查不到** → **不靜默忽略**,顯示「主系統傳來的機台代號 `X` 在台帳中不存在」,
    並照常進入未綁定的正常畫面(G1 不得被破壞)。
- 綁定狀態存在該分頁的 sessionStorage,**不寫使用者偏好** —— 換一台終端不該繼承別人的綁定。
- 直接開 `mms.ericchh.work`(無參數)時,行為與現在**完全相同**。

## 11. 追加:MM 資料庫是空的(2026-09-10 實查)

寫這份規格時順手查了 O-1,結果比預期根本:

| 資料表 | 列數 |
|---|---|
| `Equipments`(設備台帳) | **0** |
| `MaintenanceSchedules`(保養排程) | **0** |
| `MaintenanceRecords`(保養紀錄) | **0** |
| `SpareParts`(備品零件) | **0** |
| `Parts`(零件主檔) | **0** |
| `AppUsers` | 1 |

**MM 容器已運行兩週,但沒有任何人建過一筆資料。**

這改變了分期的前提:

- §10 的 **P1(入口 + 綁定)照樣可以先做**,但**現在做完會綁不到任何東西** ——
  帶 `?machine=M20` 進去必然走 AC-03 的「台帳中不存在」那條路。
  P1 的價值在於路鋪好,不在於當下可用。
- **真正的第零期是「把設備建進台帳」**,而那是現場的資料建置工作,不是程式工作。
  至少要有這台印刷機本身,`MachineCode` 與主系統的 `machine_id`(現為 `M20`)一致。
- P3 之後的所有時數累積、保養到期、停機開單,**全部掛在設備台帳上** ——
  台帳空著,那些機制寫得再對也不會有任何輸出。

**建議順序改為:P0 建台帳(現場) → P1 入口綁定 → P2 補地基 → P3~P5。**

順帶一則觀察,不在本規格範圍但值得記:S9 的稽核指出主系統的 `ProductionLogs` /
`ProductionCompletions` / `Products` 在正式庫上都是 0 列。加上這次查到的 MM 全空 ——
**兩套系統目前都只有「上線」,還沒有「投用」。**
規格與實作的正確性到目前為止全部由測試背書,尚未由真實資料背書。
