# 10 月份生產紀錄模擬(2026-11-15)

## 目的
Eric 要求模擬 2026 年 10 月一整個月的生產紀錄,用來檢視報告頁(日報、月報、停機原因、分析)是否正常。

## 做了什麼
- 以作業員 OP1 的登入身分,透過 `POST /api/production/completions` 逐筆送出 **294 筆完工實績**(`ClientRecordId` 前綴 `SIM202610-`,訂單號 `SIM10001` 起,設備 `MACHINE_01`)。
  走真實 API,所以工廠日、四個 OEE 值都是後端程式算的,不是直接寫資料庫。
- 固定亂數種子(20261001),內容可重現。
- 日曆:10/1–10/31,週日休、10/10 國慶休、10/17 歲修休 → **25 個生產日**;週一到五日夜兩班(日班 A 08:00–18:00、夜班 B 20:00–04:00),週六只有日班。
- 刻意放進的情境:夜班跨午夜(本地日期已過 0 點,工廠日仍屬前一日,共 64 筆);10/21 異常日(車速低、停機多且偏機械故障、不良率約 6%);8% 短缺單(含短缺原因);15% 零停機單;各單良品落在目標的 85%–103%。
- 口徑:`StopTimeMinutes` 含準備時間(與既有資料一致),停機明細只放非計畫停機。

## 對帳結果(全部由我親自實跑)
| 項目 | 結果 |
|---|---|
| 逐筆:後端回傳的工廠日、稼動、效能、良率、OEE、不良總數、停機次數 vs 獨立重算 | 294 筆 **0 不一致** |
| 月報 25 個每日列(筆數、良品、不良、運轉、停機時間) vs 預期 | **0 不一致**,無缺日 |
| 月報/日彙總總計:良品 2,680,959、不良 55,886、目標 2,664,000、294 筆 | 與預期完全相等 |
| 停機原因彙總 6 類的次數與總分鐘 | 與預期完全相等 |
| 跨午夜 64 筆的工廠日 | 全部落在前一日,符合日界 08:00 |

## 觀察(非本次造成,未修改)
同一份資料,**日彙總與月報給的稼動率、OEE 不同**:

| | 日彙總 `/summary/daily` | 月報總計 `/summary/monthly` |
|---|---|---|
| 稼動率 | 57.0%(運轉 ÷ (運轉+停機),**不扣準備時間**) | 74.3%(運轉 ÷ (運轉+停機−準備)) |
| OEE | 79.7%(逐筆 OEE 依產量加權平均,規則 6) | 72.8%(用整月合計重算) |

後端是照前端 `reportUtils.js` 的既有做法對齊(日彙總 386 行不帶準備時間,月報 491 行帶),所以是**長期存在的口徑差異**,不是回歸。使用者在日報與月報看到不同的稼動率會疑惑,是否統一口徑需要 Eric 決定。

## 清除模擬資料
資料以 `ClientRecordId LIKE 'SIM202610-%'` 標記。**先確認再執行**(不可復原):
```sql
-- docker compose exec -T postgres psql -U postgres -d FlexoDB
DELETE FROM "ProductionDefects" WHERE "CompletionId" IN (SELECT "Id" FROM "ProductionCompletions" WHERE "ClientRecordId" LIKE 'SIM202610-%');
DELETE FROM "ProductionStops"   WHERE "CompletionId" IN (SELECT "Id" FROM "ProductionCompletions" WHERE "ClientRecordId" LIKE 'SIM202610-%');
DELETE FROM "ProductionCompletions" WHERE "ClientRecordId" LIKE 'SIM202610-%';
```
