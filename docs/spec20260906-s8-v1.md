# S8 規格 — 後端彙總端點(收斂 OEE 的單一事實來源)

> 2026-09-06 · 分支 `main` · 前置為 S3(`OeeCalculator` 落地)與 S4(前端四頁改讀後端)

## 0. 這一趟要解決什麼

handoff Next Step 第 10 項:**同一組 OEE / 稼動率公式,現在有兩份實作**。

| 實作 | 位置 | 誰在用 |
|---|---|---|
| C# | `backend/PrintingIoT.Core/Services/OeeCalculator.cs` | 落地完工實績時算出每筆的四個率值,存進 `ProductionCompletions` |
| JS | `frontend/src/utils/reportUtils.js` | 日報、月報、停機分析三個檢視,**在瀏覽器裡重算** |

S4 已經把「逐筆資料」的事實來源收斂到後端,但**彙總**沒有 —— 因為後端只有逐筆率值、
沒有任何彙總端點,報表要的「當日加權平均 OEE」「當月每日一列」「停機原因排行」
只能在前端拿逐筆資料自己算。

`OeeCalculator.cs` 的註解已經明寫「前端 `calculateOEE` 必須依同一份規則表實作」——
**這句話就是漂移風險的自白**:兩份程式碼靠人記得同步,沒有任何機制強制。
規則 3 用良品數當分子這種反直覺的口徑,只要有人改了一邊,報表數字就會分岔,
而且**不會有任何測試變紅**,因為兩邊各自對著自己的期望值測。

### 0.1 這一趟的邊界

**做**:後端補三組彙總查詢端點,並讓 C# 與 JS 的逐筆公式由**共用黃金測試向量**釘死。

**不做**:不刪除 `reportUtils` 的公式。原因見 §4 —— 前端仍需為「僅存在本機的舊實績」保留計算能力,
在 handoff 第 9 項(舊實績回填)完成之前,刪掉等於讓那些資料從報表上消失。
本趟把它從「事實來源」降格為「本機資料的降級路徑」,並用測試釘住兩邊同義。

## 1. 三組彙總端點

全部掛在既有的 `ProductionController`(`api/production`),沿用 `[Authorize]` 與工廠日語意。

### 1.1 `GET /api/production/summary/daily`

| 參數 | 型別 | 說明 |
|---|---|---|
| `from` / `to` | `yyyy-MM-dd` | 工廠日區間,含端點;可省略 |
| `shift` | string | 班別過濾,可省略;比對 `Shift` 欄位,**不分大小寫** |

回應對齊前端 `calculateDailySummary` 的輸出形狀:

```jsonc
{
  "totalOrders": 12, "totalTarget": 48000, "totalGood": 46310, "totalDefect": 890,
  "avgYieldRate": 98.1,          // 以區間總良品 / 總產出重算,不是逐筆平均
  "avgAchievementRate": 96.5,    // 總良品 / 總目標
  "totalRunTime": 1310.0, "totalStopTime": 214.0, "totalPrepTime": 96.0,
  "totalStopCount": 19,
  "avgOEE": 71.4,                // 依產量加權(規則 6),不是算術平均
  "utilization": 84.9
}
```

**空區間回全 0 的物件,不回 404** —— 「這段時間沒有生產」是一個合法答案,不是查無資源。

### 1.2 `GET /api/production/summary/monthly`

參數同上。回應 `{ dailyRows: [...], totals: {...} }`,對齊 `calculateMonthlySummary`。

`dailyRows` 每列是一個工廠日,依日期遞增排序,欄位:
`date` / `orderCount` / `totalQty` / `goodQty` / `defectQty` / `targetQty` /
`yieldRate` / `avgSpeed` / `runTime` / `stopTime` / `prepTime` / `utilizationRate` / `oee`。

**關鍵不變量**:每日的 `oee` 是**拿當日彙總數據重算**,不是把當日各單的 OEE 平均掉;
`totals.oee` 同理,拿整月彙總重算。這是 S3 GAP-05 的裁決,兩邊必須一致。

### 1.3 `GET /api/production/summary/stop-reasons`

參數同上。回應依 `count` 遞減的陣列:

```jsonc
[{ "reason": "換版", "code": "ST01", "count": 34, "totalDurationMinutes": 412.0 }]
```

**刻意不回下鑽明細**。前端停機分析的展開列要顯示「哪幾張單」,那是逐筆資料,
已經有 `GET /api/production/completions` 可以取;彙總端點回下鑽明細等於把整段區間的
逐筆資料再傳一次,而且會讓回應大小無上限。前端改為「彙總看這支、展開時從既有的逐筆清單篩」。

`reason` 為空字串的停機列歸到 **`未分類`**(與前端 `groupStopReasonsByReason` 的既有行為一致)。

### 1.4 三支共同的規則

- **算術一律在資料庫外做**。用 EF 取回區間內的完工列(含 `Stops`)後在記憶體彙總,
  再交給 `OeeCalculator`。**不寫 SQL 版的公式** —— 那會變成第三份實作。
- **不分頁**。彙總的回應大小與區間內的資料量無關(停機原因除外,但原因主檔是有限集合)。
  取資料時仍需防爆:區間內完工列超過 `Production:SummaryMaxRows`(預設 20000)時
  回 **400** 並說明請縮小區間,**不靜默截斷**(沿用 S4 「不可靜默截斷」的紀律)。
- 日期格式不合法 → 400,訊息與既有 `GetCompletions` 一致。

## 2. 用共用黃金向量釘死兩份實作

端點補完之後,C# 與 JS 的逐筆公式仍然各活各的。真正消滅漂移的是這一項:

新增 `tests/fixtures/oee-golden-vectors.json`(repo 根,**兩邊共用同一個檔**),
每筆是一組輸入與期望的四個率值:

```jsonc
[{ "name": "準備時間從分母扣掉",
   "input": { "runTime": 400, "stopTime": 80, "prepTime": 30, "goodQty": 9500, "defectQty": 500, "targetQty": 10000 },
   "expected": { "availability": 88.9, "performance": 95.0, "quality": 95.0, "oee": 80.2 } }]
```

- C# 側:`OeeCalculatorGoldenVectorTests` 讀該檔,逐筆比對 `OeeCalculator.Calculate`。
- JS 側:`reportUtils.golden.test.js` 讀**同一個檔**,逐筆比對 `calculateOEE`。

**期望值由 C# 端產生後寫入檔案**(C# 是權威實作),JS 端只驗證自己算得出同樣的數字。
任何一邊改了公式而沒改另一邊,**該邊的測試立刻紅**。這是本趟真正的交付價值 ——
端點只是讓前端有得用,黃金向量才是讓漂移不可能再發生的那個機制。

向量必須涵蓋:分母為零(load / target / produced 三處各一)、超產封頂、負值夾零、
準備時間大於運轉加停機(load 夾到 0)、四捨五入邊界(x.x5)。

## 3. 前端改讀後端彙總

三個檢視改用新端點,`reportUtils` 的對應函式降為降級路徑:

| 檢視 | 原本 | 改為 |
|---|---|---|
| `DailyReportView` / `ReportsPage` | `calculateDailySummary(filteredRecords)` | `GET summary/daily` |
| `MonthlyReportView` | `calculateMonthlySummary(filtered)` | `GET summary/monthly` |
| `StopReasonView` | `groupStopReasonsByReason(filtered)` | `GET summary/stop-reasons` + 展開時從逐筆清單篩 |

沿用 S4 的三條紀律:API 失敗 → 用本機算的結果渲染但 `isDegraded` 要看得見;
不靜默截斷;不讓使用者以為資料遺失。

## 4. 這一趟不解決的:僅存在本機的舊實績

**這是本規格最重要的一段,不可略過。**

S4 的現況是「後端紀錄 + localStorage 僅存本機的舊單」合併呈現,並在畫面上標出
`localOnlyCount`。後端彙總端點**只看得到後端的資料** —— 對於還有本機舊單的瀏覽器,
換讀後端彙總會讓那些單**從彙總數字裡消失**,而逐筆清單裡卻還看得到它們。
數字對不上明細,比數字略有漂移更糟。

因此 §3 的切換必須帶一個條件:

> **當區間內 `localOnlyCount > 0` 時,不採用後端彙總**,改用前端現行計算(涵蓋兩個來源),
> 並在畫面標示「本區間有 N 筆僅存在本機,彙總以本機計算」。
> `localOnlyCount === 0` 時才採用後端彙總,並標示資料來源為後端。

這是刻意的取捨:**寧可在少數瀏覽器上維持舊路徑,也不要讓彙總與明細互相矛盾**。
handoff 第 9 項(舊實績回填後端)完成之後,這個分支才能拆掉,`reportUtils` 的彙總函式
也才真的能退場。本規格 §2 的黃金向量在那之前就已經把漂移風險關掉了,不必等。

## 5. 驗收準則

### 5.1 後端

| AC | 驗什麼 |
|---|---|
| AC-01 | `summary/daily` 空區間回全 0 物件與 200,不是 404 |
| AC-02 | `summary/daily` 的 `avgOEE` 等於 `OeeCalculator.WeightedAverageOee`,**不等於**算術平均(需造一組兩者會分岔的資料) |
| AC-03 | `summary/daily` 的 `avgYieldRate` 以區間總量重算,不等於逐筆良率的平均 |
| AC-04 | `shift` 過濾不分大小寫(`a` 與 `A` 取到同一組) |
| AC-05 | `summary/monthly` 的 `dailyRows` 依日期遞增,每列 `oee` 由當日彙總重算(與「當日各單 OEE 平均」不同) |
| AC-06 | `summary/monthly` 的 `totals.oee` 由整月彙總重算 |
| AC-07 | `summary/stop-reasons` 依 `count` 遞減,`reason` 空字串歸入 `未分類` |
| AC-08 | 三支端點日期格式不合法皆回 400 |

## 6. 明確不納入

| 不做 | 理由 |
|---|---|
| 刪除 `reportUtils` 的彙總函式 | §4 —— 本機舊單還需要它,回填完成前刪掉等於讓資料消失 |
| SQL 版的彙總公式 | 會變成第三份實作,漂移風險加倍 |
| 彙總端點回下鑽明細 | §1.3 —— 回應大小無上限,且逐筆資料已有端點 |
| 彙總結果快取 | 還沒有證據顯示查詢慢;先做對再做快 |
| 實績修改端點 | 另一條 backlog(S4 spec §8 第 4 項),與本趟無關 |
