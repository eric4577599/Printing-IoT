## 1. 背景與關鍵發現

Phase 2 原以為「接一支既有 `POST /api/orders/reorder`」即可,但深入後發現前後端**根本沒連動**:

- 前端排程 `orders` 100% 來自 **localStorage**,id 為 `ord_<ts>` / `placeholder` 字串,**從不呼叫** `GET /api/orders`,新增也不 `POST`。
- 後端 `Order` schema 比前端**瘦很多**:BoxDiagram 需要的約 25 個規格欄位(`boxLen/boxWid/boxHgt/dim*/l*/w*/h*/dieCutType/special`…)後端**沒有 typed 欄**。
- 訂單狀態不只由 4 個 context helper 異動,還被 **Dashboard 完工/佇列推進與 `useFKeyHandler` 直接 `setOrders`**(6+ 處)。

因此「真正的後端持久化」= 整條訂單同步層,而非一支 API。經與 Eric 兩輪確認,選定:
1. **後端加 `SpecJson` 欄(改 DB)** 保存前端完整規格,不遺失 BoxDiagram 欄位。
2. **全量鏡像同步**:前端每次 `orders` 變動,debounce 上傳整份排程;後端 upsert + 刪除清單外的列。此單一整合點涵蓋拖拉、完工、佇列推進、F 鍵全部,免逐一改 Dashboard。

## 3. 關鍵設計

1. **後端擁有「身分 + 排序 + 核心欄位」,SpecJson 保存完整前端 payload**;`fromBackendOrder` 以 SpecJson 還原 BoxDiagram 規格,typed 欄覆蓋核心欄位。
2. **GUID 身分**:前端訂單 id 改用 `crypto.randomUUID()`;「身分正規化」effect 保證任何路徑新增的訂單都有 GUID,讓鏡像 upsert 穩定命中、不重複新建。
3. **空清單保護**:`SyncScheduleAsync` 收到空清單「不動作」直接回傳現況,避免暫態把整份排程清空。
4. **載入前不同步**:`ordersLoaded` 旗標確保「先從後端載入」再開始鏡像,避免用 localStorage 初值覆寫後端。
5. **離線容錯**:後端無法連線時保留 localStorage 初值;localStorage 仍作為離線鏡像持續寫入。
6. **首次匯入**:後端為空但本地有訂單時,把現有 localStorage 排程(補 GUID)一次性 `sync` 上後端,避免切換來源後排程「像被清空」。
