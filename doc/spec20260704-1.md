## 1. 決策

主系統 Smart Parts 的「**零件管理**(Parts / Suppliers / SupplierParts)」**移出主系統、併入 MM**,
與既有「**備品零件**(SpareParts)」在 MM 內**並立為兩個重要元件** — 不合併、不混用。

對照 0617 規劃書三方案,此為**修正版方案 C(C′)**:

| | 方案 C(0617 原案) | 方案 C′(本次拍板) |
|---|---|---|
| 零件管理去處 | 獨立成第三個外掛 | 併入 MM,成為 MM 第二元件 |
| 外掛數量 | 2(MM + Parts) | 1(MM 一站式) |
| 部署成本 | 多一組後端+DB+tunnel | 沿用 MM 既有三容器,零新增 |
| 商業包裝 | 兩個加值品項分開賣 | 一個「設備資產管理」品項 |

MM 定位由「保養維修外掛」升級為「**設備資產管理外掛**」(設備/保養/維修/備品/採購零件)。
分離原則不變:後端互不引用,MM 自帶 MmsDB。

**兩元件並立的理由**:備品零件是保養的**耗用庫存**(維修紀錄自動扣庫存),零件管理是**採購主檔**
(零件×供應商×報價)。生命週期不同,合併會重演 0617 §4 的命名地雷。

## 2. 兩元件邊界(命名/UI/API 準繩)

| | 元件一:備品零件 | 元件二:零件管理 |
|---|---|---|
| 回答的問題 | 保養用什麼?還剩多少? | 跟誰買?規格價格為何? |
| 資料表 | `SpareParts` | `Parts`、`Suppliers`、`SupplierParts` |
| 核心行為 | 自動扣庫存、最低庫存警示 | 主檔 CRUD、供應關聯與報價 |
| UI 頁籤(建議) | 🔩 備品庫存(由「零件庫存」更名) | 📦 零件主檔、🏢 供應商 |
| API 路由(建議) | `/api/parts`(MM 既有,不動) | `/api/v1/parts`、`/api/v1/suppliers`、`/api/v1/supplier-parts` |

**路由衝突**:MM `/api/parts` 已被備品佔用;零件管理沿用主系統 `/api/v1/*` 前綴,
路由不撞且 sm-frontend API 呼叫幾乎零改。

## 3. 遷移盤點

| 位置 | 處置 |
|---|---|
| `PrintingIoT.Core/Entities/Parts/`(Part/Supplier/SupplierPart) | 移植到 MM 後端 |
| `PrintingIoT.API/Controllers/PartsController.cs`(`api/v1/parts`) | 移植後移除 |
| `PrintingIoT.Infrastructure/Services/PartService.cs` + Core 介面/DTO | 移植後移除 |
| `PrintingIoT.Tests/PartServiceTests.cs` | 隨服務移植 |
| FlexoDB `Parts`/`Suppliers`/`SupplierParts` | 搬 MmsDB;主系統 `RemoveSmartPartsModule` migration drop(Down 可還原,比照 `7a839f4`) |
| `smart-parts-frontend/`(:5100) | 整併進 MM 前端;容器退役 |
| `backend/SmartParts.API/` | **Phase 5 殘留舊專案,直接刪除**(不在任何 compose) |

**前端整併(建議案)**:MM 前端加「零件主檔/供應商」頁籤;認證改走 MM 體系;
`smartparts.ericchh.work` 移除或 301 → `mms.ericchh.work`。
替代案(保留 sm-frontend 僅改 API 指向)不建議 — 長期兩套前端兩條 tunnel,違背一站式定位。

**部署變化**:主系統減 sm-frontend 容器;MM 容器不變;FlexoDB 純監控生產;MmsDB = 保養四表 + 零件三表;
tunnel 必補 `mms.ericchh.work`。
