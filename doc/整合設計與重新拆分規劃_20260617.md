## 1. 系統全景（整合後的單一藍圖）

整個產品線實際上是**三個關注點（concern）**，建議用「一個核心 ＋ 一個內建模組 ＋ 一個選配外掛」來描述：

```
┌──────────────────────────────────────────────────────────────┐
│  PriIoT 產品線                                                 │
│                                                               │
│  ┌─────────────────────────────┐   ┌───────────────────────┐ │
│  │ A. Printing IoT 主系統        │   │ C. MM 維護保養外掛     │ │
│  │   （核心，本 repo）           │   │   （選配，獨立 repo）  │ │
│  │                             │   │                       │ │
│  │  A1 即時監控/排程/報表       │   │  保養排程 Schedules    │ │
│  │  A2 Smart Parts 零件管理     │   │  備品零件 SpareParts   │ │
│  │     （內建，資料在 FlexoDB） │   │  保養紀錄 Records      │ │
│  │                             │   │  ERP 級聯設定 Settings │ │
│  │  backend-api  :5200         │   │  mms-backend  :5300    │ │
│  │  frontend     :5600         │   │  mms-frontend :5301    │ │
│  │  sm-frontend  :5100         │   │  MmsDB (postgres)     │ │
│  │  FlexoDB (postgres :5433)   │   │                       │ │
│  └─────────────────────────────┘   └───────────────────────┘ │
│             │                                  ▲              │
│             │  無後端互相依賴；MM 為真分離     │              │
│             └── 前端可直呼 MM API（選配 widget）┘              │
│                                                               │
│  共用：cloudflared tunnel、JWT 認證、Docker Compose 編排       │
└──────────────────────────────────────────────────────────────┘
```

三塊的定位差異是這次重新拆分的關鍵，必須先講清楚：

**A1 — 印刷機台即時監控（核心中的核心）**
即時 Dashboard（F-Key 操作邏輯）、訂單排程 CRUD、生產報表分析、五語系（繁中/簡中/英/越/泰）。資料走 MQTT（Worker）＋ Polling（前端 `useRealtimeData`）。這是產品的不可分割本體。

**A2 — Smart Parts 零件管理（內建模組）**
零件主檔 `Parts`、供應商 `Suppliers`、供應關聯 `SupplierParts`、庫存。**已併入主 backend-api，資料在 FlexoDB**，前端為獨立 `sm-frontend`（:5100，`smartparts.ericchh.work`）。注意：這裡的 `Part/SupplierPart` 與 MM 的 `SparePart` 是**兩套不同的東西**（見 §4 易混淆對照）。

**C — 維護保養 MM（選配外掛，先前從主系統移出的就是這塊）**
保養排程、備品零件、保養／維修紀錄（建立時自動扣庫存）、ERP 級聯設定（InheritErp / LocalOverride）。**完全獨立**：自帶 MmsDB、自帶後端（:5300）與前端（:5301），透過 cloudflared 以 `mms-api.ericchh.work` 對外。主系統後端**不引用** MM 程式碼，僅前端可選擇性直呼其 API。

## 3. 整合資料模型

### 3.1 主系統 FlexoDB（核心 ＋ 零件，已無保養表）

- 監控/排程/生產：`Users`、`Roles`、`UserRoles`、`Machines`、`Alarms`、`Orders`/排程、生產履歷、產品檔（含箱型 RSC/HSC、楞型 A/B/AB）。
- Smart Parts：`Parts`、`Suppliers`、`SupplierParts`、`Inventory`。
- 認證：JWT ＋ BCrypt ＋ Role-based ＋ Rate Limiting。
- **保養三表已於 2026-06-06 由 migration `RemoveMaintenanceModule` drop（Down 可還原）**。

### 3.2 MM MmsDB（外掛自帶，先前移出的設計）

| 資料表 | 用途 | 備註 |
|---|---|---|
| `MaintenanceSchedules` | 保養排程 | 頻率 Daily/Weekly/Monthly/AdHoc |
| `SpareParts` | 備品零件 | 庫存量、最低庫存閾值 |
| `MaintenanceRecords` | 保養/維修紀錄 | FK→Schedule、FK→SparePart，建立時自動扣庫存 |
| `MaintenanceSettings` | ERP 級聯設定 | `SettingSource`: InheritErp / LocalOverride；`EffectiveValue` 依 Source 動態取值（類 CSS cascade） |

**級聯設計重點**：`EffectiveValue = Source==LocalOverride ? LocalValue : ErpValue`。ERP 透過 `POST /api/settings/erp-sync` 推送 `Key+MachineCode → Value`，只更新 `ErpValue` 快取，本地覆寫項不受影響；來源可隨時切換。（ERP/MES 目前**只保留架構不實接**。）

### 3.3 MM API 端點（:5300）

| Method | Path | 說明 |
|---|---|---|
| GET/POST | `/api/schedules` | 保養排程 |
| GET/POST | `/api/parts` | 備品零件 |
| GET/POST | `/api/records` | 保養紀錄（自動扣庫存） |
| GET/POST/PUT/DELETE | `/api/settings` | 級聯設定 CRUD |
| POST | `/api/settings/erp-sync` | ERP 批量推送設定值 |

> 注意 MM 的 `/api/parts` ＝ **備品 SpareParts**，與主系統 `/api/v1/parts`（零件主檔 Parts）**不同**。

## 5. 重新拆分：三個方案

這是本文件**最需要 Eric 拍板**的部分。現況（方案 B）是「核心＋內建零件 ｜ 外掛保養」。三個選項：

### 方案 A — 全內建（回到 Phase 5 大一統）
把 MM 併回主系統，保養三表回 FlexoDB，單一前端單一後端。
- ✅ 部署最單純（一個 compose）、認證/資料零跨系統。
- ❌ 與 2026-06「保養外掛化、客戶選配」的商業定位**衝突**；主系統重新變胖。
- 適用：若所有客戶都要保養，且不打算單獨賣 MM。

### 方案 B — 現況：核心＋零件內建 ｜ 保養外掛（**目前狀態**）
- ✅ 保養可選配、可單獨部署、可單獨賣；主系統乾淨。
- ✅ 真分離（後端不互引），MM 自帶 DB。
- ⚠️ 兩套 parts 概念並存（主系統 Parts vs MM SpareParts）易混淆；MM 尚未版控；`mms.ericchh.work` 前端入口待補。
- 適用：保養是加值選配（最貼近目前商業敘述）。

### 方案 C — 全模組外掛化（核心最小，零件與保養都外掛）
把 Smart Parts 也比照 MM 抽成外掛，主系統只留即時監控/排程/報表。
- ✅ 核心最精簡、每個加值模組獨立賣／獨立部署、邊界最清楚。
- ❌ 工程量最大（要把已併回 FlexoDB 的零件再拆出）、跨系統認證與資料同步成本上升、與 Phase 5 收攏方向再次相反。
- 適用：要做成「核心 ＋ 可插拔模組市集」的產品策略。

> 我的傾向：若商業上保養／零件是「選配加值」，**方案 B（現況）已是合理落點**，重點不是再動架構，而是補齊三件治理缺口（見 §6）。只有當零件也要獨立販售時才走 C；只有當確定全客戶都要保養才走 A。
