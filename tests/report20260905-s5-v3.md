### T3 通過的判斷

- **AC 集合與 DoD 對得起來**:AC-01~46 逐條有對應測試,且皆非空轉(見 T1-5)。
- **既有測試沒有被放寬授權規避**:五個既有整合測試檔一律以 `TestAuthTokenFactory` 補權杖,授權層本體未被關閉。
- **不在範圍內的事項確實沒被偷做**:未新增 NuGet / npm 套件、未改 `docker-compose.yml`、未改 `ASPNETCORE_ENVIRONMENT`;
  `appsettings.Testing.json` 的測試密鑰依 §3.4 保留不動。
- **RD 交付報告完整**:`docs/report20260905-2.md` 含 §12 全部 R1~R10、§4.5 部署七步原文,並附可勾選的上線檢查清單。
- **RD 主動補強超出規格**:`noBareApiFetch.test.js` 把「不得繞過 api.js」變成靜態掃描,補上了規格 §7 原本沒有的防線;
  `LoginShiftProfile.test.jsx` 釘住班別顯示。兩者都是加分項。

### 阻斷項【G-1】login 的帳號大小寫比對語意規格全篇未定義,與 §4.2「不分大小寫唯一」不對稱,會在現場造成鎖門

**事實與行號**

1. 規格 §4.2 明訂建立使用者時 `username` **不分大小寫唯一**;實作照做 ——
   `backend/PrintingIoT.API/Controllers/AuthController.cs:202-204`
   以 `StringComparison.OrdinalIgnoreCase` 比對既有帳號,AC-22(`AuthSetupAndUsersTests.cs:225-241`,`Op8` vs `oP8`)驗證通過。
2. 但登入端是**精確比對**:`backend/PrintingIoT.API/Controllers/AuthController.cs:57`

   ```csharp
   .FirstOrDefaultAsync(u => u.Username == request.Username);
   ```

   在 PostgreSQL 預設 collation 下為大小寫敏感;
   `backend/PrintingIoT.Infrastructure/Data/PrintingContext.cs:73-74` 的唯一索引也沒有指定 case-insensitive collation。
3. 規格**沒有任何一處**定義 login 的帳號比對語意:§2.3 只寫授權層級、§7.2 的 AC-13/14/21 全部以**相同大小寫**建立與登入
   (`AuthSetupAndUsersTests.cs:201-223`,建 `op7` 登 `op7`),§8 的 E1~E15 也沒有這條。

**後果(正是規格自列最高可用性風險 R2 的失效模式)**

- §4.5 第 5 步要求部署者建立「至少涵蓋目前使用中的 OP1~OP5」的帳號。若管理者以 `OP1` 建立,
  現場作業員輸入 `op1`,後端查無此帳號 → 401 → 前端只顯示「帳號或密碼錯誤」
  (`LoginModal.jsx:150`,依規格 §5.4 刻意不區分原因)。
- 使用者看到的是「帳號明明存在卻登不進去,而且系統說我密碼錯」,現場只能停線等管理者。
- 名冊點列會填入 `u.username`,而 `LoginModal.jsx:159` 的 `handleAddUser` 把 `username` 設為
  **顯示名稱** `newUserName`(不是代碼),與後端帳號本來就可能不一致,更容易踩到。

**為何判給 PM 而非 RD**

- RD 完全按規格寫的做了:§4.2 說不分大小寫唯一就做不分大小寫唯一,§10 檔案清單沒有要求改 login 的比對方式,
  `u.Username == request.Username` 是 S5 之前就存在、規格未指示更動的程式碼。
- 這是**規格層的定義缺口**:同一個 `username` 欄位在「建立」與「登入」兩端採用了不同的相等語意,而規格只寫了其中一端。
- S5 之前登入是裝飾品(前端硬編碼帳號),大小寫從不影響;**是 S5 把 login 變成唯一入口才把這個缺口變成現場風險**。

**PM 下一版規格需補的內容**

1. **定義 login 的帳號比對語意**(擇一寫死):
   - (a) 全面 case-insensitive:登入查詢改正規化比對,且 `Users.Username` 的唯一索引需在 migration 改為
     case-insensitive collation(或存入前一律轉小寫),否則 app 層與 DB 層規則仍不一致;
   - (b) 維持精確比對:§4.2 的「不分大小寫唯一」就該一併改成精確唯一,並在 §4.5 部署步驟明寫
     「建立帳號時的大小寫必須與現場實際輸入完全一致」。
2. **補一條 AC**:例如「以 `OP1` 建立帳號後,用 `op1` 登入的結果必須為 <所選語意的預期值>」——
   目前 §7 沒有任何 AC 會抓到這個分歧。
3. **補一條 §8 edge case**:帳號大小寫不符時的預期行為與現場處置方式。
4. 順帶明確 `LoginModal` 名冊列的 `username` 應對應**後端帳號**而非顯示名稱(§5.4 目前只說「填入帳號欄」,
   沒說名冊的 `username` 從哪來)。

### 阻斷項【G-2】§8 E6(CORS 預檢)規格自訂「必須實測確認」,但 §7 沒有對應 AC,DoD 因此不涵蓋

**事實**

- 規格 §8 E6 原文:「CORS 中介軟體在授權之前處理,預檢**不得**被 fallback policy 擋成 401 ——
  **順序修正後必須實測確認**。」
- §7.3 只有 AC-26(429 帶 CORS 標頭)與 AC-27(轉發位址分區),**沒有任何 AC 涵蓋 OPTIONS 預檢**。
- §11 DoD 第 4 條寫的是「§7 全部 AC-01 ~ AC-46 有對應測試且通過」,E6 不在 §7,於是這條「必須實測」的要求
  **沒有任何驗收出口**。
- 獨立複驗:

  ```
  $ grep -rn "HttpMethod.Options" backend/ --include="*.cs"
  (no OPTIONS test)
  $ grep -rn "Access-Control" backend/PrintingIoT.Tests/ --include="*.cs"
  (只有 RateLimitAndCorsTests.cs 的 AC-26,全部是對 POST 回應的斷言)
  ```

**影響評估(誠實標註)**

以 ASP.NET Core 行為推論,`UseCors()` 位於 `UseAuthorization()` 之前時,CorsMiddleware 會短路處理
帶 `Origin` + `Access-Control-Request-Method` 的 OPTIONS 請求並直接回 204,不會進到端點與 fallback policy,
因此**實際行為極可能是正確的**。G-2 指的是**驗收契約的洞**,不是已證實的功能缺陷 ——
但規格自己白紙黑字寫了「必須實測確認」,而目前無人實測、也沒有機制在未來回歸時抓到它。

**PM 需補的內容**

- 把 E6 升格為一條 AC(例如 AC-47):
  「帶 `Origin: <允許來源>` 與 `Access-Control-Request-Method: POST` 的 `OPTIONS /api/orders`
  在**未帶任何權杖**時,回應**不得**為 401,且必須帶 `Access-Control-Allow-Origin`」,
  置於 `backend/PrintingIoT.Tests/Integration/RateLimitAndCorsTests.cs`。
- 一併檢視 §8 其餘 edge case 是否也有「寫了預期行為卻沒有 AC」的情形
  (E10 `Auth__SetupToken` 未清空、E13/E14 舊 localStorage 清理,目前分別靠報告檢查清單與前端測試涵蓋,尚可;
  E6 是唯一一條規格明講「必須實測」卻完全無出口的)。

### T3 非阻斷的觀察(記錄,不影響本輪判定)

- `frontend/src/modules/auth/RequireAuth.jsx:28-30` 的 403 區塊文案(`權限不足 (Forbidden)`、`回首頁`)硬編碼正體中文,

  但規格表格的「情境」欄隱含了「有合法 body」的前提,未來若有人依表格逐條測會困惑。屬文件精確度問題,不阻斷。

  以本系統的使用者建立頻率(部署時一次性)而言風險可忽略,列此僅供 PM 在處理 G-1 時一併決定。
