## T3 · Judgment(驗收契約是否合理、edge case 是否被涵蓋)

### T3-1 驗收標準本身是否合理

- AC-13(把產出從良品移到不良品 → 效能**下降**)與 AC-14(準備時間增加 → 稼動率**上升**)是**方向性斷言**,能真正證偽「換公式了沒」,而不是把實作數字抄進測試。合格的驗收設計。
- AC-11 明確要求「分母為零 → 0 而非 100」,且 `Calculate_TargetZero_...` 額外加了 `Assert.NotEqual(100m, ...)`,把舊 bug 釘死。合理。
- AC-16 要求「不可退回 UTC」而非只要求「不拋例外」—— 直接針對 bug 本體,合理。
- AC-23 用**同一組數值**同時釘住 C# 與 JS,是雙實作漂移的唯一有效防線。合理。
- §8 的 15 條 edge case 有 12 條在測試中有直接對應(冪等、defects 全 0、stops 空但停機時間 > 0、目標為 0、超產、準備時間過大、大夜班、日界 0、缺 tzdata、原因主檔清空、`completedAt` 缺漏)。涵蓋率足夠。

### T3-2 非阻斷觀察(建議併入下輪 backlog,不影響本輪判定)

**O1 · `syncState: 'pending'` 沒有任何重送路徑,也沒有 UI 呈現**
`Dashboard.jsx` 落地失敗時把本地紀錄標 `pending`,但全前端搜尋不到任何讀取 `syncState` 的地方 —— 既不會重試,也不會提示現場「有 N 筆未同步」。後果:斷網期間完工的實績**永久不會進入後端**,而 S3 的核心主張是「後端是實績的權威來源」。
規格 §8 第 1 列只承諾「不阻擋現場」,§9 backlog #2 只涵蓋「既有 localStorage 資料回填」,**未涵蓋新產生的 pending 紀錄**。規格既未要求、AC 也未涵蓋,不構成本輪阻斷。
**建議下輪**:新增 pending 佇列重送(可沿用既有 `clientRecordId` 冪等鍵,重送零風險)+ 前端顯示未同步筆數。

**O2 · 冪等命中時不會補做工單狀態推進**
`ProductionService.RecordCompletionAsync` L70–L96:命中既有 `ClientRecordId` 即直接回傳,`OrderStatusUpdated` 硬寫 `false`。若第一次 POST 落地成功但 `UpdateStatusAsync` 失敗(AC-04 情境),重送同一筆**不會**再嘗試把工單推進 `Completed`,工單將永遠停在 `Pending`。
規格第 2 條明文「命中 → 不新增、不更新」,實作**忠實照做**,故非實作缺陷;是規格未考慮到的組合(冪等 × 狀態推進失敗)。
**建議下輪**:冪等命中時仍嘗試一次 `UpdateStatusAsync`,或把 `OrderStatusUpdated` 持久化。

**O3 · `stops[].startedAt` 實務上恆為 null**
後端 DTO 與資料表都留了 `StartedAt DateTime?`,但 `Dashboard.jsx` 送出的 `stops` 只帶 `{ code, reason, durationMinutes }` —— 因為 `stopReasons` 在前端只存 `HH:MM:SS` 字串、無日期,無法安全組出 UTC 時間戳。結果該欄位在現行流程下是死欄位。
規格 §F2 範例本體有 `startedAt`,但無任何 AC 要求前端必須帶,實作選擇不猜測日期是保守且正確的。
**建議下輪**:前端停機紀錄改存 ISO 時間戳,再回填此欄。

**O4 · `completedAt` 格式錯誤的 400 回應本體與 §6 不同形**
§6 表列「`完工時間格式不正確`」,但實作未在 `Validate` 內處理 —— 非法日期字串在 ASP.NET 模型繫結階段就被 `[ApiController]` 攔下,回的是 `ValidationProblemDetails`,而非 `{ success: false, error: "完工時間格式不正確" }`。狀態碼仍是 400、仍零寫入,且 AC-06 只指定 `goodQty` 為負與 `clientRecordId` 空白兩例,故不違反任一 AC。
**建議下輪**:若前端要依 `error` 欄位顯示訊息,需統一 `InvalidModelStateResponseFactory`。

**O5 · 規格 §F2 範例 JSON 的數字與 §5.1 互相矛盾(文件層面)**

**O6 · `useReasonCodes` 的 fallback 清單不隨語言切換重新翻譯**
`applyFallback` 的 `useCallback` 依賴為 `[type]`(刻意以 eslint-disable 抑制),閉包捕捉的是首次渲染的 `fallbackList`。`FinishOrderModal.jsx` 註解寫「語言切換時內建預設也跟著翻譯」,實際上在 API 失敗、且元件未卸載重掛的情況下不會重新翻譯。
