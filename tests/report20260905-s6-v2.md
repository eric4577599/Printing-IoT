### T3-1(阻斷)規格漏掉名冊的第二個寫入點,缺口 G-1 在管理者路徑上原封不動

**事實(全部可複驗):**

`localStorage.appUsers` 這份名冊有**兩個**寫入元件,規格 §7 / §11 只認定了其中一個:

| 元件 | 寫入點 | `username` 取值 | 規格是否涵蓋 |
|---|---|---|---|
| `frontend/src/modules/auth/LoginModal.jsx` | `:171` / `:180`,新增列在 `:162` | `newUserCode`(代碼),本輪已修 | §7 表格兩列 |
| `frontend/src/components/settings/GeneralTab.jsx` | `:67` / `:135` / `:149`,新增列在 **`:111`** | **`newUserName`(顯示名稱),未修** | **完全未提及** |

```
$ grep -rn "appUsers" frontend/src | grep -v "/tests/"
frontend/src/components/settings/GeneralTab.jsx:57,67,135,149
frontend/src/modules/auth/LoginModal.jsx:32,36,171,180

$ grep -n "username" frontend/src/components/settings/GeneralTab.jsx
63:                username: u?.username ?? u?.name ?? '',     ← 缺 `?? u?.id`,與 LoginModal:18 的修法不一致
111:            username: newUserName,                          ← 這正是 §7 要修掉的那一行,原封不動
```

`GeneralTab.jsx` 是**設定 → 一般 → 使用者名冊**,也就是管理者實際維護現場帳號名冊的地方;`LoginModal` 的名冊子面板只是登入畫面上的便利入口。規格挑到的是次要入口,漏掉主要入口。

**造成的實際後果(不是理論風險):**

1. 管理者在設定頁新增「代碼 `OP1` / 操作員 `王小明`」→ 寫入 `{ id:'OP1', name:'王小明', username:'王小明' }`。
2. 作業員在登入畫面點該列 → `LoginModal.jsx:113` `setLoginUsername(u.username || u.name || '')` 填入 **`王小明`** → 送出 → 後端查無此帳號 → **401**,畫面只說「帳號或密碼錯誤」。
   —— 這正是規格 §0 描述 G-1 時所寫的「現場停線且無人猜得到原因」,一字不差,只是換了一條路徑進來。
3. AC-60 的 id 遞補**救不到**這種列:`u?.username ?? u?.id` 的第一段有值(是顯示名稱),遞補不會發生。
4. `GeneralTab.jsx:57-67` 在掛載時會把 sanitize 後的名冊**回寫** `localStorage`,因此上述值會被持續保留、擴散到 `LoginModal` 讀到的同一份資料。

**規格 §10 E20 的敘述因此是錯的(反向成立):**

> E20:「管理者把該列**重新儲存一次**(Upsert)即修正」

管理者最自然的「重新儲存」動作就是進設定頁重存一次 —— 而那條路徑會走 `GeneralTab.jsx:111`,**再一次把顯示名稱寫進 `username`**。唯一真正能修正該列的操作,是在登入視窗的管理者子面板重存。規格把一個會**加深**問題的動作寫成了修復指引,交付報告 `docs/report20260905-2.md:151-160` 也照抄了這個說法,部署者與管理者會照著做。

### T3-2(不阻斷,供 PM 一併決定的觀察)

1. **migration 回填規則與 C# 正規化在非 ASCII 上不等價**:`20260905010000_...cs:37` 用 PostgreSQL 的 `UPPER(TRIM(...))`,應用層用 `ToUpperInvariant()` / `.Trim()`。PG 的 `UPPER` 受資料庫定序影響、`TRIM` 預設只去空白字元,而 .NET 的 `Trim()` 會去掉所有 Unicode 空白(Tab、NBSP 等)。若既有帳號含非 ASCII 字元或非空白的空白字元,回填值會與應用層算出的值不同,該帳號登入後查無資料。規格 §10 E21 已把非 ASCII 帳號劃出範圍,故不阻斷;建議在部署前置檢查 SQL 旁補一句「本檢查僅對 ASCII 帳號成立」。
2. **交付報告內部交叉引用不一致**:報告 §2 標題為「部署者操作順序(規格 §4.5,原樣照抄)」,但 R2(`:306`)與 `:178` 仍寫「§4.5 第 5 步」,指向的是 S5 規格的節號而非本報告的 §2。這是規格 §13「必須原樣保留、用字不可軟化」造成的既有現象,**不建議 RD 自行改寫**;若要修,應由 PM 在下一輪規格明確授權(例如統一寫成「§2(原 S5 規格 §4.5)第 5 步」)。
3. **E19 / 併發 409 分支確實無自動化出口**,規格與程式碼註解都誠實標註,AC-53 + 程式碼審查的替代把關可接受;已複核 `AuthController.cs:141-150 / 236-245` 兩處 catch 都在,無誤。
